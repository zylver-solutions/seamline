### Why ADR-0005 and aspirational 6B.2 are in the way

ADR-0005 makes the contradiction the primary output and defers gaps entirely. Aspirational 6B.2 turns that into a standing prohibition: "No declaration-driven gaps. ... A report that says 'you failed to annotate this' is not shipped, at any version." Both exist because v2's gap report asserted the absence of a declaration, produced thousands of findings, and could be cleared by a substring (`docs/audit/2026-08-29-council-review-v2.md`; ADR-0005 DA-02, DA-03, DA-04).

The four items above are not that. Each is an assertion the maintainers already wrote, in a structured place, that the implementation does not support. The remedy for each is a change to a document or to code, never an annotation. But two of the four are "claimed, absent" and the only word the current text gives such a thing is "gap", which 6B.2 forbids. The rule must be amended so that it forbids what it was written to forbid and allows what it was never about. Left alone, the choice is to ignore the drift or to ship it under a name the project has already ruled out.

The word also collides. In v3 and ADR-0005, a gap is a **missing declaration** (`docs/design/v3.md:32`: "A gap is a complaint about documentation."). In the classes below, a gap is a **present claim with no implementation**. The missing side is opposite. This record uses the new meaning only inside the names "Planned gap" and "Unexplained gap", and says so wherever they appear.

## Admission (aspirational-state section 5.3)

All three legs are required. They are recorded here, not assumed.

1. **Cited instance.** The four false statements above in the pre-fix tree, in this project's own repository (which section 5.3 leg 1 explicitly counts). They shipped; they are not synthetic.
2. **Named owner.** `@zylv3r`, the repository owner (the owner in `.github/CODEOWNERS`), runs the capability against this repository and triages what it reports. **Window: three triage passes after the implementing change merges, or the first public release, whichever is later.** A triage pass is one run of `seamline align` against the head of the main branch, with every reported Observed drift, Unexplained gap and Unknown either fixed or labelled a true or false positive in a comment on the implementing pull request. The window starts when that pull request merges, not when this record does, because the capability does not exist before then, and it does not end while a permanent public command has nobody triaging it. The window has no calendar bound or cadence of its own: three passes could happen in one afternoon, and the clause "or the first public release, whichever is later" is what prevents that from ending it early. The owner may restate the window as a comment on the pull request that introduces this record; a restated window replaces this one in a follow-up edit to this section.
3. **Design-spec pass.** [`docs/design/alignment.md`](../design/alignment.md) is that pass. The implementation change builds against it without further decisions.

## Decision

**Add a second report family, alignment, beside contradictions. It compares claims that documents already make with facts about the implementation, classifies each comparison into exactly five classes, never gates anything, and is emitted as a versioned, redacted, consumer-agnostic finding packet.**

### 1. Five classes, from a decision table

Every comparison ends in exactly one class. The full table is `alignment.md` section 6; its shape is:

| Class               | Meaning                                                                                                                                                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Observed drift**  | The documentation makes a claim and the implementation has a counterpart whose value disagrees with it (or, under an exact probe, the documentation marks something absent or deferred that the implementation now has). |
| **Unexplained gap** | The documentation claims something exists or works, the implementation has no counterpart, and nothing in the documentation says that is expected.                                                                       |
| **Planned gap**     | As above, but the documentation itself marks the item deferred or planned. It is reported, not suppressed.                                                                                                               |
| **Unknown**         | The comparison could not be made: an extractor or probe was not `PASS`, the input is unsupported, or the claim cannot be anchored. Never read as absence (AGENTS.md invariant 3, ADR-0003).                              |
| **Resolved**        | A baseline packet reported Observed drift or Unexplained gap for this subject, and the subject now agrees, or is now explained, or the claim is gone. Never produced from Unknown.                                       |

Only a probe that can see absence reports a gap: the output-format probe, the detector-liveness probe and the manifest probe can, and each only over a closed set of witness sources that the design lists per probe (`alignment.md` 5.4). If the tree holds a declaration or a source of a kind the probe knows can carry the fact and the probe does not read it (a floor pinned in a file other than `engines`, or nearer than the `engines` a package would inherit from the root, a library that a bundled CLI lists under `devDependencies` or reaches through a pnpm alias, an extractor in another language), the answer is Unknown, never a gap and never drift. The control-wiring probe cannot, because the extraction records static imports only, so a control claim is aligned or Unknown and never a gap (`alignment.md` 4.4).

### 2. Documents are inputs with provenance, and claims come from structure and closed templates

A claim is read from Markdown by a deterministic scanner in two steps, and this record states both because an earlier draft described only the first.

1. **Structural anchors.** Tables, headings, list items with a bold lead label, front matter scalars and inline code spans give the scanner its units (a table row, a list item, a paragraph) and, for control claims, the path a document names.
2. **Closed sentence templates.** Within a unit, the scanner splits sentences and tests each against a fixed list of templates built from closed word lists (`alignment.md` sections 3.2, 4.2 and 4.3). **This is pattern matching on prose.** It has no model, no scoring and no fuzzy matching, and it is not natural-language understanding. What distinguishes it from the keyword matching the Alternatives section rejects is that a template must match a whole sentence, from first token to last, with the subject, verb and object in fixed positions; a sentence that merely contains the right words yields nothing. There is one exception, stated here so that it is not discovered later: the `DEFERRED` detector markers (`alignment.md` 4.3) test a label or a sentence for a detector code and a dormancy cue from a closed list, wherever they sit in it, and range phrases such as "X1 to X10" are excluded from the codes. The marker is the one non-template rule; a wrong marker can only produce a Planned gap or an `Unknown(cannot-confirm-presence)`, never drift. Parenthetical groups are deleted before matching, so an enumeration in an aside is never a claim, and an output-format claim needs the CLI named in the sentence (as its subject or in a closing "from the CLI"), so a component page describing its own output does not match. The reading is tightened where a replay over the in-set documents showed it would otherwise invent a claim: `packages/extract-contracts/README.md:3` lists input formats in a parenthetical and uses the verb "emitted", and yields nothing under the templates.

The set of claim kinds is **closed at four** (`RUNTIME_FLOOR`, `OUTPUT_FORMAT_SET`, `DETECTOR_LIVENESS`, `CONTROL_ENFORCEMENT`), each with a fixed anchor and template set and a fixed implementation fact. Adding a fifth, or a template, needs an amendment to this record, not a pull request to a lexicon. Every claim carries its file, line range, commit and extractor version, and is labelled `DECLARED` (a human wrote it); each input document carries the SHA-256 of its bytes. Every implementation fact is `EXTRACTED` or `DECLARED` and comes from Seamline's own extraction of the same commit, from sources read at that commit, or from a manifest the repository already keeps (`package.json`). There is no expectation file.

**Which code a control claim is about is decided by the document alone.** A control row is bound to code only when the row itself names a path that exists in the tree (binding B1). A row that names no path is `Unknown(claim-unanchored)`. A candidate found by wording shared between a row and a source comment is a **proposal**: it lives in a separate array of the packet, carries `INFERRED`, and is never read by the classifier. A proposal becomes a claim only when a human edits the document to add the path. This is AGENTS.md invariant 5 and ADR-0007 section 5, applied to documents. An earlier draft admitted a second binding, a shared term (`capability manifest`) between the row and a source file's header comment, as a code-side anchor. It is not admitted: two human-written texts that share a phrase are joined by a name match, a name match is `INFERRED`, and a finding must not rest on an inferred link. The consequence is accepted and stated: in the pre-fix tree the C4 row names no code, so the tool reports C4 as `Unknown(claim-unanchored)` with a proposal naming `sandbox.ts`, not as drift.

### 3. Drift never gates

`seamline check` is unchanged: its exit codes, its JSON and its gating of critical and high contradictions (`packages/cli/src/commands/check.ts:95,108`, `packages/cli/src/render.ts:17-19`, main) stay exactly as they are. Drift is reported by a new command, `seamline align`, which exits 0 whatever it reports and has no flag that makes it fail. Its only non-zero exits are usage errors (2) and runtime errors such as a redaction refusal (3), neither of which depends on what drift was found. Contradiction codes X1 to X10 keep their gating semantics.

### 4. The finding packet

`alignment.md` section 8 specifies schema v1: stable path-free ids, run provenance (including whether the pairing of tree and run was verified or asserted), a canonical byte order, a digest, and redaction through the existing redactor as the sole writer (ADR-0011, [ADR-0013](ADR-0013-redactor-never-rewrites-identity.md)). Producing the packet requires an export profile that opts in; there is no profile-free packet (AGENTS.md invariant 6). The summary printed without a profile is a projection of the same redacted packet through the same single write site.

### 5. No change to the frozen contract

Claims are not graph nodes in this design, so no node kind, edge kind or contract type is added. `alignment.md` section 10 records the alternatives that would need a contract or extraction change and why they are not taken.

### 6. Beside the contradiction pipeline, and not an extractor

Alignment is a second report family **beside** the contradiction pipeline (extract, merge, infer-join, X1 to X10, check, export, MCP), not a stage inside it. No pipeline stage imports `@seamline/align`: the CLI package is in the strict list of the semantic-boundary test, and within it only the `align` command, a report command beside the stages and not one of them, does. The package must be classified in the semantic-boundary test's package lists introduced by ADR-0015 (design section 9), as a package that is held to the same no-import rule as the pipeline.

It is also not a fourth source extractor in the sense of aspirational 6B.5 (no extractor sprawl), although three of its probes parse TypeScript and read package manifests. The reasons: it writes no node and no edge; it has no scope, so no result it produces can be mistaken for an authoritative scope of a run; it is not registered with `extract` and runs only under `align`; and it is bounded by four claim kinds rather than by the number of source entities. It carries the controls that make sense for a reader of untrusted input: declared inputs only, no execution, no network, bounded work, and a fixed output. The maintenance cost 6B.5 names is real and is paid in the four probes; adding a fifth claim kind, which is where sprawl would start, needs an amendment to this record.

## Amendment to ADR-0005

ADR-0005 stays in force as written, with this scope of change:

- **Unchanged:** the decision that the contradiction is the primary output; detectors read facts only; a detector with a non-`PASS` scope emits `UNKNOWN`; every detector carries a fixture pair and a meta-test; the ten codes X1 to X10; their severities and their gating; the 10-minute acceptance test; the deferral of the needs matrix, waivers and any readiness gate.
- **Changed:** "Gaps are deferred entirely from v0.1" is narrowed. What remains deferred is every report whose input is the **absence of a declaration** (code, schema or a contract with no document, annotation, owner or requirement). What is admitted is a report whose input is a **present, anchored claim** that the implementation facts do not support, in the five classes above, as non-gating drift.
- **Still prohibited, at any version:** reporting that code has no documentation; any suppression flag, waiver or escape hatch on a drift finding; any gate or readiness score derived from drift; any class that counts undocumented code. The decision table has no row that does.

Why the admitted report is not v2's gap: it is bounded by the number of claims the closed anchors and templates extract from the documentation, not by the number of code entities (v2's 3,000 to 4,500); it cannot be cleared by an annotation, waiver or flag, because the only ways to change a finding are to change the claim or to change the implementation (a marker beside something the implementation has is not rewarded: in v1 it becomes `Unknown`, and under an exact probe it would be drift); and it never gates, so a wrong finding cannot fail a build. It is **not** ungameable: a sentence reworded to fall outside every template stops being a claim and is reported as `Resolved` with reason `claim-removed`, which is why that reason is distinct and visible; and a word that satisfies a presence witness in the code satisfies a claim of presence. Both limits are stated below.

`docs/design/aspirational-state.md` section 6B.2 is edited in place to say the same, with a pointer to this record. `docs/design/v3.md` is edited in the same change, at line 32 only, to point here: "v0.1 ships contradictions and defers gaps" remains true of declaration-driven gaps, and the line now says where the narrower, admitted report is decided. `docs/adr/README.md` records the amendment mechanism (ADR-0013 amends ADR-0011 and this record amends ADR-0005 the same way).

## Consequences

### Positive

- The class of failure described in Context becomes visible: a claim and a fact that disagree are reported with both sides, each cited to a file and line range.
- Docs-truth fixes become provable. A fix is a `Resolved` record against a baseline packet; a "fix" that deletes the claim is distinguishable (`claim-removed`) from one that corrects it.
- A failed extraction cannot masquerade as agreement or as resolution. A crashed or unavailable extractor may be recorded with no scopes (today `unavailable()` and `failed()` write `authoritative: []`, `packages/cli/src/commands/extract.ts:405-416` and `:450-461`, main), so the design reads a scope table and not the list of extractors: a detector is called dormant only when every scope it declares it depends on is declared and `PASS` in the run, and a scope that no result declares is `Unknown(scope-not-pass)`, never absence; a source probe reports absence only when the code reading passed, package discovery was complete (the manifests parsed and the workspace file was read in full) and no source of a kind it knows can carry the fact went unread (`alignment.md` 5.4). The same documentation bytes classify as Unexplained gap when extraction passes and Unknown when it does not, and a baseline drift never becomes Resolved on an Unknown. The detector's own scope list, the one `seamline check` gates it on, cannot see an extractor that did not run, so a detector is additionally called dormant only if no extractor package of the evaluated tree (`packages/extract-*`, `packages/infer-join`, and any package whose source mentions the identifier `ExtractorManifest` at all, except the vocabulary package `@seamline/ontology`, which is exempt by name and not by shape) names the kind as a string literal or an identifier; otherwise it is `Unknown(scope-not-pass)` naming the file. A run that records an extractor as failed, with no scope, when no package of the tree carries that name is `Unknown(scope-not-pass)` too. That is a rule of the probe and is replayed with it (design 4.3 and 12.1), not an inspection. What stays invisible is an extractor outside the discovered packages whose failure the run does not record (a `contrib/` extractor, `THREATMODEL.md` C13).
- Other consumers (agents, review tools, a later MCP tool) get one stable, redacted artifact instead of scraping command text.

### Negative

- **Coverage is deliberately narrow.** Four claim kinds, anchored by structure and a closed template list. A document that says the same thing in free prose is invisible (so is a marker inside a parenthetical, such as `docs/design/v3.md:260` in the pre-fix tree); so is any drift whose implementation fact the four probes cannot see. Detector dormancy is measured at the level of node kinds only, under the assumption that each kind a detector reads is required, so X3, X5, X7 and X8, which are dormant for property-level reasons, are not reported, and a detector that reads a kind only optionally would be over-reported. It is also relative to the run and the tree: it says that the scopes the detector requires passed, that no scope of the run declares the kind and that no extractor package of the evaluated tree names it, not that no extractor anywhere could produce it.
- **The self-proof reports three of the four false statements as drift, and the fourth as `Unknown`.** The C4 row named no code in the pre-fix tree, and the extraction records no `IMPORTS` edge that crosses a package (0 of 727 in the committed self-extraction in the pre-fix tree; 0 of 978 on the code of main as of 2026-10-19), so the graph cannot show that a module of a package with dependents is unused. The module-wiring probe answers `Unknown(cross-package-unobservable)` for such a module, and it never reports a module as unwired at all: the extraction records only static `import` and `export ... from` edges, so a dynamic `import()`, a `require()`, a `new URL(..., import.meta.url)` reference, a path run from a `package.json` script and any file the run did not read are consumers it cannot see (`alignment.md` 4.4). A control claim is therefore **confirmed or Unknown, never an Unexplained gap**: the probe has no `ABSENT` result. An entry point (the source of a package's `bin`, `main` or `exports` target) is confirmed by the manifest that names it when a row names that file itself, and a path that holds only tests is `Unknown(non-extracted-anchor)`. **Naming `packages/core/src/security/sandbox.ts` in the C4 row in the pre-fix tree would still have given `Unknown(cross-package-unobservable)`**, because `@seamline/core` has dependents; a control row is confirmable only when it names code the extraction reads and that a non-test file of the same package imports statically, until workspace imports resolve to package sources (a follow-up extraction change, `alignment.md` section 10). The sandbox-wiring change makes C4 confirmable because its row names `packages/cli/src/sandbox/`, whose consumers are in the same package. The cost is stated: this probe cannot find the defect that motivated it, only decline to confirm the claim. The other controls that carry an enforcement cue are `Unknown` as well: C3 and C8 name whole packages (`Unknown(cross-package-unobservable)`), and C9 names `scripts/license-gate.mjs`, a file the code reading does not cover (`Unknown(non-extracted-anchor)`); the exact records are in `alignment.md` 4.4 and 12.1.
- **Declared entities beyond `package.json` are not read.** `ontology/seamline.yaml:684` carried the same false CSV and Mermaid statement in the pre-fix tree and is outside the input set, because it is not Markdown. That is a conscious limit.
- **Some of the clearest statements are not read.** The per-code catalog in `docs/contradictions/README.md` (links in its first column, and a "Status today" column that says which detectors fire) does not match the catalog anchor and is silently unread; the output-format sentence in `docs/reference/ontology.md` sits in a parenthetical and is unread. Reading either would be a new anchor and an amendment to this record. The tool reports what the closed anchors find, and says nothing about the rest.
- **The lexicons are a maintenance cost and a brittleness.** A reworded sentence can drop a claim, which then reads as `Resolved` with reason `claim-removed`. The reason code and the per-document claim counts in the packet are what keep that visible; they do not prevent it.
- **Presence witnesses are weak.** An output-format `AFFIRM` is satisfied by any identifier or property name in the scanned code whose words include the format, or by a string with that name that is an operand of an equality comparison or a `case`, or by the name of a file, a directory or a dependency of the scanned packages (`alignment.md` 4.2); a module counts as wired when non-test code imports it, or when a manifest names it as an entry point. Neither proves the feature works. They are therefore used only to avoid reporting, never to report: `HOLDS` produces no drift class, and a stale marker beside it is `Unknown(cannot-confirm-presence)`. A `HOLDS` can produce a `Resolved` record (`fact-changed`), and a name witness is gameable by anyone who can add a file (a stub `csv.ts`, an unused `csv-stringify` dependency); `fact.detail` of a `HOLDS` begins `token` or `name` so a reader sees which witness stood. A name that only sits in a list (an array, a `Set`, a call argument) is deliberately not a witness, because unrelated name lists collide with format names (a MySQL storage-engine list on main holds `'csv'`); the accepted cost is that a format selected only through such a list reads as absent, one of the few ways a format `ABSENT` can be wrong toward reporting (the others are the named residue of `alignment.md` 5.4: a name that does not spell the format as words, a renderer reached through a computed specifier, a format named only inside a data file, a spawned executable). A scan-set package that is not wholly TypeScript or JavaScript, an import that leaves the scanned set (a relative path out of the package, a workspace package its manifest does not list, a `tsconfig` path alias, also one reached through a relative `extends`, a dependency that names a path or an alias to a package the discovery did not reach, a `bin` package that the discovery did not reach), or incomplete package discovery (a manifest that does not parse, a workspace file or entry the reader cannot read), makes an absence `Unknown` instead.
- **Absence is closed-world per probe, and the residue is stated.** `alignment.md` 5.4 lists, for each of the three probes that can answer `ABSENT`, the sources it reads, the sources of known kinds it does not read (each an `Unknown` with a named reason) and the residue the tree gives no evidence of. The residue is a limit and not a defect: a floor pinned only in a CI workflow or a container image tag reads as an `Unexplained gap` for the Node floor, and an extractor outside the discovered packages whose failure the run does not record cannot be seen by detector liveness. The floor a package inherits from the root is inherited only across directories that hold no other floor site, because a pin kept nearer than the root's `engines` would otherwise turn a true claim into a false drift. The rule's cost runs the other way: it prefers `Unknown` where a person would call the claim a gap, and adding a source, a known kind or an `ABSENT` result to a probe is an amendment to that section.
- **Two of the four claim kinds are specific to this repository's shape** (a detector registry; a controls table with a path-bearing row). On a repository without those, only the version and format kinds apply. That is honest, and it is a limit on the "consumer-agnostic" claim: the packet is agnostic, the checks are not general.
- **Reproducibility is relative to the run.** `align` reads no clock, but a run id comes from the extraction and differs between extractions outside `SEAMLINE_DETERMINISTIC=1`, so the packet's bytes are a function of the inputs including the run record (design 8.3).
- **The word "gap" now has two meanings in the project.** The design and the packet name which one is meant; a reader of ADR-0005 alone will be misled until they see the amendment note.
- **New public surface**: one CLI command, one JSON schema, one export-profile key, one package. Each is versioned from the start and each is a promise (aspirational-state 1.3).
- The control-enforcement check never reports a control as unwired. It confirms a claim when a non-test, non-barrel file outside the claim's paths imports the module (importing a barrel counts as using everything it re-exports) or when the claim names an entry point of a package, and otherwise it is `Unknown` with a reason: no recorded static importer, a package with dependents, a path the run did not read, or incomplete package discovery. The residue (consumers the extraction does not record) is stated in the design, and is why the probe has no absence result.

## Alternatives considered

**Extract claims with natural-language processing or a model.** Rejected. A model in the gate path is prohibited (aspirational 6A.4), the output would not be byte-reproducible (AGENTS.md invariant 4), and its false positives would be claims about the maintainers' own words. The closed sentence templates of section 2 are the deliberate middle: deterministic and auditable, at the cost of missing paraphrase. Models may appear only as the source of proposals, which the classifier never reads, and v1 has none.

**A hand-written expectation file** (a list of the facts the documentation should state). Rejected. It duplicates the documentation, drifts against both, and turns the check into a comparison of two things people maintain.

**Add `Document` and `Claim` node kinds with a `CLAIMS_ABOUT` edge.** Rejected for this step. It changes `NODE_KINDS` and `EDGE_KINDS` in the frozen contract and the ontology source, brings claims under tombstone semantics for no benefit, and invites the claim to be treated as a fact in the store. Recorded in the design as the shape of a future change if a consumer needs claims queryable.

**Emit cross-package `IMPORTS` edges so the wiring probe can see every consumer.** Not taken here. It changes extraction output and the dogfood baseline and needs its own design pass (design section 10). Until then the probe says `Unknown(cross-package-unobservable)` instead of guessing. It would not make absence reportable by itself: dynamic and script consumers would stay unrecorded.

**Report an unwired control module as an Unexplained gap when the graph shows no importer.** Rejected. The graph records static imports only (`packages/extract-code-ts/src/relations.ts:174-185`, main), so a module loaded by a dynamic `import()`, a `require()` or a `new URL(..., import.meta.url)`, or run from a `package.json` script (this repository runs `packages/eval/src/bin.ts` that way), has no inbound edge and would be reported as unwired while it is in use. Closing those blind spots one at a time does not terminate, because each new shape (a workflow, a tool configuration, the next loader) is another consumer the graph cannot see, and a wrong absence is what AGENTS.md invariant 3 exists to prevent. The extraction can witness presence and never absence, so a control is confirmed or Unknown.

**Gate `seamline check` on drift (`--fail-on-drift`).** Rejected, permanently for this report. Prose is edited far more often than schemas; a gate on it is switched off within a week, which is the failure ADR-0005 and ADR-0003 were written to prevent. The owner's requirement is that drift is reported and never a failing exit.

**Fold drift into `seamline check` output.** Rejected. It mixes two kinds of finding with different gating into one report whose JSON shape is a promise (aspirational-state 1.3), and it would give a drift record the look of an X-code.

**Report code that no document mentions.** Rejected. It is the declaration-driven gap ADR-0005 and 6B.2 exist to exclude.

**A one-off script in `scripts/`, like the leak scan.** Rejected. It would repeat the "presence of a keyword" shape, carry no provenance, no ids and no baseline, and could not serve other consumers.

**Take implementation facts from a fresh extraction by whatever engine is running.** Rejected for historical commits. An engine from a later commit extracts capabilities the earlier tree lacked, so it would answer "what does today's engine see in that tree" instead of "what did that commit's extraction produce". For a past commit, facts come from a snapshot made at that commit (the committed dogfood baseline in the pre-fix tree is one). A snapshot in SIF form carries no commit, so the caller asserts the pairing and the packet says so (design 5.1). A store written by today's `seamline extract` is the same: it records `commit: null` (`packages/cli/src/commands/extract.ts:230`, main), so a null commit means an asserted pairing and never a mismatch, and recording the commit is a follow-up (design 13).
