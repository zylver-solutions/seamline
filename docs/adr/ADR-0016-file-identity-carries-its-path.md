# ADR-0016: `File` is the one kind whose id carries its path

- **Status:** Accepted. Amends [ADR-0002](ADR-0002-path-free-natural-key-identity.md) for the `File` kind and for the inputs, listed in Decision item 4, that a move or rename can change. ADR-0002's decision to use path-free natural keys for every other kind stands. [ADR-0017](ADR-0017-validated-write-contract-identity.md) amends the permitted inputs for a newly admitted local Zod write-contract producer; that producer remains unimplemented at the design amendment.
- **Date:** 2026-10-19
- **Design reference:** `docs/design/v3.md` §2.1
- **Forced by:** review of the change that introduced this rule. ADR-0002's rename gate ("`git mv` a file, re-extract, assert every node id and every edge is unchanged") and its statement that `path` is never part of identity were false for `File` as written. The first correction then over-claimed again, and successive reviews reproduced moves that change the ids of other kinds, each one a move that the list of moves written so far had missed (a package change, a migration rename, a `package.json` renamed on its own, a SQL file renamed so that its statements apply in another order). Decision item 4 is therefore a rule over the inputs an id is built from, which stays complete when the next such move is found, and not a list of moves.
- **Contract:** `packages/core/src/identity/canonical.ts` (`fileName`, `symbolCanonicalName`), `packages/core/src/identity/alias.ts`, `packages/cli/src/wiring.ts` (`fileRenameAliases`), `packages/integration/src/rename-id-boundary.test.ts`. `packages/ontology/src/contract.ts` is not changed by this record; two of its comments still omit the exception and are tracked as a follow-up to correct those two comments. The `Migration` id described in item 4 (input 3) is minted by `packages/extract-data/src/migration-ids.ts` and `migrationName` in `packages/core/src/identity/canonical.ts`; the collision it resolves was a reported id collision between two files given one name.

## Context

`File` has always been the one kind whose canonical name is its repo-relative POSIX path (`fileName` in `canonical.ts`; `fileId` in `packages/extract-code-ts/src/canonical.ts`). ADR-0002 rejected "path in the id, plus `SAME_AS` edges to stitch renames" because every consumer would have to close the alias before answering anything, and any consumer that forgot would be silently wrong. The shipped `File` design is path in the id plus an alias: `extract-change` reads git's rename detection into a ledger, and from the same ledger emits a `RENAMED_FROM` edge (new `File` to old) and, in `fileRenameAliases`, an `Alias` node `{repo}:Alias:File::<old path>` with an `ALIAS_OF` edge from that node to the resolved current `File` id. No record of that choice existed. ADR-0002 decision 3 lists `RENAMED_FROM` for `File` and ADR-0013 notes that a `git mv` changes a `File` id because the path changed, but neither says that the exception is deliberate or what a consumer may rely on.

Other kinds also change id under some moves, and the documentation said they did not: a symbol id carries its package name, a contract id can carry its file name, a migration id is its file or directory name, and the names a table or column ends with can depend on the order in which SQL files are applied. Earlier drafts of the corrected text each listed some of the moves that do this and called the list complete, and each list was then found to be short. Decision item 4 is therefore a rule over the inputs the ids are built from, with the way it was derived and a command that re-checks it, and every other site points at it.

## Decision

**A `File` id is `{repo}:File:<repo-relative POSIX path>`. Every other kind stays path-free, with one derivative exception: the `Alias` that names a retired `File` id is `{repo}:Alias:File::<retired path>`**, because an alias inherits the rules of the kind it retires (`assertCanonicalName` in `canonical.ts`). An alias is created by a rename and never changed by one. This amends ADR-0002 only as follows.

1. **Why `File` is the exception.** A file has no identity apart from its location. A content hash changes on every edit, and a minted id is not stable across a rebuild (both rejected in ADR-0002). The path is the only name of a file that the tree alone reproduces, which is what rebuild-from-scratch and byte-reproducible extraction need.
2. **What carries a rename.** For a rename that git reports (committed, at or above the similarity threshold, 0.6 by default; within the history window, 500 commits by default; `extract-change` enabled) the ledger yields `RENAMED_FROM` and the `Alias` plus `ALIAS_OF` pair. A staged but uncommitted `git mv`, a rename below the threshold or outside the window, and a run without `extract-change` yield neither: the old `File` is tombstoned and the new one is a new node.
3. **The consumer rule.** What follows from keeping the id path-bearing, and what a consumer may rely on:
   - **No finding endpoint is a `File` id.** `left` and `right` of every detector are ids of other kinds. X9 uses a `File` id only as a grouping key, and X10 only to look up verification for a symbol's file. A finding id is a hash of `left` and `right`, so a file rename cannot change it by way of a `File` id. A finding id does change when a move changes the id of a node the finding names (a `Migration` for X8, for example; `DETECTOR_ROLES` lists the kinds each detector can name), so a finding is stable across a move that changes no id of the nodes it names, and not otherwise. This is pinned over the firing fixture of every code (`packages/contradictions/src/meta.test.ts`, "no finding endpoint is a File id") and by the role table `DETECTOR_ROLES` in `packages/eval/src/roles.ts`, which has no `File` role and is compared with the detector sources by `packages/eval/src/data.test.ts`. It is not a proof over all inputs.
   - **Facts keyed by a `File` id are re-derived on each run, not rewritten.** A `CONTAINS` edge follows the file's current path. A `TOUCHES` edge keeps the path the commit touched. `rewriteEdges` in `alias.ts` is a library function with no production caller; `identity.property.test.ts` uses it as a proxy for re-extraction.
   - **A consumer that wants history across a rename follows `RENAMED_FROM` or `ALIAS_OF` itself.** The bounded impact walk in `packages/mcp` does not (`packages/mcp/README.md`, "Not walked").
   - **A detector or consumer that needs a `File` as an endpoint, or needs a `File`-keyed fact to survive a rename, amends this record first.**
4. **When a move, rename or removal changes a non-`File` id.** This is a rule over the inputs an id is built from, not a list of moves. It is complete by construction: every id is assembled in one place, `nodeId` (`packages/ontology/src/contract.ts:28-31`), and every canonical name is assembled from the inputs in the table below and from nothing else. Every other place that describes the guarantee says only that a `git mv` changes no id but the `File`'s unless it changes an input the id is built from, and points here.

   _The rule._ A `git mv`, a rename or a removal changes a non-`File` id exactly when it changes one of the inputs that id is built from. It then changes that id and the key of every edge that has it as an endpoint. A move that changes none of the inputs of a node changes none of its ids. This is a rule about ids. Whether other edges are stable is a separate question, answered under _Edges_ below. None of these changes is aliased; only `File` renames are.

   _The inputs._ Most inputs are the content of the file that declares the node, configuration, or a commit hash, and a move changes none of those. The four that a move can change are read from a location, are marked **location** below and are described after the table.

   _The four inputs read from a location._ Each bullet says when the input changes, what that changes, and which rows of `packages/integration/src/rename-id-boundary.test.ts` pin it. The moves named are illustrations of the rule and not a complete list of the moves it covers.
   1. **The package that governs a file.** `ModuleResolver.forFile` (`packages/extract-code-ts/src/modules.ts`) walks up from the file to the nearest `package.json` whose `name` is a non-empty string and uses `<root>` when there is none. The input changes when a file moves to a directory that another package governs, and also when a `package.json` is moved, renamed or removed (or loses its `name`) with no source file moving: every file below it that no nearer manifest governs changes package. Every `Symbol`, `CodeField` and `Parameter` id those files declare changes, including the `Symbol` synthesized for a route registered at the top level of a file, and so do the keys of the edges that end at them (`HANDLES_ROUTE` from that `Symbol`, for one). A `RouteHandler` id is `METHOD /path` with no package part and survives. A `Module` node exists while its package has an extracted file, so it disappears with the last one and appears with the first. Renaming or moving a whole package directory together with its manifest changes nothing, because the name is read from the manifest's content. Illustrations, pinned by "moving a file to another package ...", "a cross-package move leaves a RouteHandler id alone ...", "renaming a package.json ...", "moving a package.json down a directory ..." and "removing the root package.json ...".
   2. **The file stem of a contract that declares no title.** A contract name is `info.title` (OpenAPI), `$id` and then `title` (JSON Schema), or a Zod schema's variable name, and otherwise the file stem with its last extension removed (`plain.schema.json` gives `plain.schema`). Renaming a file that declares no title changes the `Contract` id, the id of every `SchemaProperty` under it, and the `CONTAINS` edge keys that name them. An `Operation` id is `{METHOD} {path}` and does not change, nor does the `IMPLEMENTED_BY` edge to its `RouteHandler`. A Zod contract is named after its schema variable, not its file, and does not change. A user can opt out by giving the document an `info.title` or a JSON Schema `$id`; nothing equivalent exists for a migration. Illustrations, pinned by "renaming an untitled contract file ..." and "renaming an untitled JSON Schema file ...".
   3. **The file or directory name of a migration.** A `Migration` id is built from its version: the file stem (`db/migrations/0001_init.sql` gives `0001_init`) or, for a file named `migration.sql` in a subdirectory of a migrations directory (the Prisma layout), the name of that subdirectory. Renaming the file or the directory changes the `Migration` id and the `MIGRATED_BY` edge keys that end at it, and no table or column id unless it also changes the order in which the sources apply (input 4). A `.sql` file under a directory named `migrations`, `migration`, `migrate`, `_migrations` or `drizzle` (case-insensitive) is a migration and one elsewhere is plain schema SQL, so moving a file across that boundary adds or removes its `Migration` node, and can change the order its statements apply in (input 4). `Migration` is the `left` endpoint of X8, so an X8 finding id changes with it. **A migration id is a natural key taken from the file name by design, not a defect.** The tools that write migrations order and name them by file or directory name, so the name is the key a user already has, and the alternative, a content hash, is rejected above.

   When two or more migration files share a version, the version alone would give them one id, so the names are assigned over the whole set of migration files and never from the order the files were discovered or applied in (`assignMigrationNames`, `packages/extract-data/src/migration-ids.ts`). Four tiers apply, each only to the files the tier before could not tell apart: (1) a version held by exactly one file keeps the bare version; (2) every member of a shared version, the first included, is qualified by the parts of its migrations directory, joined with `~` (`0001_init~a~migrations` and `0001_init~b~migrations` for `a/migrations/0001_init.sql` and `b/migrations/0001_init.sql`); (3) members that still share a name (the same directory holding `0001_init.sql` and `0001_init/migration.sql`) are qualified by the parts of the file path instead; (4) members that are still indistinguishable, because their paths differ only in characters outside the id alphabet (`a b/migrations` and `a_b/migrations`), take an index, `~1`, `~2`, in sorted path order. Every part is sanitised onto the id alphabet `[A-Za-z0-9._@+-]` (any other character becomes `_`), `~` is outside that alphabet so a qualified name can never equal a bare one, and no name contains `/`, so every `Migration` id passes `makeNodeId` and a `Migration` can be given an alias. A version that is itself outside the alphabet is sanitised the same way and reported as a diagnostic (`migration version "002 (copy)" is not a valid canonical name, identified as 002__copy_`); **this changes the id of a single migration with such a version against earlier releases** (`Migration:002 (copy)` becomes `Migration:002__copy_`), with no collision involved, and the `MIGRATED_BY` edge keys that end at it. A final check throws if two files were given one name, so the data loss of that reported id collision (the store upserts nodes on id, so two nodes with one id became one row) cannot recur silently.

   Which moves change a `Migration` id under this rule: renaming the file, or the migrations directory, of a migration (for the Prisma layout the version is the directory name, or the file stem when the file is not named `migration.sql`); and, for a version that more than one file holds, renaming or moving any group directory of a member (the member's own id changes), or renaming a member so that the version it holds is no longer shared (the member that was not touched then stops being qualified and takes the bare version, so its id changes too; the reverse happens when a file is added or renamed into a version another file holds). Because tier 2 qualifies by the directory and not by position in an order, moving one member to a directory that sorts differently changes that member's id and no other, and the ids cannot swap between files in tiers 1 to 3. The tier-4 index is a position in sorted path order, so it can swap: with `a b/migrations/0001_init.sql` and `a_b/migrations/0001_init.sql` the first holds `~1`, and renaming `a b` to `a~b` makes `a_b` sort first, so the two ids stay and move to the other file. Illustrations, pinned by "renaming a migration file that keeps its place in the order ...", "a Prisma migration takes its id from the directory name ...", "a SQL file that leaves a migrations directory ...", "migrations that share a version are each qualified by their directory ...", "moving a same-version migration to another directory ...", "renaming one of two same-version migrations ..." and "three same-version migrations are all qualified ..."; the tiers, the sanitising and the diagnostics are pinned in `packages/extract-data/src/migration-ids.test.ts`.

   4. **The order in which SQL sources are applied.** Standalone `.sql` files are read in sorted path order, and migrations after them, ordered by directory path, then by the leading integer of the version, then by the version (`discover`, `packages/extract-data/src/discover.ts`). Statements are applied in that order, so the names a `Schema`, `Table` or `Column` ends with are a function of it wherever two sources do not commute, for example a file that renames or drops a column and the file that creates the table. Renaming a file or a directory so that it sorts differently against such a source changes those ids, even when no `Migration` id changes (a directory rename above two migrations directories changes none). Sources that commute are not sensitive to it, and neither are the ids that Prisma and Drizzle files produce: a Prisma model block names its own table and columns, and a Drizzle table names itself. A Drizzle reference resolves through the importing module's import binding, then a same-module binding, then that variable name only when every binding of the name is the same table, so read order does not choose the target (the Drizzle foreign-key binding fix). This is also why a rename that keeps the order, or moves a commuting file across the migrations boundary or to another package, leaves every table and column id alone. Illustrations, pinned by "renaming a migration so it sorts before the one that creates its table ...", "renaming a plain SQL file changes a column id ...", "renaming a directory above two migrations directories ..." and, for the sources that are not sensitive, "moving or renaming Prisma schema files ..." and "renaming either Drizzle schema file ...".

   _Edges._ An edge key is the kind plus the source and destination ids, so an edge key changes whenever an endpoint id changes; that is the sentence in the rule above. Separately, some edges between non-`File` nodes depend on a file name or on the order files are read, with no id changing. The following have been found:

- `EXPORTS` from a `Module` to a `Symbol` is emitted only for the package entry file, which `ModuleResolver` finds by name among a fixed candidate list (`ENTRY_CANDIDATES` in `packages/extract-code-ts/src/modules.ts`, used at `relations.ts:244`). Renaming or moving the entry file (`src/index.ts` to `src/main.ts`, or `src` to `lib`) drops those edges and changes no id.
- Automatic inferred joins exclude members or resolved owners in test, fixture, mock, component and vendor paths (`packages/infer-join/src/facets.ts`). Crossing that eligibility boundary changes join membership without changing a non-`File` id. `packages/integration/src/join-eligibility.test.ts` pins one ordinary eligible move with unchanged edge keys, a fixture move that removes the join, and a return that restores it, through real extraction. This does not guarantee membership for every eligible move: path corroboration can change scores across a threshold or ambiguity boundary. This is a candidate policy, not a path-derived semantic identity or evidence that remaining declarations have a persisted role.

This list is not claimed to be complete. It was found by reading what each edge emitter takes as input and by the rename sweep described below, and neither method proves that no other edge reads a path. An edge that depends on a path is not an identity defect, because no id is wrong, but it must be disclosed; a newly found one is added here with a test row. Edges that are `INFERRED` carry a confidence that can move with a path (the persistence-shaped path and same-file or same-directory corroboration in `infer-join/structure.ts`); corroboration can affect candidate scores in addition to the explicit eligibility boundary above, and `INFERRED` edges never justify a finding. The extracted-fact case is pinned by "renaming or moving the package entry file ...". A Drizzle `FK_TO` used to follow read order when two modules exported one name (the same fix); it now follows the importing module, and "two Drizzle modules exporting one name for different tables ..." asserts that renaming the other module moves no edge.

A `File` that git reports as renamed is the one move that is recorded: the `Alias` and `ALIAS_OF` pair of item 2, pinned by `packages/cli/src/wiring.test.ts` ("a file renamed across commits leaves an ALIAS_OF from each retired File id to the current one").

_Not id changes._ A move that takes a file out of an extractor's reach does not rename anything: a directory the extractor skips (`vendor` for the SQL extractor) or a missing `tsconfig.json` (the code extractor reports UNAVAILABLE, never PASS) means the nodes are not extracted, and a later PASS run tombstones them (invariant 2). Everything else in the table is the content of the declaring file, configuration or a commit hash, and a move changes none of those.

_How the table was derived, and how to re-check it._ From the code first. The single place an id string is assembled is `nodeId`: `git grep -n -F '${repo}:${kind}:' -- 'packages/*/src/*.ts' ':!*.test.ts'` prints one line, `contract.ts:31`. The places that call it are listed by `git grep -n -P '^(?!\s*(\*|//|/\*)).*\b(nodeId|makeNodeId)\(' -- 'packages/*/src/*.ts' ':!*.test.ts'`, which prints 35 lines at this change. Twelve of them are the four extractors (`extract-change` 4, `extract-code-ts` 4, `extract-contracts` 1, `extract-data` 3), the only code that mints a non-`File` id from repository content, and the table has a row for each kind they mint. The other 23 do not: the definitions and the validating wrapper (3); the alias and rename helpers in `core` and `cli`, which build `File`, `Symbol`, `Column` and `Alias` ids from the names a rename record carries (9); lookups of ids that are already in the graph, by the X8 detector from a migration's own target and by the MCP affected-tests walk from a node's `path` (3); and test support plus the detector-source table in `packages/eval/src/roles.ts` (8). A match that falls in none of these groups, or a new `nodeId` call in an extractor, is a change to this table. Then a rename sweep as a cross-check and not as the authority: one fixture repository holding every file kind the extractors read (TypeScript, TSX, JavaScript, a Zod contract file, SQL, SQL migrations in both naming styles, Prisma, Drizzle, OpenAPI in YAML and JSON with and without `info.title`, JSON Schema with and without `$id` and `title`, `tsconfig.json`, `package.json`), each file renamed to a new stem in its own directory, each directory renamed, files moved into and out of a migrations directory and to another package, and after each of 52 scenarios every non-`File` node id and every edge key between non-`File` nodes compared with the baseline. The sweep found the package, contract and migration inputs; later reviews found the manifest, the collision qualifier and the apply order, which that fixture and those scenarios did not exercise (a manifest moved by itself, a member of a same-version pair moved or renamed, statements that do not commute). That is why the authority is the inputs and not the moves. The sweep script is not kept in the repository; `packages/integration/src/rename-id-boundary.test.ts` is the part that stays.

An id built from an input that the table does not list is a defect, and so is a path in the canonical name of any kind but `File`. A change that adds an input, or a new place that mints an id, adds a row to the table and an illustration to the integration test in the same pull request.

## Consequences

### Positive

- The invariant text now matches the code and stays strict: a non-`File` id never carries a path, and the inputs through which a name still comes from a file name, a directory name, the governing package or the order of paths are stated once, as a rule that the next newly found move falls under, and pinned by a test instead of being hidden or repeated in prose that goes stale.
- The exception is narrower than the alternative ADR-0002 rejected. Findings, the main thing a user keeps across runs, never name a `File`, so the "all historical findings invalidated" failure does not recur.
- `File` ids are readable and equal the path, which the redactor (ADR-0013) and path-based joins rely on.
- The consumer rule is a test, not only a sentence.

### Negative

- **A moved file has a new id, and continuity depends on the alias.** A rename that git does not report (below the threshold, outside the window, uncommitted, a shallow clone, `extract-change` disabled) leaves no link. The graph stays correct (old tombstoned, new present); the history across that move is lost, the same trade ADR-0002 accepted.
- **The cost ADR-0002 rejected remains for `File`-keyed facts.** A consumer that reads `CONTAINS` or `TOUCHES` across a rename must close the alias itself, and nothing in production does. This is accepted because no detector reads those facts across a rename today, and the rule above says who must amend this record before one does.
- **A change to one of the four inputs read from a location changes ids with no link.** The old ids are orphaned, and a finding that names one of them gets a new id. Aliasing the package input needs symbol-level rename detection (deferred, `docs/design/v3.md` §9); the file-name inputs need a different name source or an alias layer for non-`File` kinds; the apply-order input is inherent to applying statements in an order and has no alias to give. Each needs a named consumer and its own design pass.
- **A `Migration` id depends on its version and, for a shared version, on its directory.** Every member of a shared version carries its group parts, so renaming a group directory or a file of a shared version changes ids (item 4, input 3), and a file that stops sharing its version takes the bare one. A version outside the id alphabet is sanitised, which changes the id of a single such migration against earlier releases. The index of tier 4 depends on sorted path order and is the only part of the scheme that can swap ids between files. The data loss of that id collision (the store upserts nodes on id at `packages/core/src/store/sqlite-store.ts:334`, so two nodes with one id became one row and one file's path and statement count were lost) is closed by construction and by a final uniqueness check.
- **The consumer rule is pinned over fixtures and detector source text.** A detector added later is covered by the meta-test only through its firing fixture.
- **`TestCase` is a second path-keyed annotation.** The ontology annotates it `(repo, test_file, test_name)`; no extractor emits it, and `docs/design/real-world-inputs.md` records that it conflicts with invariant 1 and is to be replaced by a path-free key.
- `packages/ontology/src/contract.ts` still describes ids as path-free without the exception until that follow-up is taken by whoever coordinates a contract change.

## Alternatives considered

**Make `File` ids path-free (a content hash, or a minted id).** Rejected, for the reasons in ADR-0002: a hash changes on every edit and a minted id does not survive a rebuild. A file's only reproducible name is its location.

**State invariant 1 without an exception.** Rejected. The code keys `File` on its path, so the rule is false as written, and a rule the code violates is a rule nobody enforces.

**Rewrite stored edges onto the new `File` id when a rename is detected.** Rejected for ADR-0002's reason: it is a stateful migration of persisted data, so an incremental run and a rebuild would produce different graphs. The pipeline re-derives instead.

**Require every consumer to close `ALIAS_OF` (`SAME_AS` in ADR-0002's terms).** Rejected as a universal rule. The consumer rule keeps `File` off finding endpoints, so the consumers that would have to remember are the few that read `File`-keyed facts.

**Keep a list of the moves that change an id.** Tried in the first three revisions of this record and rejected: each list was falsified by a further move found by review, and a list of moves is complete only until the next one. The rule over inputs is complete as long as the table matches the construction sites, which one command re-checks.

**Alias the item 4 inputs now.** Not taken. A cross-package move needs symbol-level rename detection, which v3 §9 defers until it has a named consumer. The contract and migration inputs need a different name source, which changes extraction output and the dogfood baseline, or an alias layer for kinds other than `File`. Until then they are documented as outside the guarantee.

**Treat the migration id as a defect and make it independent of the file name.** Not taken. A migration has no name in the tools that write it other than its file or directory name, and the only other candidate is a content hash, which changes on every edit. This can be revisited with a named consumer, and the integration test would change with it. The collision qualifier is a set-based function of the migration files (item 4, input 3) and not a position in a discovery order, which is what the id collision reconsidered.

## Supplement: the validated-write producer

[ADR0017](ADR-0017-validated-write-contract-identity.md) adds one producer after the original table above. Its Contract key is the reversible encoding of declared owning package, lexical declaration chain ending at the local schema, resolved persistence-wrapper package and declaration chain, and declared Prisma model. `packages/extract-contracts/src/write-identity.ts` mints that key from the tuple proved in `write-binding.ts`. SchemaProperty retains its Contract and JSON-pointer identity. Paths, route directories, positions and hashes supply no segment. The original table is unchanged.

An eligible move preserving those inputs preserves non-File ids; changing one of those tuple inputs changes the Contract and its properties. `write-extract.test.ts` verifies moves and collisions, and `write-identity.test.ts` verifies encoding round trips. [The development proof](../evaluation/x7-parent-fix.md) records actual emitted identities; it is not independent precision qualification.
