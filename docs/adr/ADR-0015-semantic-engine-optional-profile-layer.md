## Context

ADR-0012 added a generic, profile-driven engine at `packages/core/src/semantic/` and its public entry `@seamline/core/semantic` (`packages/core/package.json:17-20`). `AGENTS.md:21` makes that directory a reviewed exception to the rule at `AGENTS.md:23`, "Do not re-expand toward v2". The exception is scoped to the directory. Everything else that v3 section 9 defers (`docs/design/v3.md:262`) still needs a named consumer and its own design pass, and `docs/design/aspirational-state.md:237-247` makes that an admission test with three legs: a cited instance, a named owner, and a design-spec pass. Section 6A of the same document closes network calls and live introspection outright (`docs/design/aspirational-state.md:257-258`).

The risk is specific. The engine ships vocabulary for worlds, inventory, deployments, incidents and test evidence (`docs/semantic-engine.md:48-58`). Vocabulary is cheap to add and easy to mistake for capability. The test in `docs/design/semantic-foundation.md:11` is "Vocabulary presence alone is not verification." A generic engine is also the obvious place for runtime observation, new capability families and multi-source fusion to arrive through a side door, which is the v2 failure the council blocked. Meanwhile the product's one promise, contradictions between facts the user already wrote (ADR-0005), is only credible if nothing optional can change what a default run extracts or reports.

"Profile" in this record means the semantic engine's `Profile` (`packages/core/src/semantic/types.ts`), the unit a host composes into a `CompiledRegistry`. It is not the core profile ontology (ADR-0001) and not an export profile (ADR-0006).

## Decision

1. **The engine is an optional layer over shared primitives.** The layer is `packages/core/src/semantic/`. It may import only `@seamline/ontology`, `canonicalJson` from `packages/core/src/merge/serialize.ts`, the redactor from `packages/core/src/security/redactor.ts`, `node:sqlite` and `node:crypto` for `createHash` only (today: `engine.ts:2-4`, `legacy.ts:2-13`, `registry.ts:1-2`). Dependence runs one way, from the layer to those primitives.
2. **The core contradiction pipeline does not depend on the layer.** The pipeline is extract, merge, infer-join, contradictions X1 to X10, and check, export and MCP over the result: the packages `ontology`, `core` (outside the layer), `extract-change`, `extract-code-ts`, `extract-contracts`, `extract-data`, `infer-join`, `contradictions`, `cli` and `mcp`. No pipeline module imports the layer, statically or dynamically, including type-only imports. No CLI command, MCP tool or config key exposes it.
3. **It is not loaded or run unless a host opts in.** Opting in means a host imports `@seamline/core/semantic`, composes a `CompiledRegistry` from the profiles it chooses, and constructs a `SemanticEngine` over a SQLite path it names (`engine.ts:253,260`). The engine accepts any path, so this record does not claim the engine and the extraction store can never share a file. It claims that no default code path opens the engine: a default `seamline extract` and `seamline check` load no module of the layer, and afterwards the extraction store holds no `semantic_` table (the engine's tables carry that prefix, `engine.ts:263-276`) and no file in the output directory has `semantic` anywhere in its path. There is no CLI, MCP or config opt-in today. Adding one needs its own ADR and design pass.
4. **Findings still come only from facts.** The legacy bridge copies extracted facts into the engine in one direction (`prepareLegacyImport`, `legacy.ts:44`) and keeps the fact/inferred distinction (`legacyIsFact`, `legacy.ts:329`). Nothing flows back into a detector. Detectors read the extraction store through `isFact` (`packages/ontology/src/contract.ts:162`). Authored semantic state is not evidence.
5. **No runtime or infrastructure observation.** The layer reads no network, process, environment, clock or random input of its own, and its only I/O is the SQLite file the host names. Handlers are deterministic (`docs/semantic-engine.md:66`). Records for deployments, environments or observations are authored state, not new extractors (`docs/semantic-engine.md:58`). Section 6A items 1 and 2 are not reopened.
6. **No new capability families.** A capability family is a new first-party built-in pack, extractor, ontology domain, or CLI or MCP surface. The five shipped packs (`world`, `inventory`, `authoring`, `software`, `code`) are the set. A host that defines its own profile in its own code is using the supported extension mechanism and is not adding a family to this repository. Adding a first-party family requires the section 5.3 admission test and a new ADR.
7. **No fusion work.** Fusion here means reconciling or estimating one state from several observation sources, or combining semantic state with extraction facts to produce findings or confidence. The engine stores authored state and reports what it does not do: no coordinate transform solver (`docs/semantic-engine.md:48`), no automatic branch merge (`docs/semantic-engine.md:80`).
8. **No re-expansion toward v2.** The exception in `AGENTS.md:21` governs the directory and does not widen section 9 or section 6B. A profile that declares vocabulary does not satisfy "named consumer" for anything outside the layer.

## Enforcement

Claims 1 to 3, and the direct-reference part of claim 5, are about structure and each has a test that fails when it stops being true. Both live in `packages/integration/src/`. Claims 4 and 6 to 8 are not mechanically enforced; see below the table.

| ----- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1     | `semantic-boundary.test.ts`         | Parsing every layer source file with the TypeScript parser, whatever its extension (`.ts .mts .cts .tsx .jsx .mjs .cjs .js`; only `*.test.<ext>` files are skipped), the import set is exactly the allowlist (and every allowlist entry is used). `node:crypto` is imported only as `{ createHash }`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| 2     | `semantic-boundary.test.ts`         | Every source file (`.ts .mts .cts .tsx .jsx .mjs .cjs .js`) under `packages/*/` at any depth except `dist` and `node_modules`, and under `examples` and `scripts`, is read for imports, re-exports, `import()` and `require()` with a literal specifier. A specifier fails unless the importing file is in a named list when it names the layer by relative path (including across packages, and through a package's `node_modules`) or by an `@seamline/core/` subpath with a `semantic` segment. A re-export from the `@seamline/core` barrel is an import of the layer by `packages/core/src/index.ts` and fails the same way. `./semantic` is the only `exports` entry of `packages/core/package.json` whose target is under the layer. Every package under `packages/` must be classified, so a new one cannot escape the scan.                                                                                                                |
| 2, 3  | `semantic-boundary-runtime.test.ts` | The real CLI binary runs `extract` and `check` on a fixture under a module-resolution hook that records every import edge. The edges entering the layer from outside must equal a named list, a control proves the hook sees the layer when `@seamline/core/semantic` is imported, the runs must do real work (one seeded X1 finding, exit status 1), and the store holds no `semantic_` table and no file in the output directory has `semantic` (any case) in its path.                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 5     | `semantic-boundary.test.ts`         | A tripwire for direct references to the names it lists, not a sandbox and not an exhaustive list. In every layer source file: no reference to `fetch`, `process`, `WebSocket`, `XMLHttpRequest`, `EventSource`, `performance`, `Date`, `globalThis` (so `globalThis.x` and `globalThis['x']` fail too), `crypto` (the Web Crypto global), `setTimeout`, `setInterval`, `setImmediate`, `queueMicrotask` or `Intl`, and `Math` appears only as `Math.<member>` for a member other than `random`. Member names, property keys, declaration names (a method, property, accessor, enum member, parameter or variable called `process`) and type positions (type references and `typeof` type queries) are not references. A shorthand property such as `{ fetch }` and a use of a local that shadows a listed name are references, because the scan has no scope analysis. A synthetic-source test shows each form is flagged and ordinary code is not. |

The exception lists are ratchets. An entry that no longer matches an import fails the test, so a list can shrink only by deleting the entry in the change that removes the import, and can grow only with a named reason a reviewer sees. The list of known deviations is empty. Opt-in consumers must live outside the pipeline packages.

Not mechanically enforced:

- **Claim 8** (no re-expansion toward v2). The tests pin the directory scope of the exception in one direction only: the pipeline cannot import the layer, and the layer imports five named primitives. They do not stop re-expansion elsewhere. A new extractor, built-in pack, ontology domain or CLI command that does not import the layer passes every test here, and the only friction is classifying a new package, which is a list edit. Section 9 and the admission test stay with review.
- **Claims 6 and 7.** The tests cannot stop someone adding a new pack, command or ingest path inside the layer, and they cannot judge whether a change is fusion.
- **Claim 4.** It rests on claim 2 (a pipeline that cannot import the layer cannot read authored state) and on invariant 5 in `AGENTS.md`. These tests do not exercise `isFact`.
- **Claim 5 beyond direct references.** The name list is a tripwire, not an exhaustive list of ambient APIs: a global that is not named is not seen, and a future runtime API is not seen until it is added. An alias or indirect call of a listed global, input that arrives through host-supplied profile code, and the SQLite path the host names are not seen either.

Those stay with the admission test and review.

## State at acceptance

The boundary holds at acceptance. Before this change, `packages/core/src/index.ts` re-exported eleven names from the layer through the `@seamline/core` root, so every package that imported the root loaded all six layer modules on a default run. The run-time test's hook measured this: the one entering edge was `packages/core/dist/index.js` to `packages/core/dist/semantic/index.js`. No pipeline source imported the layer directly. This change deletes that re-export block and moves the only first-party user of the root names, `packages/integration/src/semantic-bridge.test.ts`, to `@seamline/core/semantic`. The packages were unreleased (0.0.1) at acceptance, so no published root surface changed. The tracked-deviation lists in both tests are empty; re-adding a root re-export fails both (the static scan sees it as an import of the layer by `packages/core/src/index.ts`).

## Consequences

**Good.** The pipeline's guarantees (byte-reproducible extraction, UNAVAILABLE never PASS, findings only from facts) cannot be altered by anything in the optional layer, and a reviewer has a mechanical tripwire instead of a paragraph to remember. An external contributor can see exactly where the line is. The allowlist in claim 1 keeps the layer cheap to move into its own package later, since its whole dependency surface is five named imports.

**Bad.**

- The semantic names are available only from `@seamline/core/semantic`, not from the `@seamline/core` root. A host that wants the layer writes that import explicitly, which is the point.
- The layer cannot reuse pipeline machinery beyond the five primitives. It carries its own SQLite store and its own redaction call site rather than sharing `SqliteStore`.
- The static scan sees only specifiers it can read, in the directories it walks. A dynamic `import()` or `require()` with a computed specifier is invisible to it, and so are files outside `packages/*/`, `examples` and `scripts`.
- The run-time test sees the real module graph, but only for `extract` and `check` on one fixture. That graph is wide: `packages/cli/src/run.ts:11-18` imports every command statically (`export`, `why`, `diff`, `blast-radius` and `mcp` included) and `packages/cli/src/commands/mcp.ts:21` imports `@seamline/mcp`, so a static import of the layer in any of them is loaded, and seen, on any run. It cannot see a dynamic `import()` on a path the run does not execute (a literal one is caught by the static scan; a computed one by neither), nor the standalone `packages/mcp/dist/bin.js` entry (`seamline-mcp`), which no run loads and which only the static scan covers.
- The run-time test uses Node's `module.register` loader hooks, which are still a release-candidate API. A future Node release may require moving it to a successor.
- Growth inside the layer passes every test here. Only the admission test and review hold it.
- A new package must be classified in the test before CI is green. That friction is intended.

## Alternatives considered

- **Move the layer to its own package now.** Rejected for now. It changes the published surface and the release workflow without changing the boundary, and ADR-0012 shipped the subpath. The import allowlist keeps this option open.
- **Make the layer a supported part of check, export and MCP.** Rejected. Authored state cannot be verified as fact (`docs/semantic-engine.md:56,111`), so letting it influence a gate would break the facts-only invariant (`AGENTS.md`, invariant 5) and `docs/design/aspirational-state.md:260`. It would also be the side door this record exists to close.
- **Rely on the `AGENTS.md` paragraph and review alone.** Rejected. v2 failed that way, and a declared boundary with no check erodes silently.
- **An ESLint `no-restricted-imports` rule instead of tests.** Rejected as the only mechanism. It sees only the patterns it is given, cannot see a relative path that crosses packages or a symbol arriving through a barrel, and cannot observe what a real process loads. It could be added alongside.
- **Keep the root re-export but load it lazily.** Rejected. It is still a pipeline dependency on the layer and still makes the root surface say the layer is part of the core.
- **Remove the engine from this repository.** Rejected. ADR-0012 accepted it for named consumers, and nothing here reverses that. This record bounds it.
