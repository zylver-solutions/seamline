# ADR-0011: The Redactor is wired in as the sole writer to the store

- **Status:** Accepted. Amended by [ADR-0013](ADR-0013-redactor-never-rewrites-identity.md): the redactor no longer rewrites a node id, so the id-remap behaviour and the cross-call ordering residual described below no longer exist. The sole-writer wiring decision is unchanged.
- **Date:** 2026-08-30
- **Design reference:** `docs/design/v3.md` §2.5; ADR-0006 §2 (design intent)
- **Forced by:** A `PUBLIC-RELEASE-CHECKLIST` audit finding. The audit found that ADR-0006's "sole writer" control was designed and implemented as an isolated, well-tested unit (`createRedactor`/`redactGraph` in `packages/core/src/security/redactor.ts`) but was never actually called by `seamline extract`. `packages/cli/src/commands/extract.ts` wrote every extractor's raw output straight to `workspace.store.upsertNodes`/`upsertEdges`. `THREATMODEL.md`'s control C3 described a control that did not exist in the shipped code.
- **Contract:** `packages/core/src/security/redacting-store.ts` (new), `packages/cli/src/wiring.ts`'s `sqliteStorePort()`, `packages/cli/src/commands/extract.ts`

## Context

ADR-0006 states the intent precisely: _"Making it the sole writer, rather than one step among several, is what turns 'values are never stored' from an assertion into a property. There is no code path that reaches the store without passing through it."_ That sentence was aspirational, not descriptive, until now.

Three things about the actual (rather than intended) extraction pipeline shaped this ADR, none of which were visible from `redactor.ts`'s own excellent test suite in isolation:

1. **There is no distinct "merge" phase to hook after.** `seamline extract` (`extract.ts`) calls each extractor, then writes that extractor's `nodes`/`edges` straight to `workspace.store.upsertNodes`/`.upsertEdges`, incrementally, extractor by extractor, inside the same loop. `packages/core/src/merge/state.ts` — a correct, well-tested, pure implementation of batch merge/lifecycle reconciliation (`mergeBatches`, `liveNodes`, `liveEdges`) — has no caller outside its own test file. The "merge" that actually happens is whatever row-level upsert reconciliation `SqliteStore` performs per call. "Post-merge" in ADR-0006 has to be read as "at the point each write lands," not "after one batch merge step for the whole run," because the latter does not exist as a runtime stage.
2. **`infer-join` reads mid-run store state by design.** `extractCommand`'s special case for `infer-join` (see the long comment above `scopeAwareView` in `wiring.ts`) builds its `GraphView` from `workspace.store` — the _same_ object every other extractor has already written into during this run — specifically so cross-extractor joins see what earlier extractors in this run produced, before `finalizeRun` persists anything. Any design that defers all writes to one batch at the end of the run (a literal reading of "post-merge" as "after everything") would starve `infer-join` of the mid-run state it depends on. That would be a real, user-visible behaviour change (weaker joins), not an implementation detail — the kind of fork this ADR was told to flag rather than choose. It was considered and rejected below (Alternatives).
3. **Node identity can change under redaction.** `redactGraph(nodes, edges)` remaps a `NodeId` whose canonical name embeds a secret and rewrites every edge endpoint that pointed at the old id, in the same call. This is correct and necessary, but it means redaction is not a per-string filter applied independently to each write — it is stateful across a run (an `idRemap` that must be shared across every `upsertNodes`/`upsertEdges` call in that run for edges to resolve correctly against a node redacted earlier in the same run).

## Decision

**A `GraphStore` decorator, not a pipeline stage.** `packages/core/src/security/redacting-store.ts` exports `wrapWithRedaction(inner: GraphStore, options?: RedactorOptions): GraphStore`. It implements the full `GraphStore` interface: `upsertNodes`/`upsertEdges` run every node/edge through one `Redactor` instance (held for the wrapper's lifetime) and pass the _redacted_ result to `inner`; every other method (`beginRun`, `finalizeRun`, `traverse`, `close`, and all of `GraphView`'s read methods) passes through unchanged.

One `Redactor` per wrapper instance, one wrapper per run, so `idRemap` accumulates correctly across every incremental `upsertNodes`/`upsertEdges` call in that run — including the ones `infer-join`'s edges go through — without needing a batch step.

**Wired at the one production construction site.** `packages/cli/src/wiring.ts`'s `sqliteStorePort()` is the only place `SqliteStore` is constructed in production code (`grep -rl "new SqliteStore" packages/*/src` outside tests returns exactly this file). It now does:

```
const store = new SqliteStore({ path: file });
const runs = runHistoryOf(store);          // needs SqliteStore-specific listRuns()/getRun()
return { store: wrapWithRedaction(store), runs };
```

`Workspace.store` — the only handle `extractCommand` (or any future command) ever holds — is the wrapper. `runHistoryOf` keeps the raw `store` reference because `RunHistory` needs `SqliteStore`-specific methods (`listRuns`, `getRun`) that are not part of `GraphStore` and are read-only, so they carry no redaction obligation.

**This is where "post-merge" cashes out.** Since there is no separate merge stage, "the Redactor runs post-merge" now means: after each write's own upsert-level reconciliation is _decided_ (the caller has final node/edge bodies to persist) and before those bodies reach storage. That is the wrapper boundary, and it is the earliest point at which the full picture ADR-0006 asks for (every string field, of every node and edge, from every extractor and from `infer-join`) is available to redact.

**The store is not the only export path, so the wrapper alone is not sufficient.** Implementing the wrapper first (as the initial pass on this change) and then writing the end-to-end test the checklist demands (a canary secret planted in a source fixture, run through real `seamline extract`, checked against both "the resulting store" and "the SIF snapshot") surfaced a second, independent leak: `extractCommand` builds `Snapshot.nodes`/`.edges` for `seamline diff`'s `.sif` file from the _same local arrays_ (`allNodes`/`allEdges`) it accumulates from each extractor's raw output, before that output reaches `workspace.store` at all. Wrapping the store does nothing for this path, because it never touches the store's write methods. `extractCommand` therefore now holds one `Redactor` instance (`createRedactor()`, not the store's) for the run, calls `redactor.redactGraph(...)` on each extractor's (and `infer-join`'s) nodes/edges _before_ both the `workspace.store.upsertNodes`/`upsertEdges` call and the `allNodes`/`allEdges` accumulation, and both destinations receive the identical, already-redacted values. The store wrapper still runs on top of that (idempotent, per `redactor.ts`'s own documented no-op-on-clean-input property, so this is not a behaviour change for the store) and remains the structural backstop for any write path that is not `extractCommand` -- this two-layer shape, not a single one, is the actual "sole writer" story: **one producer of graph content (`extractCommand`) redacts once, at the earliest point content exists in memory, and the store independently refuses to trust that it was already done.**

**Known, accepted residual: cross-call id-remap ordering.** If an edge from extractor A references a node whose canonical name embeds a secret and is created by extractor B _later in the same run_ (config order, not creation order, controls the loop), the edge upserted by A resolves against the pre-redaction id, because that id has not been redacted yet when A's edges are written. This was true before this ADR too, independent of redaction — the store already tolerates edges that reference not-yet-upserted nodes (`extract-change`'s own doc: "File nodes are emitted as edge endpoints only"). Redaction adds one narrow extra case to that pre-existing tolerance: a stale pre-redaction id in an edge, specifically when the referenced node's _canonical name itself_ — not a prop value — contains a secret. This is covered by a regression test (`redacting-store.test.ts`) that documents and pins the behaviour rather than hiding it, and does not weaken the actual security property this ADR closes: **no secret value, in any prop or field on any node or edge, from any extractor, ever reaches the store.** That property holds regardless of call order, because it does not depend on `idRemap` at all.

## Consequences

### Positive

- ADR-0006's sentence is now true of the shipped code: `Workspace.store` accepts writes from `extractCommand` but there is no way to obtain a `Workspace` in production without going through `sqliteStorePort()`, and `sqliteStorePort()` never returns the raw store.
- Zero change to `extractCommand`, `scopeAwareView`, or `runInferJoin`. The fix is entirely at the construction seam, which is exactly the kind of change ADR-0006's own "structural guarantee, not discipline" framing calls for: nothing about this depends on every future command remembering to redact.
- `infer-join` keeps reading real mid-run store state, so no join-quality regression — see the "genuine product fork" analysis in Context, point 2, which this decision avoids taking.
- Testable at three levels that compose rather than duplicate: the decorator in isolation against a real `SqliteStore` (proves the mechanism), the wiring in `wiring.test.ts` (proves the _production_ construction path specifically, including a deliberate raw-store bypass for contrast), and an `extractCommand` end-to-end test that plants a canary secret in a real source fixture and checks it against both the real on-disk store _and_ the real `.sif` snapshot file (proves the property a user actually depends on, across both export surfaces that exist today).

### Negative

- **The `idRemap` ordering residual above is real**, narrow, and now permanently documented rather than accidentally absent. A future contributor who wants to close it fully needs a two-pass write (buffer a run's nodes, then its edges, resolving remap before any edge write) — deferred, because it is strictly more invasive than this fix for a threat that requires a secret specifically in a _canonical name_, which every other rule in `redactor.ts` (starting with `redactNodeId`'s repo-slug check) already treats as the rare, fail-closed-on-detection case rather than the common one.
- `RunHistory` still reads through the raw `SqliteStore` reference for `listRuns`/`getRun`, not the wrapper. This is intentional (those are read paths returning `RunRecord`, which carries no node/edge string fields to redact), but it means `redacting-store.ts` is not literally the _only_ thing holding a reference to the raw store — it is the only thing that can _write graph content_ through it. Documented here so it is not later "discovered" as a gap.
- One more object in the construction path (`sqliteStorePort`), one more file to keep in sync with `GraphStore`'s shape if the contract grows a new write method — a decorator's usual maintenance cost.

## Alternatives considered

**Defer all writes to a real batch merge step, added at the end of the run, only then redact-and-flush once.** This is the most literal reading of "post-merge" as originally written. Rejected: it requires either (a) making `infer-join` read from an in-memory pre-redaction buffer instead of `workspace.store`, which changes what its join heuristics see mid-run (a genuine behaviour fork, not an implementation choice — the kind of decision this ADR was told to escalate rather than make), or (b) making `infer-join` read from the store as before, in which case the store would need to hold _unredacted_ mid-run state anyway, which defeats the point. Also would have required wiring the currently-dead `packages/core/src/merge/state.ts` module into the runtime pipeline for the first time, a separate and larger change than the scope of this one.

**Redact inside each extractor, before it returns its output.** Rejected: this is "one step among several," the exact shape ADR-0006 already rejected and named the failure mode of (a future extractor, or a bug in an existing one, simply forgets). It would also mean re-running the entropy/pattern scan N times with N separate `idRemap` states that cannot agree with each other about a cross-extractor rename.

**Push redaction into `SqliteStore` itself (make the store secret-aware).** Rejected: conflates a storage concern with a security-detection concern that already has its own well-tested, independently-versioned home (`redactor.ts`). It would also make every other `GraphStore` implementation (a future Postgres adapter, a test fake) responsible for re-implementing the same scan, instead of getting it for free by being wrapped the same way.

**A capability-token / branded-type guard on `SqliteStore.upsertNodes` so a raw call fails at compile time without going through the wrapper.** Considered as a stronger enforcement than "the only production call site happens to wrap it." Rejected for this change: it is real over-engineering for the threat model here (an internal contributor accidentally reintroducing `new SqliteStore(...)` in a second call site, not an adversary with source access), and `wiring.test.ts`'s regression test already fails loudly the moment that happens. Left as a note for a future ADR if a second legitimate write call site is ever added and the "one call site" argument stops holding.
