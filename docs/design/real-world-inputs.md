## 1. Why this pass exists

Seamline's claim is that it finds real contradictions in repositories it did not write. At the start of this design pass, that claim rested on one bundled fictional example and one timed run. The five observations below describe the code before row C of section 2.1; their source line numbers refer to that historical code. Row C changed observations 2, 4 and 5 for raw SQL, and sections 2.1 and 8.1 record the implemented behavior and remaining validation limits:

1. `extract-code-ts` emits `QUERIES` only from raw SQL in string literals and in template literals that have no `${...}` substitution (fact 5; `packages/extract-code-ts/src/relations.ts:263-279`, `packages/extract-code-ts/src/sql.ts`). Most TypeScript services reach their database through an ORM client (`prisma.user.create(...)`, `db.insert(users).values(...)`), so on those repositories the code layer and the data layer are not connected, and every detector that walks `QUERIES` (X5, X6, X10) has nothing to walk.
2. No `QUERIES` edge carries a column list: its props are `operation`, `table`, `schema` and `binding` (`relations.ts:442-479`). X5 therefore cannot fire on any real repository (README, "what does not work", `README.md:179`).
3. No extractor produces `TestCase`, `TESTS`, `CoverageRecord`, or `COVERS`, so X10 cannot fire on any real repository either (`README.md:184`).
4. The one `QUERIES` edge per (symbol, table) is last-writer-wins: edge identity is `UNIQUE(scope, src, dst, kind)` (`packages/ontology/src/contract.ts:229`) and the collector merges same-key edges with later props winning (`packages/extract-code-ts/src/collector.ts:149-158,186`). A function that runs an `INSERT` and then an `UPDATE` on one table keeps only the update's `operation`.
5. **An interpolated SQL template produces no edge at all.** `scanBodies` hands the classifier `template.getText()` with each `${...}` replaced by `?` (`packages/extract-code-ts/src/relations.ts:276-278`), and `getText()` keeps the opening backtick. `looksLikeSql` (`packages/extract-code-ts/src/sql.ts:51-55`) requires the text to start with `select`, `insert`, `update`, `delete` or `with` (`STARTS_STATEMENT`, `sql.ts:22`), and a backtick is none of them, so every template literal with at least one substitution is rejected. SQL written as a tagged template, ``sql`...${x}...` `` on a `neon` client for example, is a common way for a TypeScript service to spell a query, and it is invisible to every detector that walks `QUERIES`. Measured with the classifier functions as they are on main, by a script over the 218 tracked `.ts` and `.tsx` files of the saintandstory parent of section 8.1: 50 literals yield a table reference today (2 string literals and 48 substitution-free templates, none an interpolated template), and classifying each template's own literal text recognises 100 more. None of the five inserts into `b2b_leads` and `b2b_standing_orders` that the prediction of 8.1 rested on (the prediction is since retired, section 2) had an edge when this was measured; all five are among the 100. Row C of section 2.1 owns the fix (3.4, 4.2).

A detector that cannot fire is not a detector, and a precision figure measured on one fixture is not a precision figure. This pass specifies the inputs and the evaluation together, because neither is worth building without the other.

## 2. Admission test (aspirational-state 5.3)

The test has three legs, all required, "and no shortcut" (`docs/design/aspirational-state.md`, section 5.3). A capability starts only when all three legs are recorded for it. **There is no waiver route.** A subordinate design document cannot add a shortcut to 5.3, and a change to 5.3 itself would be a separate, owner-approved design change that nothing here proposes. A capability without a verified cited instance stays deferred, and the detectors that depend on it are disclosed as dormant, with the reason, in the docs and the eval report.

**Leg 1 and acceptance are different things.** Leg 1 is a specific commit, incident or tracked issue in a real repository where the defect the item would address actually shipped, "not a synthetic fixture and not a hypothetical". It is a fact about the world. A capability class addresses a defect only if the defect is the one its detector exists to report: for X5, a required column that every write omits; for X10, a defect on a PII write path that no test reached. That an untested PII write exists in a repository is not a shipped defect (every repository has some), so it cannot be a leg-1 instance. **Acceptance** is a different requirement, on the pull request that implements the capability: its extraction must reproduce the parent and fix reports predicted in section 8. A failed acceptance blocks that pull request or sends the design back; it does not change whether the defect shipped, and a passing one adds nothing to leg 1. **Disposition for row E:** the runtime-DDL safety fix and historical-finding triage proceed within the accepted owner window, but the row E change remains no proof of admission or successful acceptance. Note (2026-11-10): rows A to E are implemented and ship in 0.1.0 behind their guards. That did not meet any leg: X5 is documented as dormant pending corpus evaluation (`docs/contradictions/X5.md`). The historical prediction is retired, and the cited-instance and current corpus-firing requirements remain unmet. This records the gap rather than waiving the admission test.

**Row A, as shipped.** Choices the text above leaves open, recorded so the next row does not have to
rediscover them. (1) `ormModel` is recorded only when exactly one ORM source declares the table and
gave it one name; a table declared by both Prisma and Drizzle, or by two models, has none, and
`extract-data` says so in its diagnostics, because one prop cannot say which kind of name it holds.
(2) The `DataSource` node also carries `defaultSchema`, which the alignment needs and the nodes did
not record, and a table whose own `dialect` differs from its data source's (a ClickHouse table in a
PostgreSQL source, read by ClickHouse rules since the ClickHouse dialect change) is listed in the index with that dialect and
compared by it. (3) An unqualified name binds to the default schema only. A name declared in exactly
one other schema, with no table of that name in the default schema, is not bound and not ambiguous,
because which schema a connection searches first is not in the code: the edge keeps the bytes
`defaultTableId` gives (an edge to a node `extract-data` did not emit), and the real table's name
joins `unknownWriterTables`, so a later X5 withholds that table instead of trusting "no traced
write". That costs recall (the real table gets no `QUERIES` edge, so `why` and `blast-radius` of it
miss the writer) and never precision. A repository whose tables all sit in one schema other than
`public` (Prisma `multiSchema`, Drizzle `pgSchema('app')`) gets no binding at all unless the
`extract-data` `defaultSchema` option names that schema (3.3, "Table-id alignment"). (4) An
ambiguous statement of any verb lists the real names of the tables it may mean in
`unknownWriterTables`, and so does a name only one other schema declares (3); only that part, (c) of
the 5.2 row, is A's, and (a), (b) and `untracedWriteCalls` are D's. The prop is emitted only when it
is non-empty (`describeRepo` returns early when there is nothing to write), so on a run with nothing
to list it is absent rather than empty; D, whose rule is that a missing prop is not zero, emits it
on every run. (5) Two things make an index-less run UNAVAILABLE, and both are lexical because the
index that would resolve them is the thing that is absent. (5a) An ORM-shaped write call: with no
index the delegate names of 5.2 (a) are unknown, so the shape is `<expr>.<name>.<writeOp>(...)`
(`update` and `delete` only with an object literal argument, so `map.delete(key)` is not one) or a
Drizzle `insert|update|delete(<identifier>)` chained into `.values`, `.set`, `.where` or
`.returning`, and only in a repository where some file mentions `@prisma/client` or `drizzle-orm`,
the only two clients F1 and F2 can recognise. `orm-shape.ts` is a second, index-free definition that
is not wired to `unknownWriterTables`; D owns the full lexical definition of 5.2 and replaces it. It
covers writes only: when F1 makes ORM reads (the select class) edges as well, an index-less PASS run
would sweep those too, so F1 widens the shape to any client call. (5b) A raw-SQL table reference:
any string the SQL classifier reads (`sqlTableOccurrences`), whether or not an enclosing symbol
gives it an edge, so that the rule does not depend on how a declaration resolved; the diagnostic
names the first one by file and then line. The classifier is loose and the rule inherits that: a
string that starts with a statement verb and holds `from`, `into`, `update` or `join` is read as
SQL, so UI prose such as `'Select files from your computer'` (table `your`) or `'Delete from the
list'` (table `the`) counts, as it always created a phantom `public.your` edge. A test pins this
(`sql.test.ts`). Row C does not change it: design 4.2 ("Relation to today's gate") keeps today's
gate for reads, and `Delete from the list` is a complete `DELETE FROM <ident>`, which the per-verb
shape accepts as well, so all three pinned strings still match after row C. Narrowing the gate would
be a separate decision, and it would change what this rule counts. Row A made raw-SQL `QUERIES`
destinations depend on the index, so "with no ORM-shaped call there is nothing to lose" no longer
holds for the edges A itself creates: without the index the edge points at the name-only table, and
a PASS would sweep the edge an earlier run bound to a declared table, so that `blast-radius` of the
table loses its reader and reads as "nothing touches this table". The UNAVAILABLE run's output is
still stored, so the name-only edge sits beside the bound one until the next full run, which buries
it. The cost is that a repository with raw SQL whose `extract-data` did not PASS (it crashed, it
knew of a source it did not read, or it read sources that declared no tables), or a run narrowed
with `--only extract-code-ts`, has an UNAVAILABLE code scope instead of a PASS one, and every
detector that needs the code scope is UNKNOWN on it. (5c) A repository for which discovery found no
schema source is not in that cost. When discovery completed, found no `.sql`, `.prisma` or Drizzle
`pgTable`, `pgSchema` or `pgEnum` candidate, and knew of nothing it did not read
(`ExtractDataOutput.noSchemaSource`, a field and not a diagnostic), no table was declared in any
form discovery looks for, every raw-SQL name keeps today's `defaultTableId` bytes whether or not an
index exists, and the composition root hands `extract-code-ts` an index with no tables: the code run
stays PASS, with no `ormIndexAbsent`, and the data scope stays UNAVAILABLE. That is a statement
about discovery, not about the repository. Discovery does not look for other ORMs and query builders
(TypeORM, Sequelize, Knex, Kysely and the like), for database files (`.db`, `.sqlite`: reading one
is the introspection that v3 section 6 excludes), for a Prisma schema reachable only through a
`prisma --schema` script flag, or for a schema that exists only in a running database, and it does
not enter dependency directories or a directory the caller named in `skipDirs`. A repository whose
only schema is one of those has `noSchemaSource` true. The `no schema source found` diagnostic says
"none this extractor reads" and lists them. What discovery knows exists and does not read is the
opposite case (the tables it declares are unknown) and keeps the index absent. `discoverSources`
records each such path in `Discovery.unread`, and the diagnostic then says "no schema source could
be read" and names them. The list is: a file that cannot be opened or is over the size limit; a
directory that cannot be listed; a symbolic link that is a directory or is named like a candidate
file (links are never followed); a file with an SQL-family or schema extension that no reader parses
(`.ddl`, `.psql`, `.pgsql`, `.mysql`, `.tsql`, `.plsql`, `.cql`, `.hql`, `.dbml`, chosen as the
extensions database tools write schema scripts in); a module that calls a Drizzle constructor the
reader does not parse (`sqliteTable`, `mysqlTable`, `singlestoreTable`, the `*TableCreator`
factories such as create-t3-app's `pgTableCreator`, `mysqlSchema`, `singlestoreSchema`) or renames
`pgTable`, `pgSchema` or `pgEnum` when importing, re-exporting or destructuring it (`import {
pgTable as table }`), also when the same module holds tables it does parse (it is then in `files`
and in `unread`); a Prisma schema that a `package.json` `prisma.schema` or a `prisma.config.*`
`schema` string literal (or `join` of literals) names and that was not read (a name that is not
`.prisma`, a path in a skipped directory, a missing file; a pointer that leaves the repository is
recorded as the file that holds it, and so is a non-literal `prisma.config.*` pointer, only when
nothing at all was read); and a `.sql`, `.prisma` or unparsed-extension file under a build output or
vendor directory. The last is a decision. The walk skips `build`, `dist`, `out`, `target`, `vendor`,
`.next`, `.nuxt`, `.output` and `.svelte-kit` because they mostly hold copies and artefacts, but a
schema moved into one of them (a vendored schema, a committed build) is a schema that stopped being
visible, which is exactly the transition that sweeps a bound edge: a review of this rule moved a
`.sql` into `vendor/` and the next full run buried the edge the previous run had bound. So those
directories are listed, without reading anything, for schema-kind file names. `node_modules`,
`.git`, `.pnpm-store`, `.yarn`, `.venv`, `venv`, `__pycache__`, `.cache`, `.turbo` and `coverage`
are third-party or tool state and are not entered, and naming an output directory in `skipDirs` opts
it out. The cost is a false UNAVAILABLE for a repository that has no schema it reads and third-party
SQL in one of the listed directories; `skipDirs` is the way out. Two limits remain. When a schema
was read and a candidate was not (`files` non-empty, `unread` not), the run is still a PASS with a
diagnostic that lists the first five unread paths, so a partial model is not silent, and the data
scope's claim excludes what it could not see (5d). Two limits remain here. A Drizzle constructor
reached by some route other than a rename (assigned to another binding, passed as an argument) is
not recognised. (5d) A PASS run that did not read a candidate does not bury what the candidate
declared (invariant 2). The sweep is confined to the claim's selector, and the selector is a list of
positive path patterns, so the claim for a run with `Discovery.unread` non-empty is the whole-tree
selector plus exclusions, `!` items in the selector syntax of `scope-selector.ts` ("Exclusions"): a
path is claimed when a positive pattern matches it and no exclusion does, in SQLite and in the
in-memory merge alike. The selector keeps the whole-tree form because a file that was deleted must
still be swept, and a deleted file is in no list of files read; subtracting the unread is the only
form that gives both. For each unread path `p` the run excludes `p`, `p/**` (an entry is a file or a
directory; `.` excludes everything), and, for a file moved or renamed out of sight, every path whose
file name is the stem of `p` with an extension the extractor reads (`**/b.sql` for `vendor/b.sql` or
`db/b.ddl`). The last exists because a move leaves the old path empty, and the old path is where the
tables the file declared are recorded; without it a move into `vendor/` is indistinguishable from a
deletion. It over-protects: while any `b.*` candidate is unread, a deleted `b.sql` anywhere is not
swept (a missed burial, the safe direction, until the next run that reads everything). A path with a
character the selector cannot write (`,` `{` `}` `*` `?`, a backslash, a control character,
whitespace at either end, an empty or dot segment) cannot take the `p/**` form, because a wildcard
may not precede `**` and `compilePattern` refuses it (a selector that does not compile makes
`finalizeRun` throw and loses the run). Its exclusions are instead `p` with `?` for each such
character (exact depth, which covers the entry if it is a file) and `a/**`, where `a` is the longest
run of leading segments that can be written, its nearest nameable ancestor directory (`**` when
there is none, so nothing is swept), which covers what lies under it if it is a directory. That
withholds more than the entry, never less. A leading `!` is not unwritable: it is written exactly,
as `!!p`, the exclusion of the literal `!p`. A stem whose last character is unwritable gives
`**/*.sql` and so on, which withholds every file of that extension. Two guards keep the claim from
ever failing the run: if the selector does not compile for any reason, and if it would carry more
than 1,000 exclusions (about 45 unread paths, 22 clauses each; the store tests every row against
every exclusion, and on a 3.6k-node graph 300 unread paths took 12.6 s where 50 took 1.2 s), the run
claims nothing for the data scope (`!**` after the whole-tree patterns) and the diagnostic says so.
The run's diagnostics also say that files sharing a stem with an unread candidate are protected from
sweeping until a run that reads every candidate, naming the stems when there are at most five. A
selector with no `!` item keeps the SQL predicate it had before exclusions existed, byte for byte;
only a selector with an exclusion carries the `NOT EXISTS` clause. The exclusions are sorted by code
unit and without repeats, so the same unread set gives the same selector bytes; a run with nothing
unread claims `**/*.{sql,prisma,ts,...}` as before. **Which file owns a node.** A table, column or
schema is recorded at the path of the file whose statement defined it last (`CREATE TABLE`,
`pgTable`, a Prisma `model`, a column's `ADD COLUMN` or definition; an `ALTER ... SET NOT NULL`, an
index or a comment does not move it), and the selector tests that one path. A node is therefore
protected when the file that owns it is unread, not whenever any file that touched it is. Three
cases follow. A table created in a read file and altered in an unread one is re-emitted from the
read file, so it is live by observation; the column the unread file added is owned by it and falls
outside the claim. A table created in an unread file and altered in a read one is created by the
`ALTER` in the model (path: the read file) and re-emitted. A table created in a read file that no
longer declares it, while an unread file also declares or alters it, is buried (tracked in extract-data-contributing-files.md;
reproduced): the selector cannot express "any contributing file", because the store keeps one path
per node and the extractor holds no earlier run, so the conservative rule "protected if any
contributing file is unread" is not available and this case is the residual risk (the table is
declared nowhere this run could read). Edges are placed by the file of their source node, so an edge
whose source is in a read file may be buried although its other endpoint is in an unread one (a
`MIGRATED_BY` edge from a table in a read file to an unread migration; an `FK_TO` edge to a table in
an unread file, which is skipped as "endpoint not extracted"). That has not been reproduced:
attempts with an `ALTER` in an unread migration and an `FK_TO` to a table in an unread file left
every edge live. The node the edge points at is protected. (6) The injected `tableId` function
option is gone: a function cannot cross the host, and the index replaces it.

## 3. ORM client calls as `QUERIES`

### 3.1 What is recognised

Recognition is syntactic plus in-repo symbol resolution. It never reads `node_modules`, because extraction must not depend on whether dependencies are installed (a generated client is usually absent from a fresh clone), and it never executes analysed code. Acceptance (section 7) includes a byte-identical SIF with and without `node_modules`.

| Client  | Receiver evidence (any one form; the table name must also bind, section 3.3)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prisma  | (a) a value whose initialiser resolves, through in-repo declarations and imports, to `new PrismaClient(...)` where `PrismaClient` is imported from `@prisma/client` or a re-export of it. This includes `globalThis.x ?? new PrismaClient()`, `g.prisma \|\| new PrismaClient()`, an in-repo factory function returning one, and the value of `.$extends(...)` called on such a value. (c) An in-repo class that `extends PrismaClient` and any parameter or property annotated with it. (d) The callback parameter of `$transaction`. |

(c) The callback parameter of `.transaction(...)`.                                                                                                                                                                                                                                                                                                                                                                                                                                       |

A client imported from any other path, including a generated client emitted into the repository (for example `@/generated/prisma/client`), is not resolvable without the generated output and produces no edge. A call that has the write shape (`<x>.<delegate>.<writeOp>(...)`, `db.insert(<arg>)`) but fails the receiver or the table binding **produces no edge and keeps its table in `unknownWriterTables`** (section 5.2). The method name alone is never evidence. The route receiver rule that landed with the route receiver change (`packages/extract-code-ts/src/receiver.ts`) is the model: the ORM rules above are its first two evidence kinds, construction and declaration, which need no installed dependency, and the ORM receiver code sits beside it with the same structure. Its third kind, the checker's type when packages are installed, is deliberately not used for ORM clients, because it would make the answer depend on `node_modules`.

**Workspace packages.** In-repo packages are discovered from every `package.json` outside the skipped directories (the `extract-data` skip list: `node_modules`, `dist`, `build`, `out`, `.next`, `vendor`, `coverage` and similar, `packages/extract-data/src/discover.ts:18-36`), keyed by its `name`. An import specifier equal to a name, or a name plus a subpath, resolves without `node_modules` to the file the package's `exports` map names: the `.` entry for the bare name, the matching key or a `./*` pattern for a subpath (the `*` is substituted into the target). Within an entry the conditions are tried in the order `types`, `import`, `default`; a package with no `exports` falls back to `types` then `main`. A target that is not a relative path inside the package, two packages with the same name, or a missing file is unresolved: no edge, and the table joins `unknownWriterTables`. The extractor already reads the nearest `package.json` name for `{module}` (`packages/extract-code-ts/src/modules.ts`). Fixtures: a bare import through an `exports["."]` conditions map, and a subpath import (`@x/prisma/enum`) through `./*`.

Drizzle `db.query.<t>` needs `<t>` to be a key of the `schema` object or namespace import passed to `drizzle(...)`; otherwise no edge. `pgSchema('s').table(...)` is a table constructor like `pgTable`, with the schema taken from the `pgSchema` literal.

**Write hooks.** A Prisma `$use(...)` call, or a `$extends(...)` call whose argument is not an object literal or has a `query` component, may inject fields on every write that no call site names. Each is counted in `writeHooks` (section 5.2). `$extends` with only `result`, `model` or `client` components is not counted. Drizzle has no equivalent call-time hook; its column-level hooks are recorded as client-side defaults (section 4.4).

Kysely, Knex, TypeORM, MikroORM, Sequelize and query builders not listed are out of scope and produce no edge. Adding one is a new row in this table with its own fixtures, not a heuristic.

### 3.3 Binding a call to a `Table`, with one source of truth for names

`extract-code-ts` does not read `schema.prisma`, does not depend on `extract-data` (its `package.json`), and does not re-derive column names. `applyPrismaFile` is not exported by `extract-data` (`packages/extract-data/src/index.ts:9-24`), and this design does not export it.

- `extract-data` additionally records `ormModel` on each `Table` (the Prisma model name, or the Drizzle export name; ships with row A) and `ormField` on each `Column` (the Prisma field name, or the Drizzle property key; ships with F1 and F2). These are props, not new kinds. The physical column name for a Drizzle key is the one `extract-data` already computes (`columnName ?? toSnakeCase(key)`, `packages/extract-data/src/drizzle.ts:312`, pinned by `parity.test.ts:116`: `createdAt: timestamp()` is `created_at`), and for Prisma the `@map` value or field name (`packages/extract-data/src/prisma.ts:266-267`).
- The code-side extractor consumes a **read-only data-model index** built from `extract-data`'s sorted output. **Row A ships** table identity by `(schema, name)`, the Prisma delegate to model to table id map, and the Drizzle table-export name to table id map. **F1 adds** the key-to-physical-column map for Prisma and, for each relation field, the target model, the foreign-key scalar columns and which side owns them (the side whose field has `@relation(fields: [...])`), so nested writes resolve from either side (section 4.2). **F2 adds** the Drizzle key-to-physical-column map and casing. The seam before row A was an injected `tableId` option that nothing passed: `defaultTableId` builds `public.<table>` (`defaultTableId` in `packages/extract-code-ts/src/extract.ts`), the CLI ran the two extractors independently (`codeTsExtractorPort` and `dataExtractorPort` in `packages/cli/src/wiring.ts`), and `extract-data` ids come from `tableName(withDataSource(...))` (`packages/extract-data/src/emit.ts:263-267`). Row A replaces `tableId` with the index (`defaultTableId` stays as the answer for a name no table matches) and has the composition root run `extract-data` first and pass the index in. No new inter-extractor package dependency is introduced.
- **Table-id alignment (row A).** `sqlTableRefs` lowercases every name it returns (`packages/extract-code-ts/src/sql.ts`), while a Prisma model without `@@map` is a quoted, mixed-case table (`"Invitation"`). Matching follows the dialect that `extract-data` recorded for the data source: Postgres folds an unquoted identifier to lower case and keeps a quoted one exact; SQLite compares case-insensitively; MySQL compares exactly. A schema-qualified name binds only to that schema. An unqualified name binds to the default schema (`public` for Postgres); if several schemas hold a table of that name and none is the default, or the folded name matches more than one table, the name is **ambiguous**: no edge, and the name joins `unknownWriterTables` (it is not counted in `untracedWriteCalls`, section 4.2). A name that matches **no** `Table` is not ambiguous: it keeps the answer `defaultTableId` gives today, so the edge still points at an external `Table` node (`emitQueries` in `relations.ts`), and nothing is counted. A name that exactly one **non-default** schema declares, with no table of that name in the default schema, is not bound either: it keeps the same name-only edge, byte for byte, **and** its physical name joins `unknownWriterTables`, so the real table is withheld from a detector that would otherwise trust "no traced write" (the cost is recall: the real table gets no `QUERIES` edge). The default schema is the one the `extract-data` extractor is configured with, `public` when unset; a repository whose tables all live in one other schema names it in `seamline.config.json`, for example `{ "name": "extract-data", "enabled": true, "options": { "defaultSchema": "app" } }`, and unqualified names then bind there. Fixtures: an unquoted statement against a quoted mixed-case Prisma table; `auth.users` and `public.users` both present, where an unqualified `users` binds to `public.users` (the default); `auth.users` and `app.users` with no `public.users`, where an unqualified `users` is ambiguous; a name that matches no table; a schema-qualified statement; `only_other.widgets` as the only `widgets`, where an unqualified `widgets` keeps the name-only edge and is listed in `unknownWriterTables`, and binds to `only_other.widgets` once `defaultSchema` is `only_other`.
- **Crossing the extractor host.** The index is a canonical JSON document built from the sorted `extract-data` output with the `canonicalJson` that `extract-data` already exports (`packages/extract-data/src/index.ts:9-24`). The composition root passes it to `extract-code-ts` as a structured option, and the sandboxed extractor host (`packages/cli/src/sandbox/`) passes that option across the process boundary unchanged. Its bytes are an input of the code run: byte-identical index in, byte-identical SIF out, and the determinism test asserts both. It is handed in rather than read from disk, so the `reads` manifest of `extract-code-ts` does not change.
- **Failure behaviour.** If `extract-data` did not PASS, the index is absent. ORM calls then produce
  no edges and `extract-code-ts` sets `ormIndexAbsent` on the `Repo` node. A PASS code scope with
  every ORM `QUERIES` edge missing is the shape invariant 3 forbids: the store sweeps only for PASS
  results (`packages/core/src/store/sqlite-store.ts:437-452`, gated at `:484`), so a PASS here would
  tombstone the earlier edges, and `why`, `blast-radius` and the MCP tools would read the loss as
  absence. The same holds for raw SQL, since row A made its `QUERIES` destinations depend on the
  index: without it a statement is not bound to a declared table, its edge would point at the
  name-only table, and a PASS would sweep the edge an earlier run bound. So when the index is absent
  and the files read contain at least one ORM-shaped call (the lexical shape of section 5.2) or at
  least one raw-SQL table reference (a string the SQL classifier reads: `sqlTableOccurrences`
  accepts any string that starts with a statement verb and holds `from`, `into`, `update` or `join`,
  so interface prose such as `'Select files from your computer'` counts; that looseness is older
  than row A, and row C keeps today's gate for reads, 4.2), `extract-code-ts` reports
  **UNAVAILABLE** for the run, with a diagnostic naming the first such call or reference: its output
  is still emitted, nothing is swept, and the code scope reads as not PASS, so every detector that
  needs it is UNKNOWN. With neither there is nothing to lose and the run stays PASS (the `Repo` node
  still carries `ormIndexAbsent`). The index is **absent**, not empty, in three cases. (1)
  `extract-data` did not run (`--only extract-code-ts`). (2) It did not see the schema: it reached
  FAIL or crashed, or it was UNAVAILABLE because discovery failed or because it knew of a source it
  did not read (5c lists them: a file that is unreadable or over the size limit, a directory it
  could not list, a symbolic link, a schema in an extension or a Drizzle dialect it does not parse,
  a Prisma schema a package names that it did not open, a schema file under a build output or vendor
  directory). (3) It read sources and they declared no tables (a `seed.sql` with only `INSERT`, a
  `schema.prisma` with a `datasource` block and no model): UNAVAILABLE without the flag, because a
  parser that yields no tables from schema text it did not understand must not read as "no tables".
  When a config lists more than one `extract-data` entry (possible only with different `skipDirs` or
  `maxFileBytes`), an entry in case (2) makes the index absent whichever entry ran first, unless
  some entry reached PASS, whose index stands. The index is **empty** when `extract-data` reports
  that discovery completed, found no schema source it reads or recognises, and knew of nothing it
  did not read: no table was declared in any form discovery looks for, so no name can bind to one
  and every raw-SQL name keeps the `defaultTableId` answer, as it did before row A. That is a
  statement about discovery, not about the repository (5c lists what discovery does not look for).
  The composition root then hands `extract-code-ts` an index with no tables and the code run stays
  PASS, while the data scope stays UNAVAILABLE. The signal is a field of the extractor's output
  (`ExtractDataOutput.noSchemaSource`, carried to the command as `ExtractorOutput.noSchemaSource`),
  never a diagnostic, and it is set only by that discovery result; an empty index never replaces the
  index of an `extract-data` that reached PASS. The cost that remains is that a repository with raw
  SQL whose `extract-data` did not PASS for any other reason (a crash, a source it knew of and did
  not read, or sources it read that declared no tables), or a run narrowed with `--only
extract-code-ts`, has an UNAVAILABLE code scope. An ORM-shaped write in a repository where
  discovery found no schema source is not UNAVAILABLE either: there is no table it found for the
  write to bind to and, before F1, no ORM edge to lose. X5 and X10 additionally require the data
  scope to PASS (`x5-unwritten-column.ts:35`, `x10-untested-pii-write.ts:68`). A crashed extractor
  that returns no authoritative scopes is a separate path, a known open item.
- **Drizzle casing (F2).** `extract-data` has no `casing` handling today (`drizzle.ts` contains none). F2 reads the `casing` option of the `drizzle(...)` call or `drizzle.config.ts`, applies it in the key-to-column map, and where casing cannot be determined marks the table's map unresolved, so a write naming an unnamed-builder key is treated as incomplete. A fixture covers `casing: 'snake_case'`, no casing, and unresolved casing.
- `binding` is `prisma-model` or `drizzle-table` for ORM calls, in addition to the existing `unqualified-name` for raw SQL. Provenance is `EXTRACTED`. Confidence is 1 for an ORM call whose receiver and table both bound; there is no lower-confidence ORM variant, because a guessed receiver is exactly the false positive this design refuses.

### 3.4 One edge per (symbol, table), merged order-independently

The extractor accumulates every call per (caller symbol, table) itself and emits **one** `QUERIES` edge, in sorted order. It does not rely on the collector's merge, which takes the maximum confidence, shallow-merges props with the later edge winning, and keeps the first edge's `srcFile` and `sourceRef` (`packages/extract-code-ts/src/collector.ts:149-158`, `:186`; the node merge at `:120` is later-wins too). Folding before queueing is the precedent `imports.ts` sets and `collector.ts:149-158` now documents. Props, all scalar:

| Prop                              | Meaning                                                                                                                                                                                                                                                                                                                          |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `operation`                       | Unchanged when exactly one class is present, so the bytes of a single-class raw-SQL edge do not change.                                                                                                                                                                                                                          |
| `operations`                      | Added only when two or more classes are present: the sorted, comma-separated set of `delete`, `insert`, `select`, `update`, `upsert`. `writes` is added with it (true when any class is a write). A reader takes `operations` when present and `operation` otherwise; `queryWrites` and the new accessors do the same.           |
| `insertColumns`                   | Sorted union of the columns of the insert-class calls whose own set is complete. Absent when there is no insert-class call.                                                                                                                                                                                                      |
| `insertComplete`                  | Boolean AND over **every** insert-class call (an upsert's create branch included). **A call with no determination counts as incomplete (`false`).** Absent only when there is no insert-class call.                                                                                                                              |
| `updateColumns`, `updateComplete` | The same for update-class calls (an upsert's update branch included).                                                                                                                                                                                                                                                            |
| `insertOrm`                       | True when at least one insert-class call is an ORM client call. Client-side defaults apply only then (section 4.4).                                                                                                                                                                                                              |

| `interpolated`                    | True only when **every** contributing call is a raw statement read from a template literal with at least one substitution; absent otherwise. | edge `confidence`                 | The **minimum** over the contributing calls: the weakest binding governs, so a name-only raw-SQL binding keeps 0.7 (`relations.ts:30`).                                                                                                                                                                                          |
| edge `srcFile`, `sourceRef`       | The smallest `(path, line)` among the contributing calls, as the collector picks for nodes (`collector.ts:118-119`), so the choice does not depend on traversal order.                                                                                                                                                           |

`insertColumns` is a union of complete calls only, so it is never a partial list presented as complete: `insertComplete` is the AND that says whether any call was undetermined, and a detector that needs completeness reads that and nothing else. Lists use the comma-separated encoding `listProp` reads (`packages/contradictions/src/props.ts:43-48`); a column name containing a comma, quote or whitespace makes the call incomplete instead of being encoded. The implementing pull request adds accessors in `props.ts` for every key above (`columnsComplete` has none today; `props.ts:155` reads only `columns`) and updates `queryWrites`.

**Baseline.** Per-class props exist only where column facts are determined (an explicit-list insert or update), and single-class edges keep `operation`, so edges for statements without them keep their bytes. Edges that gain props move the dogfood baseline if Seamline's own source contains such statements or interpolated templates; the implementing pull request is then paired with a dedicated baseline pull request, as is done for other lanes, and says exactly what moved.

**Other consumers of `QUERIES`.** New edges are read by more than X5 and X10. Row C creates edges that do not exist today for two reasons. One is raw-SQL forms the classifier does not know (`COPY`, `TRUNCATE`, `REPLACE`, `MERGE`, `INSERT IGNORE`, `INSERT OR REPLACE`, section 4.2), a handful of statements. The other is every statement written as an interpolated template, which the classifier never sees today (section 1, fact 5) and which is a common way to write production SQL: 100 more recognised statements against 50 on the saintandstory parent. F1 creates ORM-bound edges. Each of those pull requests accounts for the three consumers below:

- **X6** reads every `QUERIES` edge of a reached symbol and prices a fact edge as certain (`packages/contradictions/src/detectors/x6-pii-unauthenticated.ts:73`, `docs/contradictions/X6.md`). When the edge has no `columns` prop it treats every PII column of the table as reached (`x6-pii-unauthenticated.ts:61-78`, `queryColumns` at `props.ts:155`). No extractor emits `columns` today, ORM edges carry `insertColumns` and `updateColumns` instead, and a select-class edge carries none, so a new edge would make X6, the only `critical` detector, report a table's whole PII for a public operation on the strength of a statement whose columns nobody extracted. **X6 therefore skips two kinds of edge and counts them in a note** ("n query edges were not evaluated; ORM-bound: a, interpolated: b"): (a) edges whose `bindings` contain `prisma-model` or `drizzle-table` (F1); (b) edges whose `interpolated` prop is true (C). For these inputs X6 then reads exactly what it reads today: an interpolated statement had no edge before, and a (symbol, table) pair that also has a plain statement keeps `interpolated` absent and is read as it was, because that plain statement already made the edge. A skip is lifted for a kind only by a later row that extracts the select list of such a statement into `columns` (X6 already honours `columns`), and that row needs an instance of its own. The other option, giving a select-class template edge a `columns` list whenever its select list is a literal, is not taken: it needs alias and join resolution across tables, which is a new extraction capability with no cited instance. Fixtures: a public operation reaching a symbol whose only statement on a PII table is an interpolated template gives no finding and the note; the same statement without a substitution gives the finding as today; a symbol with a plain `SELECT` and an interpolated `UPDATE` on that table gives the finding as today (one edge, `interpolated` absent); an ORM-bound edge gives no finding and the note.
- **`infer-join`** scores Column to CodeField joins partly on `QUERIES` structure (`packages/infer-join/src/structure.ts:84,164`: a class with an edge to the column's table scores 0.50, a symbol in the same file 0.30). It reads template-derived and ORM-bound edges like any other: they are facts about which table a symbol runs SQL against, and skipping them would keep the blind spot this pass removes. Joins whose only structural evidence is such an edge therefore gain that component, join confidences rise, and the severities that are capped by them can move. C reports which joins moved on the saintandstory parent and on the bundled example, with a fixture: a Column to CodeField pair whose class has only an interpolated insert into the column's table scores as it does with the substitution-free statement.
- **Traversal allow-lists** include `QUERIES` (`packages/core/src/traversal/reachability.ts:25`, `packages/mcp/src/graph.ts:53`), so `why`, `blast-radius` and the MCP tools return different reachable sets once these edges exist: the blast radius of a table gains every symbol that runs an interpolated statement against it. C reports the change in reachable sets on the saintandstory parent, with a fixture: the blast radius of a `Table` contains a symbol whose only statement against it is an interpolated template.

C and F1 each report what moved in each of the three, and each baseline movement is a paired baseline pull request. The other new raw forms of C (`COPY`, `TRUNCATE`, `REPLACE`, `MERGE`, `INSERT IGNORE`, `INSERT OR REPLACE`) are read by X6 as raw-SQL edges are today; they are a few statements, not a second population, and C lists them in its report.

Determinism test: byte-identical SIF across statement order within a function, across call order, and across file order, for a function that inserts and updates one table, inserts twice with different literals, and upserts.

## 4. Column-level writes

### 4.1 The facts

Each write class has a column set that is either **statically complete** or not. Complete means every column the call writes is known from the source text. An incomplete set (a spread, a non-literal argument, a computed key, a helper that builds the object, an unresolved name) is recorded as `...Complete: false`, never as a shorter list. An incomplete list that a detector treated as complete would manufacture an X5 finding out of an extraction limit, which is the failure invariant 3 exists to prevent.

### 4.2 Sources

| Source                                                                                                                     | Statically complete when                                                                                                                                                                                                                                                                                                   | Column names come from                                                                                                                                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Raw SQL insert-class forms (the table below)                                                                               | an explicit column list of plain identifier tokens, in a single string or template literal. `INSERT ... **Classified raw SQL forms.** A string or template literal is a write statement only if, after leading whitespace and SQL comments (`--` and `/* */`), its text matches one of the per-verb shapes below, read case-insensitively. For a template literal the text is the one defined under "Interpolated templates" below. `<ident>` is a schema-qualified or plain, quoted or unquoted identifier. **The `<ident>` slot of a shape also accepts a placeholder**, so ``sql`INSERT INTO ${table} (a) VALUES (${x})` `` is recognised as an insert and, its table being unknown, is counted (Counting). **A column list and a `SET` target do not accept one**: a placeholder there is not an identifier, so the statement is recognised and its set is incomplete.

| ---------------------------------------------------------------------------------------------------------- | --------------------------------------- | ---------------------------------------------------------------------------------- |
| `INSERT [IGNORE\|OR REPLACE\|OR IGNORE\|OR ABORT\|OR FAIL\|OR ROLLBACK] INTO <ident>`                      | insert                                  | an explicit plain-identifier column list follows                                   |
| `REPLACE INTO <ident>`                                                                                     | insert and delete                       | an explicit column list follows                                                    |
| `INSERT ... INTO <ident> ... ON CONFLICT ... DO UPDATE SET`, `... ON DUPLICATE KEY UPDATE`                 | upsert (insert and update)              | the insert list is explicit and every `SET` target is plain                        |

**Relation to today's gate.** `looksLikeSql` (`packages/extract-code-ts/src/sql.ts:51-55`) accepts a string of 12 or more characters that starts with `select`, `insert`, `update`, `delete` or `with` (`STARTS_STATEMENT`, `sql.ts:22`) and contains `from`, `into`, `update` or `join` anywhere; `TABLE_REF` (`sql.ts:32-33`) then finds the table. It passes prose such as `"Update assumption"` (and `sqlTableRefs` then reports a table `assumption`), and it cannot pass `CALL` or `EXEC`, which contain none of those words. The per-verb shapes replace it for write verbs, because each requires the structure of the statement (`INSERT ... INTO <ident>`, `UPDATE <ident> SET`, `DELETE FROM <ident>`), so text that begins with a verb but lacks the rest of the structure is not a statement: `"Update assumption"`, `"Call us"`, `"Call now"`, `"Call back"`, `"Copy reference"`. Text that has the whole structure is one whatever its author meant: `"Delete from cart"` matches `DELETE FROM <ident>`, as it does under today's gate, and yields a `delete` edge to a table named `cart` (an external table node when no such table is declared). That over-match is a label that spells a complete statement; it costs a spurious edge, not a finding, unless a declared table has that name (9.4). Reads keep today's gate. Today `INSERT IGNORE`, `INSERT OR REPLACE`, `REPLACE`, `MERGE`, `COPY`, `TRUNCATE` and `CALL` return no reference, and neither does a statement preceded by a comment line.

**Interpolated templates.** Today a template with a substitution never reaches that gate in a form it accepts. `scanBodies` gives `emitQueries` `template.getText().replace(/\$\{[^}]*\}/g, '?')` (`relations.ts:276-278`), and `getText()` includes the opening backtick, so the text starts with a backtick, `STARTS_STATEMENT` (`sql.ts:22`) fails, `looksLikeSql` returns false and `sqlTableRefs` returns nothing. (The pattern also stops at the first `}`, so a substitution that holds an object literal or a nested template would leave a fragment behind.) Only a template without substitutions, which `scanBodies` reads through `getLiteralText()` as it reads a string, produces an edge. Row C replaces this: **the classifier is given the template's own literal text**, the head and the literal text of each span joined in order, with one placeholder token in place of each substitution (a token the classifier recognises even inside quotes and never reads as part of an identifier; the code used `?` when this was written; as shipped it is U+FFFF, `SUBSTITUTION` in `packages/extract-code-ts/src/sql.ts`), and never `getText()`. The substitutions are not parsed, so nothing inside `${...}` can change the result. A template nested inside a substitution is a separate literal and is classified on its own. A tagged template (``sql`...` ``, ``prisma.$executeRaw`...` ``, ``db.execute(sql`...`)``) is classified by the same text whatever its tag: a tag is not evidence of a database client, exactly as for a string literal. A placeholder keeps the structure of the statement. In a value position it is ordinary. In the table slot it makes the table non-literal: a placeholder alone, or adjacent to identifier characters or a `.` (`${t}`, `${schema}.users`, `users_${suffix}`, `"${t}"`). In a column list or a `SET` target it makes the set incomplete. On the saintandstory parent 43 of the 44 write-shaped literals (a count made when this section was written; section 8.1 no longer carries it) are interpolated templates, which is why the instance depends on this change.

**Counting.** A literal that matches a shape but yields no attributable (table, class) is counted in `untracedWriteCalls`: the table slot holds a placeholder (a non-literal table), or the shape is `CALL` or `EXEC`. Two other cases are not counted. A literal name that matches **no** `Table` is attributable: it keeps today's edge to an external `Table` node (`relations.ts:450`), because the extractor cannot tell an undeclared table from one declared in a file it does not read, and X5 has no `NOT NULL` fact for it. A literal name that matches **more than one** `Table`, none being the default (3.3), yields no edge and feeds `unknownWriterTables`, so the tables it could be are withheld one by one instead of the whole repository going UNKNOWN. A verb-led literal that matches no shape is not SQL and is not counted. One fixture pair per shape: the classified statement produces its edge, and a variant that cannot be attributed is counted. Clean cases that must count nothing: `createHash("sha256").update(str)`, `searchParams.delete("q")`, `"DELETE"`, `"Call or email us"`, `"Call us"`, `"Call now"`, `"Call back"`, `"Update assumption"`, `"Copy reference"`, `` `Call ${phone}` `` and `` `Update ${n} items` ``. `"Delete from cart"` produces an edge to an external table and counts nothing. A label in the form `CALL <word>(` is counted (`"Call us (24h)"`); that is a false UNKNOWN and costs recall only.

Nested writes (Prisma). A nested write under a relation field is an insert, update or connect on the **other** model's table, and the foreign key is supplied by the parent, so a nested literal never names it (the nested input type omits it).

- On the **owning** side (this model's field carries `@relation(fields: [...])`), `connect`, `connectOrCreate` and a nested `create` contribute the scalar foreign-key columns named there to this call's set.
- On the **inverse** side (the foreign key lives on the child, and the opposite field carries `@relation(fields: [...])`), a nested `create`, a nested `createMany`, or the `create` branch of `connectOrCreate` is an insert-class call on a `QUERIES` edge from the same symbol to the child's table. Its column set is the literal's keys **plus the scalar foreign-key columns from the opposite field's `@relation(fields: [...])`**, taken from the index. If the opposite field cannot be resolved (an ambiguous self-relation, a model missing from the index) the call is incomplete, which silences the child table for X5. A nested `connect` or `set` on an inverse field is an update-class call on the child's table whose set is exactly those foreign-key columns. A nested value that is not an object literal (or array of them) is incomplete. Without this rule X5 would report the child's foreign key as unwritten by construction.
- Implicit many-to-many relations touch a join table with no `Table` fact, so no claim can concern it.

Keys whose value may be `undefined` at run time (Prisma ignores `undefined`) are counted as named. That is precision-safe for X5 (more columns look supplied) and the X10 claim wording is accordingly "names" (section 5.4), not "stores a value in".

Property keys are mapped to physical column names only through the index (section 3.3). Nothing in `extract-code-ts` lowercases, snake-cases or otherwise re-derives a column name.

### 4.4 Defaults: what counts, and who supplies it

A column has a default when its source declares one. ## 5. Detectors, unknown-writer facts, and test facts

### 5.1 X5 (unwritten required column)

X5 as written reads every write edge and drops edges with no column list (`packages/contradictions/src/detectors/x5-unwritten-column.ts:42-51`; below, `x5` and `x10` abbreviate that file and `x10-untested-pii-write.ts` in the same directory). It changes as follows. Note (2026-11-10): row E has shipped, so "as written", "today" and "current" in this list describe X5 before row E, and the items describe X5 in 0.1.0 (for item 7, `Math.min` over the insert edges' confidence in `x5-unwritten-column.ts`). The X10 half of item 7 is not done: `x10-untested-pii-write.ts` still computes `isFact(provenance) ? 1 : confidence`.

1. **Only inserts can omit a required column.** X5 reads `insertColumns` and `insertComplete` only. An `UPDATE` that does not set a `NOT NULL` column is correct.
2. **An insert edge with no `insertComplete` counts as incomplete**, not as nothing: today a column-less edge is filtered out (`x5:42-45`) instead of being treated as an unknown writer.
3. **One unknown insert silences the table.** If any insert-class edge into a table from a fact symbol has `insertComplete` false, X5 says nothing about that table, because the unknown insert may supply the column.
4. **A column is reported** when it is `NOT NULL`, has no default the writers supply, and is named by no edge's `insertColumns`. A client-side default (`defaultSite = client`) is supplied only by an edge with `insertOrm` true; a raw-SQL-only edge does not receive it. A `db` default is supplied to every writer.
5. **Closed-world guards (section 5.2) apply before any of the above.**
6. **Triggers and dynamic DDL.** A `BEFORE INSERT` trigger on the table, seen in any SQL file `extract-data` read, may supply the column; `extract-data` records it as `insertTrigger` on the `Table` and X5 stays silent for that table. A `DO` block or `EXECUTE` of dynamic DDL means the replay of the schema is incomplete, in any `.sql` file the model replays and not only in a migration; `extract-data` counts these in `dynamicDdl` on the `DataSource` and X5 is UNKNOWN while it is above zero (a dynamic `ALTER ... SET DEFAULT` could otherwise make a visible NOT NULL column look unsatisfied). Every `DO` block or `EXECUTE` in a migration counts; in any other `.sql` file, such as a schema snapshot or a seed, one counts when its own text contains `CREATE`, `ALTER` or `DROP`, so a data load in a `DO` block does not make X5 UNKNOWN for the repository. `insertTrigger` is a union over the standalone `.sql` files and an ordered replay over the migrations (5.2), so trigger add/drop replay does not depend on standalone file order. Cross-file table renames remain path-order dependent when a rename sorts before its table declaration: the model cannot rename a table it has not seen. Keep a rename with its declaration or in an ordered migration (see `packages/extract-data/README.md`, "Triggers and replay order").
7. **Confidence** is the minimum of the contributing insert edges' own confidence. The current `isFact(provenance) ? 1 : confidence` (`x5:28-30`) discards the edge's 0.7 and would report a name-only table binding at confidence 1; E replaces it by the edge's `confidence`. The same line in X10 (`x10-untested-pii-write.ts:87`) is replaced by G (section 5.4).
8. **A table declared by more than one non-migration source is withheld.** `extract-data` merges declarations of one table by name into a single `Table` whose columns and defaults are the union, so a column that only one declaration has can look unwritten by an insert written for the other (two `schema.prisma` files with `@@map("notes")` declaring different NOT NULL columns; Prisma plus a `.sql` file; Prisma plus Drizzle). `extract-data` records `declarations`, the count of distinct non-migration source files that declare the table, and X5 withholds a table with `declarations > 1` with a note. Migrations that alter a table are not declarations. Fixture: the `@@map("notes")` pair with a raw insert from the second application's columns.

**What the guards do not see.** They are lexical, so they bound recall and weaken the claim from "no write path supplies the column" to "no traced write path supplies it", the wording the detector already uses (`x5:69`). Writers that stay invisible: an aliased delegate (`const model = prismaModelForTable(t); model.upsert(...)`, madrasati-pro `src/services/database-service.ts:69,242,258`; `const m = prisma[name]; m.create(...)`); `db.insert(param)` where `param` is an identifier that is not a Drizzle table export, in a file that imports none of the listed modules (rule (5) counts it in a file that imports one), which includes an aliased table import (`insert(appUsers)`) in such a file; a statement built by concatenation other than the phrase-only form of rule (2b) (`"UPDATE " + table + " SET ..."`, or a verb that is itself spliced); a nested relation write into another table that 4.2 does not resolve; a leading `WITH ... INSERT|UPDATE|DELETE`; `UPSERT INTO`; `LOAD DATA`; and any statement at module level, because `emitQueries` returns when there is no enclosing symbol (`relations.ts:442-450`). A visible insert that omits a truly NOT NULL column still fails at run time whatever else writes the table, so these gaps cost recall and can make the finding's "no write supplies it" wording too strong; they do not make the visible insert correct.

**Mechanism.** A detector sees `GraphView.scopeStatus` only, which returns PASS, FAIL or UNAVAILABLE (`contract.ts:377-384`), and extractor diagnostics are free-text strings never exposed to detectors (`contract.ts:261`); UNKNOWN today comes solely from `requiredScopes` (`packages/contradictions/src/detector.ts:121-123`, `runner.ts:73-93`). The props above therefore **are graph facts**, and `DetectorSpec` (`detector.ts:97-112`) gains an optional `unknownWhen(g): string | undefined`. `runDetectors` treats a defined return exactly like a blocked scope: outcome `unknown`, the reason text, no findings. This is a change inside `packages/contradictions`, not in `contract.ts`; the contract's `Maybe` already carries the UNKNOWN outcome. The implementing pull request carries a fixture pair per prop.

Repo-wide: `untracedWriteCalls > 0`, `writeHooks > 0`, `runtimeDdl > 0` or `dynamicDdl > 0` makes X5 UNKNOWN. **A missing prop is not zero**: an older SIF, a partial run or an extractor that did not run leaves `untracedWriteCalls`, `writeHooks`, `runtimeDdl`, `testFilesUnread` or `dynamicDdl` absent, and `unknownWhen` then returns a reason naming the absent prop. **The per-table and per-column facts read the same way.** An absent `declarations` or `insertTrigger` on a `Table`, or an absent `defaultSite` on a `Column`, is unknown, never "one declaration", "no trigger" or "no default": a data scope kept in the store from an older run, next to a newer code run, would otherwise read as exactly those. `extract-data` writes them so that the two can be told apart. `defaultSite` is `db`, `client` or `none`, `insertTrigger` is `true` or `false`, `declarations` and `dynamicDdl` are counts, and each is left off when a file of a kind that could contradict it failed to parse or was not read (a failed file never turns into `client`, `none`, `false`, `1` or `0` by omission). "Not read" covers a file that failed to parse, a file over the size limit or unreadable, a symlinked `.sql` or `.prisma` file (not followed), and a directory that could not be listed, each named in the run's diagnostics as `schema source not read (<reason>): <path>`. A symlinked directory (`db/migrations -> /etc`) is reported the same way as a symlinked file, because its target may lie outside the repository, where nothing is read, and a directory or a link to one may hold a source of any kind, so it withholds every kind. A directory link whose target is inside the repository and not under a skipped directory is walked at its own path and is not reported. A candidate file link is always unread, including an alias to a separately read target: that target may later be capped or unreadable, and cannot authorize sweeping facts previously owned by the alias's path; a link that points nowhere hides nothing and is not reported, while one that cannot be resolved for another reason (a loop, no permission) is. Test and fixture modules, including `.test.` and `.spec.` basenames, are probed like any other module. Constructor names only in strings, comments or string-valued object labels are ignored; an actual unparsed declaration remains unread regardless of its filename. Every TypeScript or JavaScript source file over the configured size limit, unreadable, or symlinked outside the repository is a possible Drizzle schema and withholds `declarations` and `defaultSite` (not the SQL props). A bounded prefix cannot establish absence: any dialect's schema import may follow a long comment or license preamble. The size cap is preserved, so this deliberately withholds facts for oversized ordinary modules and bundles too; fully read string and comment samples still hide no schema. `defaultSite` keeps `db` in that case, although an unread file may add a database default or remove one (an unread migration can `DROP DEFAULT`): `db` is the safe direction, because X5 reads it as supplied and stays silent. A consumer gates on `defaultSite`, not on `hasDefault`, which keeps saying what was read. A `CREATE TRIGGER` that cannot be attributed to a table can only add a trigger, so it withholds `insertTrigger: false` on the other tables and leaves a trigger already seen `true`; an unread file or a construct that hides statements may also drop one, and withholds both values. Per table: a table in `unknownWriterTables`, or carrying `insertTrigger`, is withheld from X5 with a detector note naming it. Row E makes detector notes visible in `check`, so a withheld table does not look like a clean one. Fixtures for 5.2 include an SIF with each prop absent, and an unread JS file with `prisma.<camelModel>.create` over a `@@map`ped table (the table is withheld).

### 5.3 Test facts (`TestCase`, `TESTS`) in `extract-code-ts`

- **Test-shaped files** are files the extractor already reads whose name matches `*.test.*` or `*.spec.*`, or any of whose path segments is `__tests__`, `test`, `tests`, `e2e` or `spec`, or that import a package from a fixed list of other runners (`tape`, `uvu`, `@japa/runner`, `jasmine`, `qunit`, `zora`, `supertape`, `baretest`, `riteway`). Defining test-shaped by directory and runner import, not only by name, is what stops a file such as `test/user.ts` that uses an unlisted runner from hiding.
- **Test files** are test-shaped files, or files that call test functions, that take their test functions from either of:
  - an import from a recognised module: `vitest`, `@effect/vitest` (whose `it.effect`, `it.scoped`, `it.live` and `it.scopedLive` are test calls), `@jest/globals`, `node:test`, `bun:test`, `@playwright/test`, `mocha`, `ava`, `tap`;
  - **globals**: a file that calls `describe`, `it`, `test` (or the BDD aliases `context` and `specify`) with no import of that name is a recognised test file. These are the globals frameworks: Jest, Mocha, Jasmine, and Vitest with `globals: true`. The extractor does not read the runner's configuration; a global call in a test-shaped file is enough.
- **Unread test files.** A test-shaped file that (a) imports a test function from any other module, (b) has no recognised test call but calls a runner entry point on a short fixed list (`suite`, `QUnit.test`, `Deno.test`), or (c) has a test callback that cannot be resolved (below), produces no `TestCase` for the unresolved part and is counted in `testFilesUnread`. A global-call file that also imports a test function from an unlisted module is case (a). A test-shaped file with no test call at all (a helper) is not counted.
- **One `TestCase` per test call.** The title segment is the static title (a string literal or a template literal without substitutions). **A dynamic title** (`it.each`, `test.each` and `describe.each` tables, a template with substitutions, a test generated in a loop) still produces a `TestCase`, with the fixed segment `<dynamic>` in place of the title, so its `TESTS` edges survive; several dynamic tests under one describe chain merge into one node (below). A dynamic `describe` title is likewise the segment `<dynamic>`. `testCallsDynamicTitle` counts these calls for the report and is **not** an UNKNOWN trigger.
- **Callbacks.** For `.each` forms the callback is the last function argument of the returned call. A callback given as an identifier (`it('x', runCase)`, `it.each(table)('x', handler)`) is resolved by the checker to its declaration and treated as the callback; if it cannot be resolved, the file is case (c) above. A `beforeAll` or `beforeEach` at file level, outside any `describe`, is a hook of every test in the file.
- **Skipped.** Definitely skipped forms never count as verification: `.skip`, `xit`, `xtest`, `xdescribe`, `describe.skip` or `describe.todo` on any ancestor, `it.todo`, `test.todo`, `test.fixme`, and `skipIf(true)`/`runIf(false)` with literal arguments. Conditional forms (`skipIf`/`runIf` with a non-literal argument, `test.skip()` called inside a test body) count as verification, the precision-safe direction because more tests mean fewer X10 findings.
- **Identity is path-free:** `{repo}:TestCase:{module}#test:{describe chain} > {title}`, with `{module}` the nearest `package.json` name as for symbols. Two test cases with the same chain and title in one module merge into one node. The extractor performs this merge itself rather than relying on the collector, whose node merge is later-wins (`collector.ts:120`): `skipped` is the **AND** across copies (the merged test is skipped only if every copy is), and `TESTS` edges are the union. This can over-count verification (a skipped copy's edges stay), which is the precision-safe direction.
- **`TESTS` edges** go from a `TestCase` to each in-repo `Symbol` called directly in the test callback or in a hook of an enclosing `describe` (`beforeEach`, `beforeAll`, `before`), resolved by the type checker as `CALLS` is. Test names are never read for meaning.
- **Helpers and dynamic imports.** A test callback may call a helper declared in the same test file; the helper is a `Symbol`, `TESTS` points to it and `CALLS` continues from it, and X10's closure passes through it (section 5.4). In a test file, a binding destructured from `await import('<literal specifier>')`, or a namespace object from it, resolves to the named export of the target module when the specifier resolves to an in-repo file or workspace package. Mocking frameworks hoist module mocks and force the unit under test to be imported dynamically (`mock.module` in `bun:test`, `vi.mock` in vitest), so without this rule the usual unit-test shape leaves no edge. The rule applies to calls in test files only, so it does not change the `CALLS` facts of production code.
- **What `TESTS` cannot see, stated.** Resolution stops at the declaration the checker names (`resolve.ts:48`): an interface-typed receiver resolves to the interface member, not the implementation, so X10 follows `IMPLEMENTS` (section 5.4). Tests that drive the code through a transport create no edge. **Driver shapes** (`testDriversUnresolved` counts the test files containing any of them): an import of `supertest`; a call to `app.request(`, `app.fetch(` or `app.inject(`; any file that imports `@playwright/test` and uses its `page` or `request` fixtures; a call to `createCaller(` or `createCallerFactory(`; `Test.createTestingModule(`; `testApiHandler(`. Event emitters and DI containers have no lexical shape and are not detected (section 9.4).
- **Provenance.** `TestCase` and `TESTS` are `EXTRACTED` with confidence 1, as `CALLS` is; they are facts under `isFact` and may justify an X10 finding. The counts of section 5.2 are not findings inputs.

### 5.4 X10 (untested PII write path)

1. As today, X10 reports nothing and emits a note when the graph holds no `TestCase` at all (`x10:72`); a repository with no tests has an absent suite, not untested paths. (`CoverageRecord` is not produced by this pass; `isVerified`'s `COVERS` branch stays dormant.)
2. **UNKNOWN when the test layer is incomplete:** `testFilesUnread > 0`, or the prop absent, makes X10 UNKNOWN through `unknownWhen` (section 5.2), because an unread test may be the one that reaches the write. Globals-only files and dynamic-title tests are read (section 5.3), so they do not trigger it.
3. **A write counts as writing a PII column only through a complete set.** The PII columns written by an edge are `insertColumns` (when `insertComplete`) and `updateColumns` (when `updateComplete`) intersected with the PII columns, plus every PII column of the table for a `delete`. An incomplete set yields a note ("writes <table> with an undetermined column set"), never a finding. Today an incomplete set "still counts" as writing every PII column (`x10:85-91`), and a raw `UPDATE users SET last_seen = now()` already reports every PII column; both are replaced. Note (2026-11-10): as implemented, the complete-set rule is in place (`writtenColumns` in `x10-untested-pii-write.ts` returns no column set for an incomplete insert or update, and the edge then yields no finding). Two parts of this paragraph are not implemented: no "undetermined column set" note is emitted, and an edge whose only operation is `delete` yields no finding. The claim text says the call **names** the column.
4. **Untested** means the bounded reverse closure from the write symbol was **exhausted** without reaching a non-skipped `TestCase` through `TESTS`. The closure follows `CALLS` backwards and, at a call to an interface member, also reaches the same-named member of every in-repo class that `IMPLEMENTS` the interface (`relations.ts:46,96`). The bounds are constants in the detector reference page (initially depth 6 and 1,000 visited symbols), and the traversal reports truncation in the shape of `packages/core/src/traversal/bounds.ts`. **A truncated closure is UNKNOWN for that symbol (withheld, with a note), not "untested".** A fixed bound of three `CALLS` hops would be wrong: controller to use case to service to repository to DAO is routine. A test that replaces the database client wholesale and asserts on the mock still reaches the write in the call graph and counts as reach (section 9.4).
5. **Drivers.** When `testDriversUnresolved > 0`, a write symbol reachable in the closure from a symbol with a `HANDLES_ROUTE` edge is skipped with a note, because a driver-shaped test may exercise it. The skip is scoped to `HANDLES_ROUTE`, which `receiver.ts` produces for koa, elysia, express, fastify and hono and for NestJS decorators only; oRPC, tRPC, Next file routes and server actions produce none, so in a repository whose tests drive such code through a browser or an HTTP client X10 over-reports (section 9.4).
6. **Test support, seed and script symbols are not evaluated.** A write symbol whose file is test-shaped, lies under a directory named `fixtures`, `scripts`, `seed`, `seeds`, `__mocks__`, `playwright` or `cypress`, or has a file name containing `seed`, `setup` or `fixture` (case-insensitive) is skipped, and the detector note counts the skipped symbols. Without this, seed and setup helpers such as a `databaseSetup.ts` that `createMany`s users would be reported as untested PII writes. Fixture: a seed helper that writes a PII column is skipped and counted; the same write in a service file is reported.
7. Confidence is the edge's own confidence times the column's PII weight (replacing `x10:87`).

## 6. The evaluation corpus and `pnpm eval`

### 6.1 Corpus, partitions, fetching

`eval/corpus.json` pins at least six public TypeScript repositories by clone URL and full commit SHA, together spanning Prisma, Drizzle, SQL DDL or migrations, OpenAPI, and Zod, none authored by this project. They are split into a **development partition**, used to build and fix the detectors, and a **sealed partition** that nobody opens (no run output, no labels) until the detector and extractor change set is frozen; the freeze is recorded as a commit sha in `eval/FREEZE` (absent in 0.1.0; `eval/README.md` says it is recorded when the evaluation is run for 0.2.0), and a detector or extractor change after the freeze burns the sealed partition, which is then replaced by new repositories. The selection and the reason for each entry are recorded in the file. A repository may be pinned at two commits (a parent and its fix) when an admission instance of section 8 needs both; the pair counts as one repository for the partition sizes.

Nothing from these repositories is vendored. `pnpm eval` fetches each one at its pinned SHA into a gitignored cache (`.eval-cache/`), verifies `git rev-parse HEAD` equals the pin, and refuses to run on a mismatch. Cloned content is untrusted data: the fetch disables hooks (`core.hooksPath=/dev/null`), submodules (`--no-recurse-submodules`), LFS (`GIT_LFS_SKIP_SMUDGE=1` and the LFS filter overridden) and filters, and nothing from a clone is ever executed, installed or built. `pnpm verify` never fetches and never runs the evaluation, so the gate stays offline and the engine never makes a network call. The eval script lives in a private package or `scripts/`, outside every published package's `files` allowlist, so the README's "makes no network calls" stays true for what ships.

### 6.2 Licensing of the corpus and the mutants

Several plausible corpus repositories are AGPL-3.0 and some of the repositories this pass examined are, so the evaluation must not embed their source in this Apache-2.0 repository (aspirational-state 6A.6). Labels cite `path:line` and give a rationale in our own words, with no verbatim source beyond identifiers. The same holds for a repository with **no licence** (saintandstory has none at the parent commit of 8.1): it is pinned like the others, its entry records the licence as none, and because nothing may be copied from it the harness and the labels print and quote nothing from a cloned file beyond `path:line` and identifiers. A cloned repository can also track credential files (saintandstory tracks `.env.production` and `.env.vercel`): no extractor's `reads` selector matches a dotenv file, the harness never opens one, and no label, report or comment quotes one. `eval/mutants.json` stores **generated edit descriptors** (file path, anchor such as "Prisma model `Y`, field `X`", and an operation such as `set-optional`, `remove-key`, `add-not-null-column`) and the script synthesises the edit from the fetched file at run time; it stores no diff and no context lines from a third-party file.

### 6.3 Precision

`pnpm eval` runs `seamline extract` and the detector catalog on each unmodified repository and assigns every finding a stable id (repository, code, left id, right id).

- **Counting unit.** Findings are clustered by root cause before counting: findings of one detector in one repository that share the same left id or the same right id are one cluster unless the labeller records otherwise. `tp`, `fp`, `unclear` are counted per cluster.
- **Verdicts.** `tp`: both cited facts are verified at source at the pinned SHA and they genuinely disagree as the finding claims. `fp`: they do not, or the join pairs unrelated things. `unclear`: the source does not decide it (for example it depends on run-time configuration). The release figure uses the strict reading (`unclear` is not `tp`); the lenient reading (`unclear` excluded) is reported beside it.
- **Independence.** Each label records a reviewer identity that differs from the identity that authored the detector or extractor change under review; for an agent the identity is the account and model that produced the label, and two agents sharing an account do not count as independent. A sample of at least 20 percent of clusters (never fewer than 10) is labelled twice by two distinct identities and the agreement figure is reported.
- **Blind label sheet.** The sheet shows the two cited source locations as `path:line` at the pinned SHA, never file content, and the detector's generic rubric question (for X5: "does any write supply this column?"); it does not show Seamline's claim text, confidence or rationale.
- **A finding with no label fails the evaluation**, so a new finding cannot slip into the precision figure unreviewed.
- **The bar** is taken on the **sealed** partition, once it has at least 30 labelled clusters: pooled strict precision of at least 0.90 **and** a 95 percent Wilson lower bound of at least 0.75. (27 of 30 is 0.90 with a lower bound of about 0.74 and does not pass; 28 of 30 has a lower bound of about 0.79 and does.) **Per detector**, the report prints the count, precision and Wilson interval; a detector with at least 5 labelled clusters needs a point estimate of at least 0.80, and a detector with fewer is reported as **unmeasured** and cannot be called validated in the README. One prolific detector therefore cannot carry a failing one.

### 6.4 Recall

`eval/mutants.json` lists injected contradictions: for each detector, one or more small named edits (make a Prisma field optional that a Zod schema requires; add a `NOT NULL` column with no default to a table whose every traced insert is complete; remove the handler of an OpenAPI operation). Each names the finding it expects (code plus left and right ids, or a matching rule when an id is not knowable beforehand). `pnpm eval` applies each to a scratch copy, re-runs, and counts the mutant detected when the expected finding appears and was absent on the unmodified repository. Recall is reported per detector. A detector with no mutant reports recall as `n/a`, never as 1.

### 6.5 Firing and dormancy

The report states, per detector, how many findings it produced across the **unmodified** corpus repositories. A detector that produces none on any of them is disclosed as dormant in `README.md` with the reason, whatever its mutant recall. "Fires" means on an unmodified repository in the corpus, not on a Seamline fixture and not on a mutant: an X5 that fires only on mutants is dormant on real code and is disclosed as such, with its mutant recall beside it.

### 6.6 Calibration

The report groups labelled findings by confidence band and prints observed precision per band. Confidence is recalibrated only when a band's observed precision is outside its nominal range by more than the band's own sampling error, fitted on the development partition with leave-one-repository-out checking and then checked, not refitted, on the sealed partition. [THREATMODEL R8](../../THREATMODEL.md) is updated to state what the confidence score now means and on how many labelled findings it rests. Note (2026-11-10): not done; no refit has been run, and R8 says that lineage confidence remains uncalibrated.

The implemented refit trigger is a development band's 95 percent Wilson interval wholly outside its nominal band. Each band needs labelled findings from at least two upstream repositories; insufficient data means not estimable. Leave-one-repository-out excludes all pins of the held-out upstream together. The mapping targets raw finding correctness, TP/(TP+FP), not each inferred lineage edge. Its score is additive report metadata: raw confidence, severity and the full finding population remain unchanged, including mapped zeros. Sealed labels check the fitted mapping without changing it. The report records fit counts, digest and paired Brier denominators; no estimate or release validation is inferred from sparse data.

### 6.7 Release gate

`pnpm eval` is outside `verify`, so labels, pins and any README precision claim could rot unseen. The implementing pull request adds an item to `docs/PUBLIC-RELEASE-CHECKLIST.md`: a **recorded passing eval run** (corpus SHAs, the detector code sha, the figures above) newer than the release candidate commit is required, and a missing or failed eval fails the release (aspirational-state 3.1: a gate that could not run is a failed release). README precision figures cite that report.

Identifiers and calls are not executed or resolved during reconstruction. SQL strings, quoted identifiers and comments containing those words are not mutation statements. Literal and reconstructed DDL in an unread JavaScript or TypeScript setup file therefore contributes to the measurement. Valid unread source with DDL words only inside SQL strings or comments still permits a measured zero. If unread coverage cannot be listed, a bounded file read fails, or an unread source has syntax errors, `runtimeDdl` is omitted rather than certifying zero. Files and directories excluded by the existing unread-source policy remain excluded.

### 9.2 X6-shaped search, and why nothing survives

X6 fires only when all of the following hold: an OpenAPI `Operation` has an effective `auth` of none, public or anonymous (`security: []` or `[{}]`; an operation or document with no `security` at all is `unknown`, which X6 reports only as a note, `packages/extract-contracts/src/openapi.ts:26-38`); the operation's `RouteHandler` has an incoming `HANDLES_ROUTE` from a symbol and `CALLS` reach a symbol within two hops (`joins.ts` `OPERATION_TO_SYMBOL`); and that symbol has a `QUERIES` edge to a table with a PII column (`packages/contradictions/src/detectors/x6-pii-unauthenticated.ts:61-78`). So the defect shape is a contract that **declares** an endpoint public whose handler reaches a PII table. A fix that adds a missing authentication or authorization check in code is not X6-shaped unless the contract also declared the operation public.

Searches: a commit-message scan of the corpus clones for authentication, authorization, IDOR and exposure fixes (about 60 hits across documenso, dokploy, flowise, formbricks, homarr, rallly, karakeep, typebot, umami, openstatus, unkey and others); a scan of commits since mid-2024 that touch an OpenAPI or swagger file and mention `security` (rallly, karakeep, reactive-resume, dokploy, formbricks, typebot, homarr, umami); one GitHub commit search; one web search for advisories. The dokploy, formbricks, typebot and umami fixes are server actions, tRPC or oRPC procedures, or IDOR checks (unverified: judged from commit titles only). Unverified: the advisories the web search returned (Budibase, Flowise's forgot-password response, Flag Forge) appear from their summaries not to be Prisma or Drizzle applications with an OpenAPI document declaring the route public; they were not examined further. Leg 1 for ORM `QUERIES` as an X6 input is not met. X6 on real code would need a repository that ships an OpenAPI document with explicit `security: []` operations.

### 9.4 Known limits of the design

- X5 is a "no writer supplies it" detector. When one writer names the column it is silent even if three siblings still omit it (section 8.1 once cited such a case; its prediction is since retired). That is the precision-first choice, and it costs recall.
- The closed-world guards make X5 UNKNOWN on repositories with any `$executeRawUnsafe(<variable>)`, computed delegate, field-injecting extension or dynamic DDL (umami and management-os above). On real repositories this may leave X5 UNKNOWN more often than it fires; the evaluation will measure that, and if X5 fires on no unmodified repository it is disclosed dormant (section 6.5). The guards are lexical and miss aliased delegates and the other forms listed under "What the guards do not see" in 5.2, as madrasati-pro's snapshot import shows, so a finding can name a column that an unseen writer supplies.
- `unknownWriterTables` is a lexical scan. A computed table name in an unread file is not detected, and a name collision can only over-count (withhold a table).
- Keys whose value is `undefined` at run time count as named (section 4.2).
- A statement-shaped label is a statement. `"Delete from cart"` matches `DELETE FROM <ident>` and yields a `delete` edge to a table named `cart` (4.2), and `"Call us (24h)"` matches `CALL <ident>(` and is counted in `untracedWriteCalls`. The first adds a spurious edge, the second a false UNKNOWN for X5.
- Schema facts that exist only in dynamic DDL, TypeScript-embedded DDL strings, or database triggers beyond `BEFORE INSERT` are invisible to `extract-data`; absence of a finding there is not evidence.
- Receiver evidence is syntactic. A client reached through a path the rules do not name is untraced, not wrongly traced.
- The driver shapes of 5.3 are enumerated, not inferred. Event emitters and DI containers have no lexical shape and are not detected, and a driver shape not on the list is a hidden test path (X10 can over-report), which the evaluation's labels are the check on.
- Any test-shaped file that takes its test function from a runner not on the list in 5.3 makes X10 UNKNOWN for the whole repository (`testFilesUnread`). That is deliberately conservative; `@effect/vitest` had to be added for one corpus repository, and the evaluation will show how many corpus repositories still fall out of X10 for this reason.
- Reporting UNAVAILABLE for the code scope when the data-model index is absent (3.3) blocks every code-scope detector on that run, including X4 and X9, which do not need the data scope. That is the conservative direction. It applies to any repository whose code holds a string the SQL classifier reads (not only real SQL: `'Select files from your computer'` is read as a `SELECT` from a table named `your`, a looseness older than row A that row C leaves as it is, 4.2), so a repository with such a string, a schema source it did not read and no index is never PASS on the code scope. A repository for which discovery found no schema source is not affected: its index is empty and its code run stays PASS (3.3, "Failure behaviour"). That is a statement about discovery, not about the repository: a schema kept in a form discovery does not look for (another ORM or query builder, a database file, a `prisma --schema` script flag, a database reached only at runtime) leaves it true, and 5c lists the forms. A schema moved between two runs into a form discovery does not read but does recognise (a symbolic link, a `.ddl` rename, a directory under `vendor/`) keeps the code scope UNAVAILABLE and sweeps nothing; one moved into a form it neither reads nor recognises would not, which is the residual risk of the empty index.
- `defaultSchema` is a property of a data source, and an unqualified name is bound against it alone, so one data source cannot bind both a PostgreSQL `public` table and a ClickHouse table that lives in another database. umami is the example in the corpus: `website_event_stats_hourly` is a ClickHouse table in the database `umami` (`db/clickhouse/schema.sql`) and the queries reference it unqualified, so with the default `public` it is the "declared in exactly one other schema" case of decision 3: the edge keeps today's bytes and the `Repo` node gains `unknownWriterTables: website_event_stats_hourly`. Pointing `defaultSchema` at `umami` would flip the same problem onto the PostgreSQL tables. Rows D and E should expect this table to be withheld rather than traced; a fix needs the default schema to belong to a table's dialect or to a second data source, not to the one option.
- Drizzle behind a namespace import: `eachCall` skips a member prefix, so `export const user = pg.pgTable(...)` carries `ormModel` and is in `drizzleExports`, but a column builder behind a namespace (`pg.text('id')`) is not read (`parseBuilder` takes the first word as the builder). A table declared only that way has no columns from Drizzle, and a foreign key from a bare-import table to it is unresolved, now for the column instead of the table. Where migration SQL declares the columns, they come from it.
- `extract-data` does not infer the dialect from a Prisma `provider` or a Drizzle driver. A MySQL or SQLite repository with the default configuration is bound by PostgreSQL rules, which under-binds (today's behaviour); the `dialect` option states it.
- The three rules written for the typebot candidate (workspace-package resolution, dynamic-import bindings in test files, `@effect/vitest`) stay in the design for the blocked rows F1 and G; nothing admitted depends on them, and each ships with its own fixtures.
- **A mocked client counts as reach.** A test that replaces the database client wholesale and asserts on the mock reaches the write in the call graph, so X10 counts the write as tested. That is a verification of the call chain, not of the write.
- **The X10 driver skip is narrow.** 5.4(5) is scoped to symbols reachable from a `HANDLES_ROUTE` symbol, and `receiver.ts` recognises koa, elysia, express, fastify, hono and NestJS decorators only. oRPC, tRPC, Next file routes and server actions produce no `HANDLES_ROUTE`, so in a repository whose tests drive such code through Playwright or an HTTP client, X10 reports writes that the end-to-end tests do reach.
- **Symbol ids collide.** Symbol ids are `{module}#{name}`, and same-named non-exported top-level symbols in two files of one package share an id (a known engine issue). Test helpers such as `setup` and `createUser` collide often, which merges `CALLS` edges across test files and can credit a test in one file for a write reached from another. That is the precision-safe direction for X10 (more tests reach the write), but the facts then depend on unrelated files. A fixture covers it. X5 is affected only in its evidence: a collision merges the insert edges of same-named symbols into one `QUERIES` edge whose columns are a union and whose `insertComplete` is an AND, and X5 already unions across all insert edges of a table, so a collision neither adds nor hides a finding, but it changes the "N traced insert path(s)" count, and the evidence location is taken from the edge's `sourceRef` (the insert statement), not from the Symbol node, which may sit in another file.
