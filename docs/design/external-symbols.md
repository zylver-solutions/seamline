# External symbols: stub nodes for out-of-repo decorators, and the validator constraints they carry

- **Status:** Design-spec pass (v3 section 9 gate, aspirational-state section 5.3 admission test). Subordinate to `docs/design/v3.md`. Documentation only: no code accompanies this document. **Not admitted for implementation.** Leg 1 of the admission test (a cited instance) is not met for the decorator constraint read of X3 and X7, and nothing else in this document has a consumer without that read (section 2). The document is the reviewed design-spec pass (leg 3), so that a consumer that does cite an instance can land the work without a redesign.
- **Date:** 2026-10-18, revised 2026-10-19
- **Tracking:** third-party decorator support; this document is the design record.
- **Scope:** one capability. `extract-code-ts` represents a decorator imported from a package as a stub `Symbol` built from the importing file's own text, so that `DECORATED_WITH` has a node to point at, validator rule R1 in `infer-join` can recognise the decorator by package and export name, and the constraint arguments of a few validators become facts that X3 and X7 can read once the read is admitted. No new node kind, edge kind, extractor package, store adapter, ontology change or contract change. v3 section 9 does not list this item, so section 9 is not edited.

## 1. The problem

Take a repository with a table `users (id bigserial primary key, email varchar(64) not null)` and this file:

```ts
import { IsEmail, Length } from 'class-validator';

export class CreateUserDto {
  @IsEmail()
  @Length(1, 64)
  email!: string;
}
```

`seamline extract` reports PASS and emits the `CodeField` `CreateUserDto.email` with the prop `decorators = "IsEmail,Length"` (names only, no package, no arguments). `infer-join` joins the column to the field (`MAPS_TO_FIELD`). There is no `DECORATED_WITH` edge and no `VALIDATED_BY` edge. The result is identical whether or not `class-validator` is installed.

The cause is in `packages/extract-code-ts/src/relations.ts`. `decorate()` (line 133) resolves a decorator through the declarations this run walked, and the declaration of `IsEmail` lives in `node_modules`, which the extractor never reads. That is deliberate: dependencies are often absent from a fresh clone, reading them would make output depend on what is installed, and it would put third-party code in the extraction path. With no node to point at, the edge is not emitted, because inventing a node for a dependency would claim authority the extractor does not have. Three consequences follow.

1. **R1 cannot fire on extracted code.** Rule R1 (`packages/infer-join/src/validators.ts`, `infer.ts`) reads a `DECORATED_WITH` edge from a `CodeField`. Its unit tests pass because they build a graph by hand with a bare `Symbol` named `IsString`; no extractor produces such a node for a third-party decorator.
2. **X3 and X7 cannot see decorator constraints.** They read `required`, `minLength`, `maxLength`, `minimum`, `maximum` and `enum` off the validator `Symbol` (`packages/contradictions/src/props.ts`, `validatorConstraints`). No extractor sets those props on any `Symbol`, so a constraint written as `@Length(1, 64)` has no path to a detector.
3. **ORM corroboration cannot see third-party ORM decorators.** `ORM_DECORATORS` in `packages/infer-join/src/structure.ts` lists names such as `Column` and `PrimaryGeneratedColumn`, which only ever come from packages. This pass leaves that reader alone (section 5.5).

## 4. Decisions on the open questions

### 4.1 Kind: reuse `Symbol`, with `external: true`

A stub is a `Symbol` node. The alternative, a dedicated kind, was rejected.

- **No ontology or contract change.** A new kind changes `NODE_KINDS` in the frozen contract, `ontology/seamline.yaml`, `DEFAULT_SENSITIVITY`, every shipped export profile and the generated artifacts. The ontology's own description of `Symbol` already argues against splitting it by what it is, and puts the distinction in a prop.
- **The edge signatures already accept it.** `DECORATED_WITH` declares `[Symbol, Symbol]` and `[CodeField, Symbol]`; `isValidEdge` returns true for both with a stub as the destination. `ontology/lint.mjs` compares the YAML with the contract and neither changes, so it has nothing to flag. `Parameter` is not a `DECORATED_WITH` source, so a parameter decorator never produces a stub.
- **No invariant breaks.** Identity, lifecycle, reproducibility, facts-only and default-deny export are each checked in 4.2 to 4.5.

The stub:

| Field                  | Value                                                                                                            |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| id                     | `{repo}:Symbol:{specifier}#{exportName}` (4.2)                                                                   |
| `name`                 | the export name, as for an in-repo decorator                                                                     |
| `path`                 | the smallest repo-relative path of an importing file that carries an accepted edge to it in this run (4.3)       |
| provenance, confidence | `EXTRACTED`, 1                                                                                                   |
| sensitivity            | the `Symbol` default, `internal` (4.4)                                                                           |
| props                  | `external: true`, `package`, `exportName`, and `subpath` for a deep import only                                  |
| absent on purpose      | `symbolKind`, `library`, `sourceRef`, `untrusted`, and any per-statement fact such as import kind or local alias |

**What `external` means.** `external: true` means "not resolved in-repo by this run": the importing file's specifier met the conditions of 4.2 and no declaration of it was found among the files this run walked. It does not mean "outside the repository". A bundler, test-runner or package-manager alias (`npm:` and `workspace:` entries in a `package.json` dependency list, or a vite or jest alias) can make a bare-looking specifier name repository code, and the extractor reads none of those configurations (section 7). Consumers must read the prop as a statement about this run's resolution and never about the package.

`symbolKind` and `library` are absent because the importing file does not state them and resolving them would mean reading the package. Their absence also keeps stubs out of rule R2, which needs `symbolKind` of `function` or `variable`. Import kind and local alias are facts about one import statement, and a stub is shared by every file that imports the same export, so a shared node cannot hold them without the merge order deciding their value. The issue suggests recording import kind; this spec does not, for that reason.

The edge: `DECORATED_WITH` from the decorated `Symbol` (class, method) or `CodeField` (property, accessor) to the stub. `EXTRACTED`, confidence 1, `srcFile` the importing file, no `dstFile`, `sourceRef` the decorator's line, and the constraint props of section 5.3.

Consumers that enumerate `Symbol` nodes were audited. Rule R2 excludes stubs as above. X6 and X10 walk `CALLS` and `QUERIES`, which stubs do not have in this pass. `extract-change` links commits to symbols by name from git and never names a stub. ORM corroboration is handled in 5.5. The implementing change confirms by test that no other reader requires `symbolKind`.

### 4.2 Identity: `{repo}:Symbol:{specifier}#{exportName}`

The canonical name is `symbolCanonicalName(specifier, chain)`, the same assembly in-repo symbols use, so the form is `{module}#{chain}` with the module being the specifier as written and the chain the export name followed by any member names, joined with `.`.

Checked against the shipped code (each row run through `assertPathFree`, `makeNodeId` and `symbolName`):

| Canonical name                    | extractor `symbolId` (`assertPathFree`) | core `makeNodeId` | core `symbolName`                                         |
| --------------------------------- | --------------------------------------- | ----------------- | --------------------------------------------------------- |
| `class-validator#IsEmail`         | accepts                                 | accepts           | accepts                                                   |
| `@nestjs/common#Injectable`       | accepts                                 | accepts           | accepts                                                   |
| `zod/v4#z`                        | accepts                                 | accepts           | accepts                                                   |
| `class-validator#default`         | accepts                                 | accepts           | accepts                                                   |
| `class-validator#default.IsEmail` | accepts                                 | accepts           | accepts                                                   |
| `@scope/pkg#A.B.C`                | accepts                                 | accepts           | accepts                                                   |
| `socket.io#Server`                | accepts                                 | accepts           | rejects (a dotted last segment reads as a file extension) |
| `@scope/pkg.js#X`                 | rejects                                 | accepts           | rejects                                                   |
| `date-fns/esm/index.js#format`    | rejects                                 | accepts           | rejects                                                   |

Three rules follow.

1. Stub ids are built with `symbolCanonicalName` and `symbolId`, as in-repo ids are. The validating builder `symbolName` is never used for a stub; it would reject real package names such as `socket.io`.
2. `assertPathFree` throws, and a throw inside extraction turns the whole run into FAIL. The eligibility check below therefore runs first and without throwing: a specifier whose canonical name `assertPathFree` would reject yields a counted diagnostic and no stub. A file-style subpath (`date-fns/esm/index.js`) is refused for the same reason `assertModuleSpecifier` forbids an extension: a module specifier is not a file path.
3. **The export name is the imported name, never the local alias, and a member chain is part of the name.** There is one rule for each way a decorator can reach a package, and each spelling maps to exactly one id:

   | Spelling in the importing file                                                                                                 | Canonical name                                                                                        |
   | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
   | `import { IsEmail as Email } from 'class-validator'`, then `@Email()`                                                          | `class-validator#IsEmail`                                                                             |
   | `import * as v from 'class-validator'`, then `@v.IsEmail()`                                                                    | `class-validator#IsEmail`                                                                             |
   | `import v = require('class-validator')`, then `@v.IsEmail()`                                                                   | `class-validator#IsEmail` (the binding is the module object, so it is a namespace import)             |
   | `export { IsEmail } from 'class-validator'` in an in-repo barrel, imported from the barrel                                     | `class-validator#IsEmail`                                                                             |
   | `export * as ns from 'class-validator'` in an in-repo barrel, imported from the barrel, then `@ns.IsEmail()`                   | `class-validator#IsEmail` (a namespace re-export binds the module object, as a namespace import does) |
   | `export { default } from 'class-validator'` in an in-repo barrel, imported as `import V from './barrel'`, then `@V()`          | `class-validator#default`                                                                             |
   | `export { default as X } from 'class-validator'` in an in-repo barrel, imported as `import { X } from './barrel'`, then `@X()` | `class-validator#default`                                                                             |
   | `import { Foo } from 'pkg'`, then `@Foo.Bar()`                                                                                 | `pkg#Foo.Bar`                                                                                         |
   | `import * as ns from 'pkg'`, then `@ns.A.B()`                                                                                  | `pkg#A.B`                                                                                             |
   | `import IsEmail from 'class-validator'`, then `@IsEmail()`                                                                     | `class-validator#default`                                                                             |
   | `import { default as X } from 'class-validator'`, then `@X()`                                                                  | `class-validator#default`                                                                             |
   | `import v from 'class-validator'`, then `@v.IsEmail()` (default import plus member access)                                     | `class-validator#default.IsEmail`                                                                     |

   **A default import is its own node, `#default`, and is never merged with a named export of the same package.** Whether `import v from 'class-validator'` binds the module object (a CommonJS interop default under `esModuleInterop`) or an object that merely has a property of that name depends on how the package is built, which is what the extractor does not read. Keeping `default.IsEmail` apart from `IsEmail` is the same safe direction as for deep imports: R1's table (5.1) lists `class-validator#IsEmail` and not `class-validator#default.IsEmail`, so the interop spelling gets a stub and is not recognised, and a missed recognition can only remove a finding. Recognising it later is one table row with its own fixture and a cited instance.

   The chain may be any depth, joined with `.` as for in-repo chains, and member access on a barrel binding follows the same rule as on a direct import (`@X.IsEmail()` over `export { default as X } from 'class-validator'` gives `class-validator#default.IsEmail`). A decorator reaching the package through an in-repo barrel is followed through the barrel's own import and export declarations and stops at the first declaration whose specifier is external. The walk must not use the checker's fully resolved alias target, which ends in the package's declaration file when it is installed and in nothing when it is not.

   **Declined, with a counted diagnostic and no stub:** `export * from 'pkg'` (it cannot name the export without resolution); a bare namespace or `require` binding used as the decorator itself (`@v()` with `import * as v`, or with a binding made by `export * as ns from 'pkg'`); `const x = require('pkg')` and dynamic `import()` (not import declarations); a callee that is not an identifier or a plain property-access chain rooted at an import binding (`@ns['A']()`, `@make().X()`, `@(cond ? A : B)()`); and a type-only import.

**Deep imports key on the full specifier.** `zod/v4#z` and `zod#z` are two nodes. With no resolution into the package, whether the two are one export is unknown, and merging them would assert something the extractor does not know. Splitting is the safe direction: a split can only mean a validator is recognised under one specifier and not the other. ADR-0002 rejects import-site identity because it varies with which file was scanned; a stub does not, because every file importing the same specifier and export produces the same id. The `package` prop holds the package part (`zod`) and `subpath` the rest (`v4`), so consumers can tell them apart without parsing the id.

**A specifier produces a stub only if all five of these conditions hold.** Otherwise there is no stub, no edge and a counted diagnostic.

1. In-repo resolution found no declaration. In-repo declarations are tried first and always win.
2. It is a bare specifier: not relative, not absolute, no scheme (`node:`, `https:`, `npm:`, `jsr:`, `data:`), the package part uses npm package-name characters, any subpath segments use letters, digits and `._~@+-`, and its canonical name passes `assertPathFree`. Scheme-bearing specifiers can embed hosts or credentials and are never turned into ids.
3. The package part is not the `name` of any `package.json` in the repository.
4. It matches no `paths` pattern of the importing file's tsconfig, and when `baseUrl` is set its first segment names no entry directly under `baseUrl`. Those are in-repo aliases that happen to look like packages (`src/lib/x`).
5. The source of the edge is a `Symbol` or `CodeField`.

**Collision with an in-repo package is prevented by condition 3.** In-repo symbol ids are `{module}#{chain}` where the module is a `package.json` name, so a stub could equal an in-repo id only if the package part equalled an in-repo package name. The in-repo package names are every `name` in every `package.json` under the root outside `node_modules` and dot-directories, found by the same walk that discovers `tsconfig.json` files but ignoring the run's `exclude`: an excluded package is still in the repository. A narrowed run that excludes a workspace package must not mint a stub that overwrites that package's node from an earlier run. The set is a function of committed files. A second guard sits in the collector: a stub whose id is already held by a non-external node is dropped with a diagnostic, and nodes are never merged across the external boundary. `<root>`, the module name of files with no `package.json`, cannot match the grammar.

_Alternative considered:_ a marker in the id (`npm:class-validator#IsEmail`), which makes a collision impossible by construction because `:` cannot appear in a package name. It was not chosen because it departs from the `{package}#{exportName}` shape the issue proposes and readers of the graph will expect, and condition 3 plus the collector guard close the same hole. Ids are expensive to change later, so the review of this document should confirm that choice.

### 4.3 Authority and tombstoning

**Authority.** `extract-code-ts`, scope `code.ts`. `Symbol` is already in `PRODUCED_KINDS`, so the manifest's produced kinds and authoritative scope are unchanged, and no other extractor emits `Symbol` nodes with `external`. `collector.external(...)` is the wrong tool and is not used: it declares the kind of a node another extractor owns (`extract-data` owns `Table`) so an edge can be signature-checked without two extractors fighting over tombstones. Nobody owns a package symbol, so the node is emitted, not declared.

**Emission.** A stub is emitted only as the endpoint of an accepted `DECORATED_WITH` edge, never on its own. At the end of a run the collector drops any stub with no accepted inbound edge, so a rejected edge cannot leave an orphan. There is no `CONTAINS` edge from a file and no `EXPORTS` edge: a file imports a stub, it does not declare it. Every eligible decorator gets a stub, whether or not any rule recognises it. Recognition is a downstream decision (5.1), and the number of stubs is bounded by the distinct decorator exports a repository imports. A decorator that is declined (any condition of 4.2 fails, or the binding cannot be tied to an import) is reported as one counted diagnostic line per reason, sorted, and does not change the run's status, because a declined decorator can only remove a finding (5.4).

**`path`.** The smallest repo-relative path of an importing file that carries an accepted edge to the stub in this run. This is the rule `RouteHandler` already follows for a shared identity emitted by several files, and the collector's merge already keeps the smaller path, so the result does not depend on traversal order. For a stub, `path` is an evidence location and not a declaration site; consumers must not read it as one.

**Why not leave `path` off.** The store's sweep tombstones only nodes whose `path` matches the run's selector; a node with no path never matches. Checked against the shipped store (`packages/core/src/store/sqlite-store.ts`, `#sweepNodes`, lines 457-483), a path-less stub stays live forever after its last importer stops, which breaks "the graph can forget". The in-memory merge matches a path-less node by name instead, so the two implementations would also disagree about it. A stub with a `path` is swept identically by both, using the existing rule and nothing new.

**What the selector claims, and what it does not.** A stub is tombstoned when a PASS run whose selector covers its `path` does not re-emit it. That is the rule for in-repo symbols, and it has a limit that this section states instead of hiding: the store compares the selector with the single `path` the node carries, and the upsert overwrites that `path` on every re-emit (`sqlite-store.ts:254-260`), with the sweep matching `path` against the selector (line 473) and `last_seen_run <> run_id` (line 480). It does not compare the selector with every file that imports the stub. This document therefore does **not** claim that a narrowed run is safe for stubs.

The request behind this section asked that `code.ts`'s file selector not claim stubs. Read literally, that means sweeping stubs without the selector, which needs a scope entry with no selector over a kind of their own (an ontology change), and it would tombstone a stub in any run narrowed away from its importers, because those importers cannot re-emit it. Confining the sweep to `path` avoids that for the common narrowed run, the one whose selector excludes the importers' directories entirely. It does not avoid the run in the last row of this table.

| Scenario                                                                                                                                                                                       | Stub node                                                                                                                    |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| The last importing file stops using the export                                                                                                                                                 | tombstoned in that run                                                                                                       |
| The last importing file is deleted                                                                                                                                                             | tombstoned (its directory stays inside the selector)                                                                         |
| Two files import it and one stops (full run)                                                                                                                                                   | stays live; `path` moves to the remaining importer                                                                           |
| The decorator returns after a tombstone                                                                                                                                                        | resurrected, same id, `deletedAt` cleared                                                                                    |
| The run is FAIL or UNAVAILABLE                                                                                                                                                                 | untouched                                                                                                                    |
| A narrowed PASS run whose selector excludes every importer's directory                                                                                                                         | node untouched                                                                                                               |
| A narrowed PASS run whose selector covers the stub's `path` (`a/x.ts`, the smallest importer from the last run), where `a/x.ts` dropped the import and a live importer (`z/y.ts`) lies outside | **tombstoned although `z/y.ts` still imports it**; resurrected, same id, by the next run whose scope reads any live importer |

**Accepted behaviour for the last row.** In that run the stub is not re-emitted, because `z/y.ts` is not read, and its `path` is inside the selector, so the sweep tombstones it. Every inbound edge is then hidden from `edgesFrom`/`edgesTo` by `LIVE_ENDPOINTS` (`sqlite-store.ts:94-95`, applied at line 517) while an endpoint is tombstoned, including the edge from `z/y.ts`. The effect is a false negative that lasts until the next run that reads an importer: a finding that needed one of those edges is absent. It cannot create a finding. The next full run re-emits the stub and clears `deletedAt` (the resurrection row). This is accepted because the alternative below needs a store change this document may not make, and because a narrowed run is a local convenience whose absences are the same kind of absence as a decorator the extractor declined (5.4).

_Alternative considered:_ tombstone a stub only when it has no live inbound edge left after the run, so that liveness follows importers and not `path`. That makes the sweep a join between nodes and edges, a change to both sweeps (the SQLite adapter and `merge/tombstone.ts`, which `packages/core/src/store/sweep-agreement.test.ts` pins to bury the same facts), and section 7 rules out store changes. The edge sweep no longer stands in its way: since the edge-sweep change the edge from `z/y.ts` survives the narrowed run (next paragraph), so after the run the stub still has a live inbound edge and the join alone would keep it live. Revisit it if a consumer cannot accept the false-negative window.

**Edges follow the selector through their anchoring file.** The edge sweep (`#sweepEdges`, `sqlite-store.ts:429-448`, run at line 407) applies the run's selector to the file that anchors the edge, `src_file` and else `dst_file` (`edgeAnchorSql`, `scope-selector.ts:357-359`), whenever the claim names node kinds (`selectorNarrowsEdges`, `scope-selector.ts:366-368`), which `code.ts`'s claim does; an edge with no file never matches. `decorate()` already emits `DECORATED_WITH` with the decorated declaration's file as `srcFile` (`packages/extract-code-ts/src/relations.ts:140-141`); a stub has no file, so its inbound edge has no `dst_file` and anchors on `src_file`. A narrowed run therefore tombstones only the stub edges whose importing file is inside the selector and that it did not re-emit, and leaves the edges of importers outside the selector alone. That is the rule every `code.ts` edge follows since the edge-sweep change, and it is not changed here. The last row of the table is therefore a node-only effect: the `z/y.ts` edge stays live in the store, and it is hidden from `edgesFrom`/`edgesTo` only while its stub endpoint is tombstoned (`LIVE_ENDPOINTS`); `edgesByFile` (lines 528-536), the re-run invalidation read, still returns it, and no detector reads through it.

**Manifest.** `produces` is unchanged. `reads` names only the root `package.json` today, while `ModuleResolver` already reads nested ones; the implementing change widens `reads` to `**/package.json` so the declaration matches the read. No environment, network or memory change.

### 4.4 Export policy and sensitivity

Stubs take no special case. Their sensitivity is the `Symbol` default, `internal`, and a node-level value can only raise it (`sensitivity.ts`), so no stub is ever `public`. The `public` profile admits no `Symbol` and therefore no stub. `team` and `audit` admit them with all props. A profile declared in `seamline.config.json` releases a stub only if its `allow` lists the pair `[Symbol, internal]` (matched against the stub's effective sensitivity) and its `allowProvenance` includes `EXTRACTED`. The stub's props (`external`, `package`, `exportName`, `subpath`) are released only when `allowProps.Symbol` names them or is `'*'`; the `DECORATED_WITH` edge is released only when `allowEdges` lists it and both endpoints are released, and its props only when `allowEdgeProps.DECORATED_WITH` names them or is `'*'`. A file written by `seamline export` also carries a `props` object only when the profile's `allowFields` names `props`. See `docs/design/export-profile.md`. Default-deny is unchanged.

Why `internal` and not lower: the set of stubs is a dependency-usage inventory of the repository and can include private package names. It is derived from text the repository already contains, but this project makes no exception for names that look harmless.

The `untrusted` tag stays unset. `package` and `exportName` come from the repository's own import declarations, like any identifier in the code. Nothing from a dependency is read, so no third-party text enters a stub. They pass through the redactor like every other string. Specifiers with a scheme are refused (4.2), so a URL-shaped import cannot carry a credential into a node.

### 4.5 Determinism

A stub and its edge are a function of three inputs, all committed text: the importing file's source, the repository's `package.json` names, and its tsconfig `paths` and `baseUrl` (with the entries directly under `baseUrl`). They are never derived from `node_modules` contents, installed versions, lockfiles or the registry. The binding from a decorator identifier to its import declaration is a syntactic lookup, the same read `validation.ts` already uses for the `library` prop, and gives the same answer with the package installed, absent or at another version.

Output is sorted by the collector, no stub or edge body holds a time, and stub props are identical for every importer, so only `path` varies and it takes the smallest value. A file rename changes `path` and `srcFile` and no stub id (the importing file's own `File` id changes, as for any file). The extractor version is bumped when this lands. Whether the checker resolves an import of a workspace package through an installed link already changes in-repo edges today; it cannot change a stub, because such an import yields no stub either way (condition 3 of 4.2).

## 5. Validator recognition and constraint facts

### 5.1 What R1 recognises

R1 keeps its current behaviour for in-repo decorator symbols: recognition by name through `isValidatorDecorator`. For an external stub it requires a `(package, exportName)` match against a closed table and does not apply the name predicate to the stub's name.

The name predicate is a prefix regex with no word boundary and no export list (`VALIDATOR_DECORATOR_PATTERN`, `packages/infer-join/src/validators.ts:46`, beginning `Is[A-Z]`, `Not[A-Z]`, `Min`, `Max`, `Length`, ..., `Assert`, `Check`, `Required`, `Optional`). It accepts `Optional`, which is dependency injection in `@nestjs/common`, and `Check`, which is a database check constraint in `typeorm`; a stub for either would otherwise produce a false `VALIDATED_BY` edge. It is also wider than the package it would serve: `class-validator`'s decorator modules (`src/decorator/` in its repository) include none whose name begins `Assert`, `Check`, `Required` or `Optional`. This document therefore does not claim the predicate has no false positive inside `class-validator`; it replaces the predicate with an explicit list for stubs.

The table has one package in this pass. For the exact specifier `class-validator` (a deep import is not recognised), the recognised exports are exactly these 34:

`Allow`, `ArrayMaxSize`, `ArrayMinSize`, `ArrayNotEmpty`, `ArrayUnique`, `Contains`, `Equals`, `IsArray`, `IsBoolean`, `IsDate`, `IsDateString`, `IsDefined`, `IsEmail`, `IsEnum`, `IsIn`, `IsInt`, `IsNotEmpty`, `IsNumber`, `IsOptional`, `IsPositive`, `IsString`, `IsUUID`, `IsUrl`, `Length`, `Matches`, `Max`, `MaxLength`, `Min`, `MinLength`, `NotContains`, `NotEquals`, `Validate`, `ValidateIf`, `ValidateNested`.

Each name matches a decorator module re-exported by `src/decorator/decorators.ts` in the `class-validator` repository (checked against that file when this section was revised; the package is not installed here, so the published export list was not read). The list is a design decision and not an enumeration of the package: a rarely used export is missing from it, which is the safe direction, and another export is added as one row with a fixture. A fixture pins the accepted set, asserting that it equals this list exactly. Another library is added as a row with its own fixtures and a cited instance, not speculatively.

R1's output is unchanged: `VALIDATED_BY` from the `CodeField` to the stub, `INFERRED`, confidence 0.9, rule `validator-decorator`.

The extractor cannot import `infer-join`, so it keeps its own copy of the lowering table (5.3), as it does for `VALIDATION_LIBRARIES`. An integration test asserts that every export the extractor lowers is in the list above.

### 5.2 Where constraint values live: on the `DECORATED_WITH` edge

The values go on the edge, not on the stub and not on the `CodeField`.

- **Not the stub.** It is shared by every use. `Length(1, 64)` on one field and `Length(1, 255)` on another cannot both be props of `class-validator#Length`, and the merge order would pick the winner.
- **Not the `CodeField`.** `symbols.ts` already sets `required` there as a type-level fact (`!optional`), so a validator `required` would collide with it. The constraint is also a property of one application of the decorator, and the edge carries that application's line in `sourceRef`, which is what a finding quotes.
- **Not the `VALIDATED_BY` edge.** It is `INFERRED`. Constraint values on it would be inference feeding a gate.
- **The edge** is `EXTRACTED`, one per declaration and export, and disappears with the decorator.

The prop names are the dimension names `props.ts` already reads: `minLength`, `maxLength`, `minimum`, `maximum`, `enum`. Values are numbers, or for `enum` a sorted comma-joined string, which is the form `listProp` reads.

### 5.3 What is lowered

| Export of `class-validator` | Fact on the edge                                                                                |
| --------------------------- | ----------------------------------------------------------------------------------------------- |
| `Length(min, max?)`         | `minLength = min`, and `maxLength = max` when given                                             |
| `MinLength(min)`            | `minLength`                                                                                     |
| `MaxLength(max)`            | `maxLength`                                                                                     |
| `Min(n)`                    | `minimum`                                                                                       |
| `Max(n)`                    | `maximum`                                                                                       |
| `IsIn(values)`              | `enum`, when `values` is an array literal of string or number literals, none containing a comma |

Rules:

1. Literal arguments only: a numeric literal (with a leading minus), a string literal, or an array literal of those. An identifier, call, substituted template or spread means that fact is not stated; other facts of the same call still are. `Length(MIN, 64)` states `maxLength` only.
2. A validation-options argument is read only when it is an object literal. If it has an `each` property with any value other than `false`, or is not a literal, nothing is stated, because the bound then applies to elements and not to the field. `message` and `groups` are ignored.
3. A repeated application of one export on one declaration states only the values on which every application agrees.
4. `IsOptional`, `IsDefined`, `IsNotEmpty`, `ValidateIf` and `Allow` are recognised by R1 and state nothing. In particular no `required` fact is lowered (5.4).
5. Everything else in the family, including `IsEnum`, `IsPositive`, `Matches` and `Validate`, is recognised and states nothing, because the value is not a literal in the call or is not one of the five comparable dimensions.

These are EXTRACTED because they are literal arguments of an explicit call in the importing file, mapped one to one by a published table, with no checker inference and no read of the package. A wrong mapping is a bug the fixtures in section 6 catch; it is not a guess.

### 5.4 How X3 and X7 read them

The detectors gain a second source of validator constraints, the fields themselves. A new accessor in `props.ts` merges the dimension props of the live `DECORATED_WITH` edges from one `CodeField` to external stubs, reading the edges through `factEdgesFrom` and requiring `isFact` on each. For each dimension, exactly one distinct value across the field's edges means it is stated; two distinct values mean it is not stated. The accessor tags its result as decorator-derived, and the rules below apply only to that tag; the path for validator `Symbol` nodes that carry the props themselves is unchanged.

**What the column side can state today.** A shipped `Column` states exactly two constraint dimensions to `columnConstraints` (`packages/contradictions/src/props.ts:286-296`): `maxLength`, from `char`, `varchar` and `bit` types (`packages/extract-data/src/normalize-type.ts:251-260`, emitted at `emit.ts:167`), and `required`, from `nullable` (`props.ts:289`). No extractor sets `minLength`, `minimum`, `maximum` or `enum` on a `Column`: `CHECK` text goes to the raw `checkConstraint` prop, which `columnConstraints` does not read. So `Min`, `Max`, `IsIn` and `MinLength` are lowered by 5.3 for the day a column-side extractor states those dimensions (a separate capability that needs its own cited instance); until then X3 cannot compare them and the X7 control below cannot pass for them. Only `maxLength` can meet a column today.

- **X3** walks `COLUMN_TO_FIELD` (`MAPS_TO_FIELD`), and for each field compares the column's constraints with the field's on dimensions both state. The finding has `left` the `Column`, `right` the `CodeField`, `viaPath` `['MAPS_TO_FIELD']`, and the confidence of that one join hop. `right` is the field and not a stub because the constraint set belongs to the field, and a stub shared by every field would give different columns the same finding identity. The right-hand fact quotes the edge's `sourceRef`.
  - **Direction.** X3 as shipped fires on any inequality (`x3-constraint.ts:47`), and before this change it could never fire on extracted code, because no extractor sets these props on a code node. This is the first time its equality rule meets real data, and a validator stricter than its column is a deliberate and safe choice: `@MaxLength(50)` over `varchar(255)` is not a defect. For decorator-derived sets X3 reports only a validator **looser** than the column, that is, one that accepts a value the column rejects: `maxLength` above the column's; `minLength` below the column's; `maximum` above the column's; `minimum` below the column's; `enum` where the validator's set is not a subset of the column's. A stricter validator (`maxLength` below the column's, a subset enum) is silent, and so is equality. Rows for `minLength`, `minimum`, `maximum` and `enum` are reachable only when a column states them (above).
  - **Units are a limit, not a feature.** The comparison is nominal: it compares two numbers and not what each side counts. JavaScript string length counts UTF-16 code units; a PostgreSQL or MySQL `varchar(n)` counts characters; SQL Server `varchar(n)` counts bytes; and two of the repositories examined in section 3 (row B) report that a validator `@MaxLength` and a `varchar` of the same number disagree about what one character is. Equal numbers therefore do not prove equal acceptance, and unequal numbers do not prove a difference. The finding's claim text says the comparison is nominal. This design does not model units, and it does not claim to catch the defect in row B.
- **X7** reports only the arm where the validator enforces a value the column does not state. The other arm, where the column enforces something the validator does not, is not reported for decorator-derived sets. A missing captured value cannot be told apart from a bound enforced by a decorator this pass lowers incompletely (`Matches`, `IsPositive`, `Validate`) or by one outside the table, so absence would be masquerading as a fact. Proving a field's decorator set closed needs per-decorator coverage metadata that has no cited instance.
  - **Why the shipped control is vacuous here.** X7's control 3 ("the column states at least one constraint of its own", `x7-validator-divergence.ts:49`) is satisfied by `required`, which `columnConstraints` states for every column whose nullability is known (`props.ts:289`). So `dbConstraints.size > 0` holds for essentially every column, and `@MaxLength(n)` over a `text` column, `@Min(0)` over an `integer` column with no `CHECK` and `@Length(3, 64)` over `varchar(64)` are how nearly every application is written. Reporting them would read column silence as a fact, which is the gap-not-contradiction pattern v3 rejects.
  - **The control for decorator-derived sets.** The column must state a constraint in the **same dimension family** as the one the validator states, and `required` never counts. The families are: a length bound (`maxLength`, `minLength`); a range (`minimum`, `maximum`); an enum (`enum`). X7 reports the validator's dimension `d` only when the column states a different dimension of `d`'s family and is silent on `d`. A column that states `d` itself belongs to X3. Two explicit exclusions apply on top of the family rule, because the rule alone does not give the intended result:
    - **`minLength` is never reported by X7 for decorator-derived sets.** A column's length bound (`varchar(n)`, `char(n)`) states only an upper bound, so the family rule alone would be satisfied for every `@MinLength(m)` or `@Length(m, n)` over a sized column, at X7's `high` severity. A validator minimum over `varchar(n)` is normal and not a defect: `@Length(3, 64)` over `varchar(64)` is the most common DTO and column pairing, and it is a must-not-fire fixture (section 6).
    - **The `enum` arm is dead by construction.** The enum family has a single member, so no column can state "a different dimension of the family" while being silent on `enum`. X7 reports nothing from `IsIn`. A disagreement between a validator enum and a column enum is X3's, once a column states `enum`.
  - **Consequence of those exclusions.** What remains reachable under the rule is the range family (a validator `minimum` against a column that states only `maximum`, or the reverse) and a validator `maxLength` against a column that states only `minLength`. No shipped extractor states `minimum`, `maximum` or `minLength` on a `Column` (above). So with shipped extractors the X7 read reports nothing from decorator-derived sets, and that is a consequence of three explicit facts: `minLength` is excluded, the `enum` arm is dead, and the remaining dimensions need a column dimension that no extractor states. It is not a property of the family control, which on its own would fire on `@Length(3, 64)` over `varchar(64)`. The expected finding volume on a repository whose columns come from the shipped extractors is therefore zero. Once a column-side extractor states `minimum`, `maximum` or `minLength`, the volume is unmeasured: the landing change must report the count of fires and of decorated fields compared, and a nonzero count needs a reviewed triage before the read is enabled. The range pairing in particular is unproven for the same reason `minLength` is excluded: a validator `@Max(100)` over a column that states only `minimum: 0` adds a bound in a direction the column does not state, which may be as normal as `@Length(3, 64)` over `varchar(64)`. The range Fires fixture in section 6 pins the rule as written and does not settle that it reports defects; the range arm needs its own cited instance before it is enabled. The read is specified for that day and is not admitted in any case (section 2).
- **The `required` dimension is not read** from decorator-derived sets by either detector. `columnConstraints` states `required` for every `NOT NULL` column without looking at `hasDefault`, so a decorator-derived `required: false` from `@IsOptional()` would flag every optional DTO field over a `NOT NULL` column that has a default. Optionality disagreement between a column and a code field is X1's subject. Taking `required` from decorators needs a detector change with its own corpus evidence, and is a follow-up.

**What "no inference feeds a gate" means here.** Every value a detector compares is a prop on a node or edge with `EXTRACTED` provenance. The path to those values does include one INFERRED hop, the `MAPS_TO_FIELD` join. `packages/contradictions/src/graph.ts` rule 2 (lines 12-19) allows exactly that: an INFERRED edge may join two facts, its confidence is carried into the finding and caps severity (`detector.ts`), and an `LLM_SUGGESTED` edge is dropped. So the accurate claim is narrower than "no inference": no INFERRED value is compared, and the one inferred hop is the join every field-level detector already uses. Aspirational-state 6A.4 ("Contradiction detection reads facts only") is read the same way `graph.ts` reads it; this design adds no new use of inference and does not rely on a stricter reading than the shipped one. R1's `VALIDATED_BY` edge is not on the path, so its 0.9 does not multiply in and its absence silences nothing. The existing `COLUMN_TO_VALIDATOR` route still reaches a stub, but a stub has no dimension props: by reading, X3 skips it (`x3-constraint.ts:41`) and X7 treats it as not enumerated (`validatorIsEnumerated`, `props.ts:316-318`, used at `x7-validator-divergence.ts:52`), so nothing is reported twice; the landing change adds a fixture that pins this. The required scopes are unchanged (`SCOPE_DATA`, `SCOPE_CODE`, `SCOPE_JOIN`), so a `code.ts` scope that is not PASS yields UNKNOWN as before. A decorator the extractor could not attribute yields no edge, so a missing stub can only remove a finding and never create one.

### 5.5 What does not change

- **ORM corroboration** (`corroborateColumnField`) skips nodes with `external: true`. Without that, landing stubs would silently start scoring `@Column()` and `@Field()` from any package by name alone, changing join scores on every repository with decorators. Giving that reader a `(package, exportName)` table is a separate capability and needs its own cited instance, owner and design-spec pass.
- **Rule R2** is untouched: stubs carry no `symbolKind`.
- **`CodeField.decorators`** keeps its current meaning (sorted names).
- **Nullability** stays with X1.

## 7. Non-goals

- **No resolution into `node_modules`.** No file under it is read, no `package.json` of a dependency, no declaration file. A stub states the specifier and export name the importing file wrote and nothing about what the package contains. Package-manager aliases and bundler aliases can make a specifier name something else, and a stub never claims otherwise (4.1, "What `external` means").
- **No version-specific behaviour.** No installed version, dependency range or lockfile is read. A major version that renames an export produces an unrecognised stub and no fact, not a branch.
- **No new extractor.** The change is inside `extract-code-ts`, `infer-join` and two detectors.
- **No stubs for other edges.** `CALLS` into a package, `EXTENDS` or `IMPLEMENTS` of a library class, `USES_TYPE` of a library type and a `File` to package `IMPORTS` edge each need their own consumer. A package dependency graph is a different capability.
- **No libraries beyond `class-validator`** for recognition or lowering, and no composed or wrapped decorators (`applyDecorators`, a local `IsFoo` that calls library decorators).
- **No `required` fact from decorators, no X7 absence arm, no ORM decorator scoring** (5.4, 5.5).
- **No unit modelling.** Lengths are compared nominally (5.4); a unit-aware comparison is a different capability with a different consumer.
