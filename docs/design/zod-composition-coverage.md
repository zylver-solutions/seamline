# Static Zod composition coverage

This repair implements the existing v3 scope and fact invariants for the Zod composition coverage repair. The named consumers are the field-lineage join and contradiction runners that compare extracted contract properties. It does not introduce new ontology kinds, arbitrary helper evaluation or a hosted alignment service.

Same-file constant literal shape composition follows JavaScript source order, including replacement of required fields by optional fields. Known literal spreads and `.extend()` use the same merge semantics. Paths remain source locators, while contract/property natural keys remain unchanged.

Unsupported imported/dynamic/mutable/cyclic shapes, computed keys and helper wrappers produce a diagnostic and degrade per schema, as described in "Degradation per schema" below; they no longer fail the scope. Unresolved requiredness is omitted, never asserted as true. An unknown spread can replace any earlier property, so the shape is no longer known and the contract is withheld. Mutated constant objects, aliases of the same object and constant schema/literal values escaping to unmodeled calls, mutable/local/destructured aliases or return values are conservatively excluded from resolution. Known immutable Zod validation reads (`parse`/`safeParse` and async variants) do not escape their schema receiver; type-only references do not count as runtime aliases. Unsupported wrappers stay unknown after later optional modifiers; array wrappers reset the outer presence obligation. No analyzed source is executed.

Lowering has a fixed deterministic budget of 100,000 recursive operations per schema, in addition to the existing depth bound. Exhaustion emits `ZOD_UNSUPPORTED_WORK_LIMIT` and withholds that schema. Candidate discovery visits each syntax node once and stops on a Zod reference, so repeated alias graphs cannot cause unbounded expansion.

The supported facts describe statically lowered schema definitions. Unmodeled refinements, transforms, cross-field rules and imported enum members do not certify runtime acceptance or complete consumer behavior. Those require separate supported extraction and execution evidence. Empty complete shapes still yield a contract, distinct from unavailable extraction. When the optional TypeScript peer is unavailable, a Zod-only extraction stays UNAVAILABLE with an explicit diagnostic; successful JSON extraction in a mixed scope cannot turn the skipped TypeScript coverage into PASS.

Syntax parse recovery, unmodeled lazy blocks and prototype-setting literal keys withhold conservatively; a partial mask leaves requiredness unknown. Acceptance includes positive composition, aligned literal controls, unsupported forms, override optionality, reproducible replay, file-rename stable IDs and a representative real-source read. Changed behavior is bound to extract-contracts version 0.0.2 (composition) and 0.0.3 (degradation per schema). Existing ontology, provenance, export and sandbox contracts stay intact.

## Degradation per schema

Evidence: on six public repositories every one of these diagnostics turned the whole `contracts` scope into FAIL, which left `infer-join` UNAVAILABLE and the contract detectors UNKNOWN, so nothing was reported on real code. A scope that fails on any one unreadable schema certifies nothing; a scope that quietly drops that schema certifies a falsehood. The rule below keeps both properties: an unsupported construct makes exactly the facts it hides unknown, never absent and never defaulted.

This is a fix to an existing extractor, bound to the same named consumers (the field-lineage join and the contradiction runners). It adds no ontology kind and no capability, and `packages/ontology/src/contract.ts` is untouched.

**What the detectors may and may not assume.** Only X9 reasons from the absence of a `contracts` fact: a served route (code scope) with no declared `Operation` (`x9-contract-drift.ts`, direction 2). X4 reasons from the absence of a producer for a contract's response properties, but only response properties, which `propertyDirection` derives from an OpenAPI operation-body pointer (`/paths/{path}/{method}/responses/`, `/paths/{path}/{method}/requestBody`). The patterns are anchored at `/paths/`, so a Zod pointer never matches, not even one through a property that is named `responses` or `requestBody`. X1, X2 and X6 compare two present facts. X3, X5, X7, X8 and X10 do not require the scope. Zod-derived facts never produce an `Operation` or a `RouteHandler` (`extractZod` returns no operations), so a Zod file the run could not read cannot hide an operation. Operations therefore come only from OpenAPI documents. A document named as a contract (`openapi*`, `swagger*`, `*.schema.json`) or listed explicitly keeps its all-or-nothing behavior: if it cannot be read, the scope is FAIL. A document found by discovery under any other name that cannot be read is not a failure. One that is too large leaves the claim whatever it holds. Every document that does not parse leaves the claim, even when truncation removes its contract header, so the contract and operations an earlier run took from it are neither re-observed nor buried. YAML parsing checks the document error collection before converting it to values. Syntax errors, including recoverable syntax errors, take the unread path; warning-only documents still read, and the alias-expansion bound remains 100. Multiple-document streams are refused, including when a later document is malformed. Diagnostics release only parser codes and offsets or generic conversion codes, never source frames or input values. Strict named or explicitly listed malformed documents fail the scope; other discovered malformed documents degrade per file. `GraphView.scopeStatus` cannot see selectors. Every emitted Contract and Operation therefore carries `unreadStructuredDocuments`, the measured count of unread structured-document paths, including zero. X9 uses the detector `unknownWhen` gate to report UNKNOWN when the count is missing, invalid or nonzero; direct `detect` calls refuse the same conclusion. A profile that withholds the count cannot turn UNKNOWN into a finding. Before projection, `profileView` also preserves incomplete contracts coverage as UNAVAILABLE, so hiding the whole current witness cannot expose stale operations stamped with zero. No hidden count or path is released. Retained nodes from an older partial run can conservatively keep X9 UNKNOWN until they are re-observed or swept. The shared UNKNOWN hook is brought forward from row D of `real-world-inputs.md`; it changes no frozen contract.

An unrecognised modifier may change a value's type, make it optional or nullable, or (`omit`, `pick`, `merge`, `pipe`, `transform`) reshape it. On a scalar only that property's facets are at stake, so it loses `type`, `format`, `typeCategory`, `required`, `nullable`, `isArray` and `hasDefault`. On anything with nested properties the property set is at stake, so it is shape-level, and so is a `.catch(...)` there. A masked `partial` keeps the property set and loses only `required`. `z.nativeEnum` no longer declares `type: string`, since native enums may be numeric.

**What a missing facet means.** A prop that is absent from a `SchemaProperty` is not extracted. It is never a declared `false`, `'unknown'` or `''`. The one reader that treated a missing `nullable` as a value, X1's presence fallback ("`required` stands in for non-null"), is removed: `required` says the key is present, not that the value cannot be null, and the extractor states `nullable` whenever it can. A union or intersection with a branch whose facets could not be read loses `type`, `nullable` and `required` for the same reason: the branch it could not read may be a `.nullable()`, an `.optional()` or another type, and recomputing the facets from the branches that were read would state `nullable: false` from nothing. So does a union whose branches are never enumerated because its argument is not an array literal (`z.union(OPTIONS)`, `z.discriminatedUnion('kind', OPTIONS)`, `z.union(make())`): no branch is read at all, which is not the same as a union of nothing. A `.optional()` on the union itself is still read and stated. The same holds one construct over. `z.literal(null)` is a null (`type: null`, `nullable: true`), and a `z.literal` whose argument is not read as a scalar (a binding, a call, or the Zod 4 list form `z.literal(['a', null])`) leaves `nullable` unknown, as does a union or intersection that holds one. An intersection takes `nullable` from its own schema and not from its branches, so one with any branch that is, or may be, null (a `.nullable()`, a `z.null()`, a union with a null branch, a branch whose null-ness is unknown) leaves `nullable` unknown rather than stating `false`; the full fix, null only if every branch accepts it, is in the shared schema walk and changes how OpenAPI `allOf` is read, so it is left for its own change. A union accepts what any branch accepts, so a union with an optional branch (`z.union([z.string().optional(), z.number()])`) states `required: false`. An intersection with a required branch states `required: true`; one whose branches are all optional states nothing, because Zod 3.25 and 4.0 to 4.3 accept a missing key there and Zod 4.4.0 onwards rejects it even for two `.optional()`. An array of such a union, written `z.array(...)` or `.array()`, states that it is an array and leaves what it holds unknown, so its `type` and `typeCategory` are absent too.

`nullable` on a Zod property means the schema accepts `null` as input, which is what X1 needs: a NULL from the database must pass the contract without failing it. It is not the output type of `z.infer`. So a `.catch(v)`, which turns any value that fails to parse into `v`, and a `z.coerce.*`, which turns a null into `'null'`, `0`, the epoch or `false`, leave `nullable` unknown; the output type they produce is still read. A catch states `required: false` only when its receiver already accepts a missing key (`.optional()`, `.nullish()`, `.default(v)`, or an `.optional()` written after the catch). A bare catch leaves `required` unknown because of Zod 4.4.0 to 4.4.2. From 4.4.0 an object consults each property's `optin` (before 4.4.0 it did not), and a catch takes its `optin` from its receiver until 4.4.3 sets it on the catch itself; so on those three releases `z.string().catch('x')` rejects a missing key, while Zod 3.25, 4.0 to 4.3 and 4.4.3 onwards accept it. The same object-parser change at 4.4.0 is why the other presence splits below begin there. They are published patch releases a project can be pinned to, so the facet is left unread, like the others below whose answer depends on the release. A union or an intersection that holds a bare catch as a branch reads it as a branch whose presence is unread. A coercion leaves `required` unknown: on Zod 3.25 and 4.0 to 4.3 `z.coerce.string()` accepts a missing key and `z.coerce.number()` does not, and Zod 4.4.0 onwards rejects it for both, so the facet is left unread because the releases differ. A coercion is `z.coerce.<base>()` and also the same thing spelled as a constructor option, `z.<base>({ coerce: true })` for `string`, `number`, `boolean`, `date` and `bigint`; an options argument that is not read (a binding, a call, a spread, a computed key, a shorthand `coerce`) may switch it on and is treated as if it did, while no argument, a string message and an object literal without `coerce` (or with a literal `coerce: false`) change nothing. A `z.literal` whose argument is not read leaves `required` unknown too, since `z.literal(undefined)` and the Zod 4 list form `z.literal(['a', undefined])` accept a missing key on Zod 3.25 (`zod/v4` for the list form) and on 4.0 to 4.3, and reject it from 4.4.0. So do `z.undefined()` and `z.void()` and a union that holds one: Zod 3.25 and 4.0 to 4.3 accept a missing key for them and Zod 4.4.0 onwards rejects it, while a null is rejected on all of them and `nullable` is still read. A presence modifier after any of these (`.optional()`, `.nullish()`, `.default(v)`) is read, because it accepts a missing key on every release. An intersection of branches that are all optional leaves `required` unknown: Zod 3.25 accepts a missing key only when the values the branches parse it to agree (`.optional()` yields `undefined`, `.default(v)` and `.catch(v)` yield `v`, and two that differ are rejected as unmergeable), and Zod 4.4.0 onwards rejects it even for two `.optional()`. An intersection states an object type only when every branch is an object: the shared schema walk reads a bare `allOf` as an object, and for `z.intersection(z.string(), z.string())` that would state a type nobody read, which X2 would compare with a `text` column. A `.catch(...)` on a receiver with nested properties is shape-level like any modifier there, because it swallows a failure at any depth and no nested `nullable`, `required` or `type` is then a fact. A marker a chain link sets on a union survives the walk's collapse of a union with one non-null branch (`z.union([z.literal('a')]).catch(null)`).

**The claim.** A run that reads every file to the end keeps the whole-scope claim. When some file is not vouched for (a withheld schema, a name collision, a parse failure, a file too large to read), the `contracts` claim carries a `selector` naming the contract sources that are, so a contract an earlier run read from the other files is neither emitted nor buried (invariant 2). A directory with no unvouched file beneath it is named whole (`dir/**`), so a file deleted from it is still forgotten; a mixed directory is named file by file, so a file deleted from it stays until a run vouches for the directory again. That is the conservative direction: stale, never falsely absent. A directory deleted outright is likewise not named. The list is sorted by code unit. A path the selector syntax cannot write is left out. A source is certain when it is a document read to the end or a TypeScript file with at least one readable contract; a file whose only contracts were withheld for a name collision is not one, so a scope with nothing but those is UNAVAILABLE. The scope is PASS with at least one certain source, UNAVAILABLE with none, and FAIL if an OpenAPI or JSON document named as a contract failed or the optional TypeScript peer is missing.

**Facts from a withheld file stay live.** A file that leaves the claim keeps what an earlier run read from it: its contracts, properties and edges are not tombstoned and their `lastSeenRun` does not advance, until a run reads the file again. A finding can therefore rest on a fact from a version of the file that no longer exists, for example a property that was `shippedAt: z.string().datetime()` when the file last parsed and is now `.nullable()` in a file the extractor cannot read. That is the price of "stale, never falsely absent" (the alternative, burying what could not be re-read, makes a transient edit retract real facts), and `extract-code-ts` makes the same trade. Detectors do not look at `lastSeenRun`, so nothing at the finding says the fact was not re-observed. The signal is the narrowed-claim notice below, which says how many files were not read, not which findings rest on them.

**The narrowed-claim notice.** `GraphView.scopeStatus` is keyed by scope alone and cannot see a selector, so a `contracts` scope that PASSed on a narrowed claim looks the same to a detector as one that read everything. The extractor therefore says it in its result: a `CONTRACTS_PARTIAL_COVERAGE: <n> file(s) ...` diagnostic beside a claim that carries a selector. `seamline check` and `seamline why` read it from the latest run (`narrowedClaims` in `@seamline/core`), qualify a clean result ("among the facts it read") and print a partial coverage notice naming the count; `--json` carries `narrowedClaims` when there is one and omits it when there is not. The MCP `contradictions` tool adds the same notice. The notice is deliberately outside the export profile, like `unknown`, which lists scope, status and extractor whatever kinds the profile releases: an integer, the scope name and the extractor name cross, and the diagnostic's own text never does. A reader told "none" has to be told what "none" rests on, so the notice is not withheld together with the contract kinds it is about, and a test pins this under a profile that releases no contract kind. The count is the one the extractor reported, and a test carries a real extractor result through the store into `narrowedClaims` and compares it with the files the claim leaves out, so the diagnostic text and the pattern that reads it cannot drift apart unnoticed. `outcome` and the exit code do not change: this qualifies a clean, it does not turn it into UNKNOWN. The `code.ts` claim is narrowed the same way (files in no loaded tsconfig project) but reports it in a different diagnostic and is not covered yet.

**Name collisions.** A contract's identity is `{repo}:Contract:{name}` and carries no path, so two declarations of one name are one node and their properties would be linked to whichever came first. Every declaration of a colliding name is withheld, with its properties, and its file leaves the claim. A Zod declaration whose shape could not be read still holds its name. Nothing invents a path-based identity.

**Known limits.** `infer-join` still sees only the contracts that were emitted, so a withheld schema is not a candidate it can score or tie-break against; inferred joins are already priced by confidence. Every discovered JSON or YAML parse failure leaves that file outside the claim: truncated text cannot prove that a prior contract vanished. This also narrows coverage for config files with comments. The claims-nothing selector is `**/*,!**/*`, an empty set even for explicitly supplied paths under discovery-excluded directories. Recognising `refine`, `brand` and similar refinements as transparent to type, optionality and nullability, and `z.any()` or `z.unknown()` as opaque leaves, would recover facets and is left for a later pass with its own named consumer.

## Checking the facets against real Zod

`scripts/zod-oracle.mjs` is a manual check of the stated `nullable` and `required` facets against the real library. It generates seeded, nested Zod expressions (atoms, `.catch`, `.default`, `.nullish`, `.brand`, `.pipe`, `z.coerce.*`, unions, intersections, containers, the Zod 4 list `z.literal`), judges each one with a hand-written truth table and with `safeParse({ p: null })` and `safeParse({})` on the real Zod, fails if the table and Zod disagree (on a release below 4.4.0, see below), and then counts four cases for the extractor: `nullable: false` while Zod accepts null, `nullable: true` while it rejects null, `required: false` while it rejects a missing key, and `required: true` while it accepts one. A facet the extractor leaves unread is never counted. All four are expected to be zero, and the exit status is 1 when any is not, when the extractor's status is not PASS, or when no property states a facet (an extractor that returned UNAVAILABLE states nothing, and a run that checked nothing must not look like a pass). It checks the property's own null-ness and presence only, not nested properties, `type` or `format`.

Zod is not a dependency of this repository, and the script is not part of `pnpm verify`. It runs only when `ZOD_ORACLE_DIR` points at an external install, and it needs a build (`./node_modules/.bin/tsc --build`) so that `packages/extract-contracts/dist` exists:

```sh
mkdir /tmp/zod-oracle && cd /tmp/zod-oracle && npm init -y && npm install zod@3.25.76
cd <repository root>
ZOD_ORACLE_DIR=/tmp/zod-oracle node scripts/zod-oracle.mjs --zod 3 --seed 1
ZOD_ORACLE_DIR=/tmp/zod-oracle node scripts/zod-oracle.mjs --zod 4 --seed 11
```

`--zod 4` judges against `zod/v4` of the same install, `--count` sets the number of expressions (3000 by default), and `--extractor <path>` compares another revision of the extractor (a `.ts` entry needs `node --experimental-strip-types`). Seeds 1 to 5 and 21 to 23 on Zod 3 and 11 and 12 on Zod 4 are the ones this was last run on against 3.25.76, with all four counts zero and no SYM mismatch. The truth table follows Zod 3.25 and Zod up to 4.3; the extractor states presence only where the releases agree. Presence moved in Zod 4.4.0: from there a missing key is rejected for `z.any()`, `z.unknown()`, `z.undefined()`, `z.void()`, a `z.literal` of `undefined`, `z.coerce.string()`, `z.coerce.boolean()` and the two options spelled `{ coerce: true }`, for an intersection of optional branches, and for the expressions that hold one, and on 4.4.0 to 4.4.2 only also for a bare `.catch(...)` (4.4.3 accepts it again). So the script compares the table with the library only when the installed Zod is below 4.4.0, where they agree, and from 4.4.0 prints the mismatches as information ("table describes presence before 4.4.0; not compared") and lets the exit status be the four counts and the extractor status alone.

The four counts are zero, the extractor status is PASS and the exit status is 0 on 3.22.4, 3.25.76 (`zod` and `zod/v4`), 4.0.0, 4.3.6, 4.4.0, 4.4.1, 4.4.2, 4.4.3, 4.5.0 and 4.6.7, at seeds 1 and 2 on `--zod 3` and 11 and 12 on `--zod 4` (not on 3.22.4, which has no `zod/v4`). Before a bare catch left presence unread, `--zod 3` reported 56 `required: false` hits at seeds 1 and 2 while Zod rejects a missing key on 4.4.0, 4.4.1 and 4.4.2 (0 on every other release), every one containing a `.catch(`; that is why the oracle is run across the releases a project might be pinned to, and not only on the one or two a maintainer has installed.
