# Evidence boundaries for X1 and X2

Status (2026-11-10): implemented in 0.1.0 (detectors: `packages/contradictions/src/detectors/x1-nullability.ts` and `x2-type.ts`; join eligibility: `packages/infer-join/src/facets.ts`). Subordinate to [v3](v3.md).

This narrows v3 section 5 after the development-corpus precision report: 101 findings in 56 labelled clusters, zero true positives. (That report is an earlier development measurement that is not retained in this repository, so the figures cannot be checked here.) It does not lower the sealed precision bar, supply new labels, or claim that a smaller finding population has passed evaluation.

X1 compares a column that states it permits NULL with a joined response property that states it excludes null. Direction must be an explicit fact or derive from the anchored OpenAPI response pointer. A name containing Response is insufficient. Requests may legitimately validate more strictly than storage, and standalone schema direction remains unknown. An inline response property is supported; `$ref` component direction is not inferred from usage.

An actual literal property schema `{}` or Boolean `true` permits null in the default OpenAPI 3.1 dialect. The contract producer records `nullable: true` for those bounded cases, independently of required presence or unknown type. This policy accepts canonical `3.1.<patch>` strings and the absent or exact `https://spec.openapis.org/oas/3.1/dialect/base` dialect; an independent schema root may state that exact dialect over the document default. Opaque context or an exceeded emission-depth bound leaves nullable unextracted. It never becomes a false non-null assertion. See [OpenAPI schema dialects](https://spec.openapis.org/oas/v3.1.2.html#specifying-schema-dialects), [OpenAPI Boolean schema representations](https://spec.openapis.org/oas/v3.1.2.html#schema-object) and [Boolean JSON Schema semantics](https://json-schema.org/draft/2020-12/json-schema-core#section-4.3.2).

This correction uses only the original literal declaration, not a schema produced by reference resolution, union collapse, or a failure fallback. It propagates positive authority only through the finite wrapper keys `type`, `properties`, `required`, `items`, `$defs`, `definitions`, `$id`, `$schema`, `title`, and `description`, with basic value-shape checks. An unsupported sibling constraint makes the subtree opaque before its own properties are emitted; nested `$schema` declarations stay opaque, while `$id` alone inherits. Excluded annotations and embedded dialect overrides are conservative limits, not evidence that those schemas reject null. Other formats, noncanonical versions and nonliteral schemas retain their previous handling; this is not a general nullability solver or an endorsement of unsupported cases. Producer and real CLI regressions retain a typed non-null positive, nullable required/optional controls, request-only UNKNOWN, and an opaque-dialect UNKNOWN with live mappings. Authored regressions do not supply external precision or recall.

The shipped code extractor emits generic CodeField declarations, including separate optional and nullable facts. Presence is not nullability: `value: string | null` is present and nullable. Neither a name, a path, an inferred mapping, nor a nearby database query proves that a declaration is a stored row or an insert shape. X1's field comparisons and X2's column-to-field and field-to-property comparisons are withheld until that role is established by authoritative facts. No fixture-only role property or new producer is introduced.

An optional request is not an insert obligation. PATCH, backend enrichment and runtime defaults can supply values absent from a request. Even `hasDefault: false` is insufficient when schema sources went unread: the data extractor withholds `defaultSite` in that case (`defaultSite` in `packages/extract-data/src/emit.ts`). X1 therefore withholds the request-omission branch too. Restoring it requires source-supported insert and completeness semantics plus applicable default and trigger controls, not a name-based guess.

X2 retains column-to-contract comparisons and its existing specific representation compatibility rules. It does not equate every string with every numeric or structured value. Unknown types remain unmeasured. Automatic name-based joins require nonempty convention/plural-normalized container equality. Affix stripping, fuzzy similarity, field-name equality, structural corroboration and configurable score thresholds cannot substitute for that gate. This intentionally withholds joins such as `Post` to `PostRow` or `Resume` to `ResumeVersion`; naming alone does not prove those shapes represent the same value. Validator subject normalization removes validation-only suffixes such as `Schema` and a `validate` prefix, while retaining shape words such as `Create`, `Row`, `Input` and `Response`. Decorator targets follow the same path eligibility policy as other endpoints. Explicit authoritative mapping producers remain future work.

If no supported comparison has the required stated facts, the detector reports `VALUE_ROLE_UNOBSERVED` as UNKNOWN. If at least one comparison is observable, it can still report a genuine finding while detector notes describe withheld field or contract branches. The CLI forwards those notes and prints them under NOT EVALUATED; they do not change the exit code.

The former standalone JSON Schema finding in the fictional demo is retired because response direction was not established. Its graph remains useful lineage output. A new source-level response test runs extraction, inference and SQLite twice: non-nullable response fires X1, nullable response does not, and the unchanged stricter request never fires. Synthetic and authored-source controls establish behavior, not external precision or recall.

Dogfood snapshot changes require their own reviewed pull request. Development labels must be regenerated for the resulting findings. Freeze and sealed evaluation remain later steps, with at least 30 labelled clusters, strict precision at least 0.90 and Wilson lower bound at least 0.75. Silence, UNKNOWN and an underpowered result cannot satisfy that bar.

Automatic join candidates also exclude paths whose complete segments name test, fixture, mock, component or vendor material, plus `.test`, `.spec`, `.fixture` and `.mock` file suffixes. The implementation's closed segment list is in `packages/infer-join/src/facets.ts`. Both a member's path and its resolved owner's path are checked, including validator declarations and members. Nearby names such as `contest` and arbitrary TSX files remain eligible. This is a conservative candidate policy, not proof that every eligible declaration is a stored row. Extracted facts and scope statuses remain unchanged.

A move preserves non-`File` ids when it changes none of the identity inputs listed in ADR-0016. In the source fixture, an ordinary eligible move also preserves inferred edge keys, crossing into a fixture path removes the join, and returning restores the same key. This is not a guarantee for every eligible move: existing path-based corroboration can change scores, and thresholds or ambiguity can then change join membership. This path-sensitive edge-membership exception is disclosed in ADR-0016 and pinned through real source extraction in `packages/integration/src/join-eligibility.test.ts`. The policy can withhold legitimate schema files under excluded paths, rather than guessing their application role.

## Serialized JSON representations

The development report's representation class includes a text column joined to an object-valued contract property. The pinned development source declares both forms for configuration fields in [the schema at e0c8d80](https://github.com/Dokploy/dokploy/blob/e0c8d80cdea15a4ac3fe495a6ad38e043b4b80b5/packages/server/src/db/schema/sso.ts#L7-L11) and [the body schema in that same file](https://github.com/Dokploy/dokploy/blob/e0c8d80cdea15a4ac3fe495a6ad38e043b4b80b5/packages/server/src/db/schema/sso.ts#L49-L51). Those declarations alone do not establish whether a serializer mediates between them. The source is cited as evidence of declarations, not of observed runtime behavior; no upstream implementation is copied.

For X2, the classified pair `string` and `json` is representation-unobserved in either direction. A text column can store encoded JSON and a string contract can expose an encoded JSON value. Neither possibility proves that the values are compatible, or that a serializer exists. This pair must therefore be withheld rather than reported as a contradiction or added to the compatibility table. This applies to the existing classifier's JSON object/array class; unsupported types remain unclassified. UUID, date and binary representation rules remain unchanged. No blanket compatibility or withholding is added for other string pairs.

When these are the only classifiable joined column/property pairs, X2 reports `REPRESENTATION_UNOBSERVED` as UNKNOWN with no findings. If another classifiable, non-ambiguous pair is observable, it still determines findings or clean output under the existing rules. Library notes and the CLI's NOT EVALUATED output disclose the withheld representation comparison alongside existing generic-field withholding notes. A clean outcome in such a mixed graph does not establish completeness.

Required controls preserve a genuine positive pair and a compatible negative pair. Text/object and JSON/string pairs must not fire; an all-ambiguous graph must be UNKNOWN, including through direct detection. A mixed graph must retain an independently incompatible finding, both fact endpoints, their provenance, and its confidence. Non-fact or tombstoned endpoints cannot establish an observable comparison. Missing scopes remain UNKNOWN. Source controls must extract actual column and contract declarations through the shipped producers instead of inventing an encoding or role property. They must assert both live fact endpoints and their connecting non-LLM join exist before checking withholding. Dependency, ontology, public export and baseline changes are outside this boundary.

This is a conservative evidence boundary for the measured representation class, not a precision or recall result. It does not prove correctness of other representation pairs, supply missing labels, reduce evaluation denominators, or satisfy the sealed precision bar. A future authoritative serializer/mapping producer needs its own reviewed design and producer-backed controls. Dogfood movement still requires a separate reviewed baseline PR.
