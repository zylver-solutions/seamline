## 1. What this is, in one paragraph

A repository says things about itself in Markdown: a Node floor, the formats the CLI prints, which detectors work, which controls are enforced. Seamline already extracts facts about the implementation. This design reads a **closed set of claims** out of the documents (through structural anchors and a closed list of sentence templates, section 3.2), compares each with an implementation fact taken from Seamline's own extraction of the same commit or from a manifest the repository already keeps, and reports each comparison in one of five classes. The report never gates. It is emitted as a versioned, redacted packet that any consumer can read.

It exists because a check of this shape was missing in the pre-fix tree (ADR-0014, Context): four statements were false against the code, every gate was green, and nothing could have said otherwise.

What the three words in the title mean here. **Document** is Markdown the repository tracks. **Declared entity** is a package manifest (`package.json`), the one non-Markdown declaration the four claim kinds consult as a fact; other declared entities (for example `ontology/seamline.yaml`, which carried the same false output-format statement in the pre-fix tree, line 684) are not read, and that is a stated limit (ADR-0014, Negative). **Implementation** is the source tree and Seamline's own extraction of it.

## 2. Vocabulary

| Term         | Meaning                                                                                                                                                                                            |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Claim**    | A statement a document makes, read by the scanner: `(kind, subject, polarity, value, source)`. Provenance `DECLARED`.                                                                              |
| **Polarity** | `AFFIRM` (the document says the thing is so), `DEFERRED` (the document says it is planned or does not work yet), `ABSENT` (the document says it is not implemented). The last two are **markers**. |
| **Subject**  | A semantic, path-free key naming what the claim is about, for example `runtime:node` or `detector:X10`.                                                                                            |
| **Probe**    | A deterministic reader of the implementation fact for a claim kind: `HOLDS`, `DIFFERENT`, `ABSENT` or `UNKNOWN(reason)`. `ABSENT` only over closed sources (5.4); never from `module-wiring`.      |
| **Fact**     | A probe result, with provenance `EXTRACTED` (read from source or from the extraction) or `DECLARED` (read from a manifest). Both satisfy `isFact` (`packages/ontology/src/contract.ts:162`, main). |
| **Finding**  | One classified comparison, in the packet.                                                                                                                                                          |
| **Proposal** | A link between a claim and an entity that is not anchored. `INFERRED`. Never classified, never counted.                                                                                            |
| **Baseline** | An earlier packet, supplied by the caller, against which `Resolved` is computed.                                                                                                                   |
| **Run**      | The extraction the graph facts come from: a store run (`RunRecord`) or a SIF snapshot (section 5.1).                                                                                               |

"Gap" in **Planned gap** and **Unexplained gap** means a **present claim with no implementation**. In v3 (`v3.md:32`, main) and ADR-0005 it means a missing declaration. The two are opposite, and only the first is admitted. ADR-0014 states what it admits and what stays deferred.

## 3. Inputs: documents with provenance

### 3.1 The document set

A closed default, echoed in every packet (`inputs.docs`, `inputs.excluded`), overridable only through `seamline.config.json` under a new `align` key (`docs`, `exclude`):

- Included: `*.md` at the repository root, `docs/**/*.md`, `packages/*/README.md`.
- Excluded: `docs/adr/**`, `docs/audit/**` (dated decision and review records are history, not current claims), `CHANGELOG*` at any depth (release notes are a dated record too: a line that was true when it was written would become a claim that can only be corrected by rewriting history), `docs/dogfood/**`, `**/node_modules/**`, `seamline-out/**`.

Excluding a file hides its claims. The effective exclusion list is therefore part of the packet, so a reader can see it.

Files are read from the git object database at the evaluated commit (`--at <rev>`, default `HEAD`), never from a working tree that may have moved. `--worktree` reads the working tree instead and records `subject.worktree: true`. Each input is recorded with its path, the SHA-256 of its bytes and its status.

Bounds, all fail-safe: 2000 documents, 1 MiB per file, 4096 characters per line considered for claim matching, 10000 claims, 5000 findings, 5000 source files and 1 MiB per source file for the probes of section 4. An exceeded bound is that input's status `FAIL` with reason `limit-exceeded`, and one rule decides what it does to a result: **a result that needs the whole input is `Unknown(limit-exceeded)`; a positive result already found stands.** So a source probe's `ABSENT` becomes `UNKNOWN(limit-exceeded)` (a witness found before the bound was hit still gives `HOLDS`, 4.2 step 5), and a document over the bound yields no claims, so a subject whose baseline claims lay in it is `Unknown`, never `claim-removed` (section 7).

### 3.2 The scanner: structure first, then closed sentence templates

A hand-written, line-oriented, linear-time Markdown scanner in the new package. No Markdown library and no new dependency. It does two things, and this document and ADR-0014 describe both:

1. **Structural anchors.** It recognises exactly the units below.
2. **Closed sentence templates.** Within a unit's text it splits sentences and tests each against a fixed list of templates (sections 4.2 and 4.3). This **is** pattern matching on prose. It is deterministic, has no model and no scoring, and each template must match a whole sentence from its first token to its last, with the subject, verb and object in fixed positions. A sentence that merely contains the right words matches nothing, with one stated exception: the `DEFERRED` detector markers of 4.3 test a label or a sentence for a detector code and a dormancy cue from a closed list, wherever they sit in it, and are the one place where the scanner is not template-shaped (4.3 says how their effect is bounded). Nothing else is bag-of-words, and none of it is natural-language understanding.

| Anchor       | Recognised as                                                           | Yields                                                                                   |
| ------------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Front matter | a leading `---` block of `key: scalar` lines                            | scalar values only                                                                       |
| Heading      | ATX headings (`#` to `######`)                                          | a heading path (list of heading texts) for every unit under it                           |
| Table        | GFM pipe table with a delimiter row                                     | header cells, and per row an ordered list of cells; **each row is its own unit**         |
| List item    | `-`, `*`, `+` or `1.` item, continuation lines joined; **its own unit** | the **lead label** (the inner text of a bold span that begins the item) and the **body** |
| Paragraph    | any other run of non-blank lines                                        | text for sentence templates                                                              |
| Code span    | a backticked inline run                                                 | a code token, kept for path anchoring and removed from sentence templates                |

Fenced code blocks, indented code, HTML blocks and HTML comments are skipped entirely (examples are not claims). Anything the scanner does not recognise is treated as a paragraph. A claim's line range is the line range of its unit (the list item or table row), not of the block it sits in. A document written in a way no template matches yields no claim. **Silence is the failure mode; a guess never is.**

**Which units.** Sentence templates apply to paragraphs and list items (a list item's lead label and body together). Table rows are read only by the table anchors of 4.1, 4.3 and 4.4 and are never split into sentences; for those anchors a row is its cells in order. **Preparation `P`** of a unit's text, in this order: replace links with their text; replace each code span with the single character `¤` (U+00A4); strip emphasis markers; **split into sentences** on `.`, `!` or `?` followed by whitespace and then an upper-case letter, a digit, `¤` or the end of the unit, and also on `;`; then, for each sentence, delete every parenthetical group `( ... )` (innermost first; if parentheses remain unbalanced the sentence yields nothing), delete `¤`, remove trailing `.`, `!` and `?`, collapse whitespace, and lower-case. Splitting happens before code spans are deleted and before lower-casing, so a sentence that begins with a code span is split from the one before it and capital letters still mark sentence starts. A parenthetical that contains a `;` or a sentence end is split and then left unbalanced, so its sentences yield nothing. Every template is a fixed regular expression with no nested quantifiers.

Why parentheticals are deleted: an enumeration inside parentheses describes an input or an aside, not the claim of the sentence. `packages/extract-contracts/README.md:3` (pre-fix and main) reads "...: OpenAPI 3.x (YAML and JSON), standalone JSON Schema, and Zod schemas in TypeScript source, emitted as ...". Without the rule, a looser reading finds an enumeration and the verb "emitted" and invents a claim that the CLI emits YAML and JSON. With it, and with the subject requirement in the templates, the sentence yields nothing. It is a fixture (section 12.2).

### 3.3 The claim record

```
Claim {
  kind        : 'RUNTIME_FLOOR' | 'OUTPUT_FORMAT_SET' | 'DETECTOR_LIVENESS' | 'CONTROL_ENFORCEMENT'
  subject     : string            // path-free, section 8.2
  member      : string | null     // a set member such as 'csv'
  polarity    : 'AFFIRM' | 'DEFERRED' | 'ABSENT'
  value       : string | boolean | null     // RUNTIME_FLOOR: normalised 'X.Y.Z'; the others null
  provenance  : 'DECLARED'
  source      : { path, lineStart, lineEnd, commit, extractor: { name: 'align-docs', version: '1' } }
  excerpt     : string            // normalised text of the unit, at most 240 characters, untrusted, redacted
  digest      : 'sha256:<hex>' of canonical JSON of { kind, subject, member, polarity, value }
}
```

`digest` covers the **meaning** of the claim and nothing else. It excludes the excerpt, the path, the lines and the commit. Excluding the excerpt is deliberate: a reworded sentence with the same meaning is not a correction; the redaction of the excerpt (section 8.5), which may change when the redactor's rules change, cannot move a digest; and a digest can never carry a hash of text that contained a credential.

The extractor that produces claims is named `align-docs`, version `1`, and that pair is recorded on every claim. The SHA-256 of each document's bytes is on the input record (`inputs.docs[].sha256`), not on the claim. Claims are **not graph nodes** and are not stored in the store.

## 4. The four claim kinds

The set is closed. Each kind has an anchor grammar, a subject, a probe, and a comparison. Each also shows exactly what it does to the four false statements recorded in ADR-0014 (Context), with lines in the pre-fix tree ("then") and on main ("now").

### 4.1 `RUNTIME_FLOOR`

- **Anchor.** A list item whose lead label, or a table cell in a table's first column, matches `^(Node|Node\.js|pnpm)\s*(>=|≥)\s*(\d+)(\.(\d+))?(\.(\d+))?`. The operator is `>=` or its single-character form `≥`, both read as "at least"; `>`, `^`, `~` and `=` match nothing.
- **Polarity, value.** `AFFIRM`; the three numbers as `X.Y.Z`, missing parts read as 0.
- **Subject.** `runtime:node` or `runtime:pnpm`, suffixed `@<package name>` when the document lives under a non-root package (the name is the npm name, not a path).
- **Probe `manifest-field` v1.** Provenance `DECLARED`. This probe reads no run.
  1. **Read.** Walk up from the document's directory to the repository root and take the **nearest `package.json` that declares `engines.<runtime>`** (the key is present), not the nearest `package.json`: a workspace package that keeps no `engines` of its own inherits the floor its repository root declares. **The inheritance crosses only directories that hold no other floor site.** The walk visits directories nearest first. A directory nearer than the declaring manifest is a **floor site** when it tracks a pin file of step 2, or a `package.yaml` or `package.json5` (paths relative to that directory); or its `package.json` keeps `devEngines` or `volta`, or, for `runtime:node`, `pnpm.executionEnv`, or, for `runtime:pnpm`, a `packageManager` that begins `pnpm@`; or it holds a `package.json` that is not a discovered package (5.3: a manifest outside the workspace globs, as a documentation site's is). If the walk reaches a declaring manifest across a floor site, the result is `UNKNOWN(non-extracted-anchor)` and `detail` names the nearest site: the nearer site may be where the document's own package pins its runtime, and the farther `engines` belongs to a package that may not use it. What sits beside the declaring manifest does not count (it is not nearer than itself): this repository's root keeps `engines` and a tracked `.nvmrc`, and a package under it still inherits. A `package.json` met on the way that does not parse is `UNKNOWN(manifest-unparseable)`, and that is decided before any floor site is reported. Accepted grammar for the value: a single comparator `>=X`, `>=X.Y` or `>=X.Y.Z`; a present value outside it (`^22`, `||`, a range pair) is `UNKNOWN(unsupported-range)`. `observed` is the normalised `X.Y.Z`.
  2. **Survey, when no manifest on the walk declares it.** A floor can be declared in places other than `engines.<runtime>` of the manifests on the walk, and a document can describe any package of the repository, so the probe looks across the whole tracked tree before it concludes that no floor exists. It looks at every tracked `package.json` (one that does not parse is `UNKNOWN(manifest-unparseable)`) for `engines.<runtime>` (a manifest off the walk), for a `devEngines` key and for a `volta` key; for `runtime:pnpm` also for a `packageManager` value that begins `pnpm@`; for `runtime:node` also for a `pnpm.executionEnv` key; and at every tracked file whose path is, or ends in `/` followed by, one of the **pin files** `.tool-versions`, `mise.toml`, `.mise.toml`, `.config/mise/config.toml` and `.mise/config.toml`, and for `runtime:node` also `.nvmrc` and `.node-version`; and at every tracked `package.yaml` or `package.json5` (the other manifest formats pnpm reads, which the probe does not parse). These sites are not parsed: that one exists is the finding. If one does, the result is `UNKNOWN(non-extracted-anchor)` and `detail` names the first by path: the floor may be declared there, and the probe does not read it. If the tree tracks no `package.json` at all the result is `UNKNOWN(non-extracted-anchor)` too (a repository the probe cannot read a floor from is not one without a floor). Otherwise `ABSENT`. A missing `engines` entry is therefore not by itself absence. A `packageManager` of another manager (`yarn@4`) is not a pnpm site: a document that requires pnpm in a repository that pins yarn is reported as the gap it is.
- **Comparison.** Exact tuple equality, per claim: `HOLDS` or `DIFFERENT`.
- **Completeness.** `exact`: both `HOLDS` and `DIFFERENT` are conclusive, for a floor read from the document's own package, or inherited from a farther manifest across directories that hold no other floor site (step 1). `ABSENT` is conclusive only as the closed-world answer of step 2: no site of the survey declares a floor (5.4).
- **Step 1.** Then: `docs/toolchain.md:7` "Node >= 22.11" against `package.json:13` `>=22.13.0` (both pre-fix): `DIFFERENT`, **Observed drift**. Now: `docs/toolchain.md:7` says 22.13 (main): `HOLDS`. This is the only `RUNTIME_FLOOR` claim at either commit, and in both the walk crosses only `docs/`, which tracks no manifest and no pin file, and ends at the root `package.json`, which declares `engines.node`: no floor site lies nearer, and the survey is not reached. The root's own `.nvmrc` sits beside the declaring manifest and does not count.

### 4.2 `OUTPUT_FORMAT_SET`

- **Lexicons (closed, lower case).** Formats: `text json csv tsv yaml xml html markdown mermaid dot graphml sarif pdf`. A **member** is one of these words. `SEP` is exactly the regular expression `(, and |, or |, | and | or |/)`. The spaces inside it are part of the strings: a comma and a space; a space before and after `and`; a space before and after `or`. Nothing else separates members, so `csv and mermaid` and `csv, and mermaid` are enumerations and `csvandmermaid` is not. The templates below must match the whole sentence, so the order of the alternatives changes no result. An **enumeration** `ENUM` is `member (SEP member)+`: two or more members, filling the whole object position of a template. A single format never makes a claim.
- **Templates.** Each is tested against a sentence prepared by `P` (section 3.2, so code spans such as `--json` and parentheticals are already gone) and must match it entirely. Templates apply to paragraphs and list items only.
  - **T1 (output is):** one of two forms. With the CLI named in the subject: `(the )?(cli |command line |seamline )(output|outputs|output formats?) (is|are|include|includes) ENUM( from the cli| from seamline| of the cli)?`. With a bare subject, the tail naming the CLI is required: `(the )?(output|outputs|output formats?) (is|are|include|includes) ENUM( from the cli| from seamline| of the cli)`. Yields one `AFFIRM` per member. A bare "Output is A and B" with no mention of the CLI matches nothing, so a component describing its own output cannot match.
  - **T2 (the CLI emits):** `(the )?(cli|seamline|command line)( command)? (emits|prints|renders|writes|exports|produces|outputs) ENUM( output)?`. Yields one `AFFIRM` per member.
  - **M1 (not implemented):** `ENUM( output| export| support)? (is|are) not (implemented|supported|available)`. Yields one `ABSENT` marker per member.
  - **M2 (deferred):** `ENUM( output| export| support)? (is|are) (deferred|planned|not yet (implemented|supported))`. Yields one `DEFERRED` marker per member.

  A sentence matching no template yields nothing, whatever words it contains. T1 and T2 name the CLI (T1 in the subject or the tail, T2 as the subject), so a sentence about the output of something else (an extractor, an input format) cannot match.

- **Subject.** `cli:output-format:<format>`, one finding per format, so a fix to one format does not hide the other.
- **Probe `format-witness` v1.**
  1. **Gate.** The scope table (section 5.1) must hold `code.ts` as `PASS`, else `UNKNOWN(scope-not-pass)`. A `code.ts` that no result declares is not `PASS`.
  2. **Roots.** The packages (section 5.3) whose `package.json` has a `bin` field. **No such package is `UNKNOWN(no-source-roots)`**, never `ABSENT`, except that it is `UNKNOWN(manifest-unparseable)` when package discovery is incomplete (5.3: the `bin` package may sit in the part that was not read) or when a tracked `package.json` that no discovery reached does not parse, and `UNKNOWN(source-unreadable)` when the tree tracks a `package.json` with a `bin` field that no discovery reached (step 5).
  3. **Scan set.** The roots plus the transitive closure of workspace packages they list in `dependencies`, `optionalDependencies`, `peerDependencies` or `devDependencies`. The scan therefore follows the CLI through a library package: a renderer in a workspace library the CLI depends on is in the set, including a library that a bundled CLI lists only in `devDependencies` because the bundler inlines it (`module-wiring` leaves `devDependencies` out of its dependents on purpose, 5.3). A dependency is followed by its key when the key is the name of a discovered package. It is also followed to the package it names when the specifier says so: `workspace:<name>@<range>` (a pnpm alias, whose key differs from the package) leads to the package `<name>`, and a path specifier (`file:`, `link:`, `portal:`, or `workspace:` followed by `./` or `../`), resolved from the package's directory, leads to the discovered package whose directory it is. It over-approximates (it reads all of a dependency, not only what the CLI imports), which only adds witnesses. What the closure cannot follow is not left to chance: step 5 turns each such case that the tree shows into `Unknown`, and 5.4 lists the rest. The package named `@seamline/align` is the instrument and is **excluded**: its lexicons name every format, so scanning it would witness every format (it would turn the `csv` and `mermaid` findings of the self-proof into `Unknown(cannot-confirm-presence)`). The exclusion is recorded in `inputs.probes[].diagnostics`. In the pre-fix tree the scan set is every package except the test-only `@seamline/integration` (the `bin` packages `cli` and `mcp` depend on all of the others, and `integration` has no source outside its tests, so no source is missed), and `@seamline/align` does not exist yet. On main (2026-10-19) it is the same ten packages (note, 2026-11-10: in 0.1.0 the closure also holds `@seamline/security`, which `cli` and `mcp` list in `dependencies`): `@seamline/eval`, the private evaluation harness, has no `bin` and no `bin` package depends on it, so it is outside the set, as `integration` is. `devDependencies` adds no package at either commit: the only workspace dependencies listed there on main are `@seamline/core` in `contradictions` and `infer-join`, both already in the set.
  4. **Tokens and names.** Over the source files of the scan set (section 5.3), parse each file with the TypeScript parser (syntax only: no type information, no module resolution; comments are not nodes) and keep exactly these tokens: every **identifier**; every **string literal used as a property name** (`{ 'csv': ... }`); and every **string literal (or template literal without substitutions) that is an operand of `===`, `!==`, `==` or `!=`, or the expression of a `case` clause**. Split each kept token into words and compare them case-insensitively. A word boundary falls at every `_`, `-`, `.` and `/`; between a lower-case letter or a digit and the upper-case letter that follows it (`renderCsv` gives `render`, `csv`); and inside a run of upper-case letters, before its last letter when a lower-case letter follows that letter (`CSVWriter` gives `csv`, `writer`; `parseCSV` gives `parse`, `csv`). The rule is lexical: an acronym with a plural `s` splits wrong (`CSVs` gives `cs`, `vs`) and witnesses nothing (5.4, residue). A format is **witnessed** if any word equals it. Nothing else is kept: a string that is an element of an array or `Set` literal, an argument of a call, a message, a map value or a string-literal type is not a witness. The `parseArgs` option shape of `packages/cli/src/args.ts:37-44` (main; `:32` in the pre-fix tree), `json: { type: 'boolean' }`, is witnessed through its property name.

     **Names.** Also kept, as words (split as above): the basename without its last extension and each directory name, below the package directory, of every tracked file of a scan-set package, of any extension, that is not a declaration file, a test (4.4), under `__fixtures__/` or `node_modules/`, or under the package's `compilerOptions.outDir`; and the name of every package that a scan-set package lists in `dependencies`, `optionalDependencies`, `peerDependencies` or `devDependencies` (the `@` of a scope removed). A CLI that selects a renderer by file name, loading `formats/csv.ts` through an `import()` of a computed path, or that renders through a library named for the format (`csv-stringify`), has the format in these names and nowhere else, and a rule on tokens alone would call the format absent. A data file `sample.csv` witnesses nothing: the last extension is removed. A name is as weak a witness as a token and weaker than a comparison: it says that the package holds something named for the format, not that the CLI prints it.

     _Why the rule is this narrow._ A format the CLI actually renders is dispatched on by a comparison or a `case`, or is named by the code that renders it (`renderCsv`, a `csv:` entry). A name that only sits in a list is not evidence of support, and lists of names are common in unrelated code: `packages/extract-data/src/clickhouse.ts:104` (main) holds `'csv'` in `OTHER_DIALECT_ENGINES`, the MySQL storage-engine names. A rule that counted every string literal in the scan set would let that one string witness `csv`, which would turn the M1 markers of 12.1 into `Unknown(cannot-confirm-presence)` and leave the proof with no `Resolved` record for `csv`. _The cost, stated:_ a format selected only through a list, `['json', 'csv'].includes(format)`, with no comparison, no `case` and no identifier, property, file, directory or dependency name carrying the word, is not witnessed, and `Unexplained gap` is then reported for a claim that is true. It is accepted because a rendered format is almost always also tested by a comparison or named by a renderer or a file, and because the alternative (counting lists) lets any unrelated word list defeat the probe. It is **not the only remaining way** for this probe's `ABSENT` to be wrong toward reporting. The others are sources that the tree gives the probe no evidence of, so it cannot withhold on them: (a) a name that does not spell the format as separate words (`csv2json`, an alias such as `delimited`, or `CSVs`); (b) a renderer chosen at run time through a computed specifier or a plugin path, where nothing in the scan set names it; (c) a format named only by the content of a data or template file; (d) a renderer in an executable that the CLI spawns by name, such as a tracked shell script (FW6). They are the residue of 5.4 and are listed in section 14; the list-only case is pinned by the fixtures of 12.2 (A1 to A6 do not fire, B1 to B9 fire).

  5. **Result.** Witnessed is `HOLDS`. Not witnessed, over a complete scan, is `ABSENT`. The scan is not complete, and a not-witnessed result is `Unknown`, when the tree shows that code the CLI may use was not read:
     - a source file that cannot be read, or cannot be parsed (the parser reports a syntactic diagnostic for it: `ts.createSourceFile` never throws, so "cannot be parsed" means "has parse diagnostics", 5.3), or a scan-set package that is not wholly TypeScript or JavaScript (5.3, Other-language packages): `UNKNOWN(source-unreadable)`;
     - the scan set **leaves itself**, in one of five ways that the tree shows: (1) a scanned source file has a module specifier (of an `import` or `export ... from` declaration, of an `import()` or `require()` call with a string literal, of an `import x = require()` or of an `import('x')` type) that is relative and, resolved lexically from the file's directory, lies outside the file's package directory; (2) such a specifier is bare and its package name (the first segment, or the first two of a scoped name) is that of a discovered workspace package that is not in the scan set and is not the excluded `@seamline/align` (an import of a workspace package that the manifest does not list, which a bundler or a hoisted install allows); (3) the repository root or a scan-set package directory holds a tracked `tsconfig*.json` that declares `compilerOptions.paths`, directly or through a chain of relative `extends` (followed from the extending file's directory, with `.json` added when the path does not end in it; one that names an untracked file counts as a `paths` the probe cannot read; a bare `extends` names an installed package and is not followed, 5.4), because the probe does no module resolution and cannot tell where an alias leads; (4) a scan-set package lists a dependency whose specifier is a path that is not the directory of a discovered package (`file:`, `link:`, `portal:`, or `workspace:` followed by `./` or `../`), or is `workspace:` with a target that is not a discovered package (the key for `workspace:*`, `workspace:^` and `workspace:~`, the name for an alias `workspace:<name>@<range>`); the instrument is excepted; (5) the tree tracks a `package.json` with a `bin` field that is neither the root nor a discovered package, outside `__fixtures__/`, `__tests__/` and `node_modules/`: the CLI the document describes may be that package. The result is `UNKNOWN(source-unreadable)` and `detail` names the file and the specifier, the dependency or the `tsconfig`. A specifier that is not a string literal is no evidence and is not looked for (5.4, residue);
     - a bound exceeded: `UNKNOWN(limit-exceeded)`;
     - incomplete package discovery (5.3: a manifest that does not parse, or a workspace file or entry the reader cannot read), or a tracked `package.json` that no discovery reached (the exclusions of (5) apply) and that does not parse, because it might be a `bin` package: `UNKNOWN(manifest-unparseable)`.

     Absence needs a complete scan, and a scan of the TypeScript half of a package whose rendering code is in another language, or of a package whose imports lead out of the scanned set, is not one. The reasons are tried in the order `source-unreadable`, `limit-exceeded`, `manifest-unparseable`, one per result. A witness that was found stands over all of them.

- **Completeness.** `absence-sound` under steps 4 and 5: `ABSENT` is conclusive over the sources the probe reads (5.4), except for the residue named in step 4. `HOLDS` is a **presence witness only**: a word in an identifier or a property name, in a string that a comparison or a `case` tests, or in the name of a file, a directory or a dependency, somewhere in the scan set. It can support an `AFFIRM` (not shown false) and it is the weak, presence-shaped evidence the project's own rules reject as a gate. That is why `HOLDS` never produces a drift class and a stale marker beside it is `Unknown(cannot-confirm-presence)` (section 6, D7, D8). It can produce a **`Resolved`** record: a baseline `Unexplained gap` whose claim has not changed resolves as `fact-changed` when a witness appears (section 7). A name is the weakest witness and is gameable by anyone who can add a file: a stub `src/formats/csv.ts` containing `export {};`, or an unused dependency `csv-stringify`, turns a standing gap into a `Resolved` record while the format is still not rendered (H1 to H1c). That is the stated cost of not reporting a gap for a format selected by file name. So that a reader can see which witness stood, `fact.detail` of a `HOLDS` begins `token` when a kept token of step 4 supplied the word, and `name` otherwise, then names the first supplier in path order (8.3), or `dependency <name>`.

### 4.3 `DETECTOR_LIVENESS`

- **Anchors.**
  - **Catalog table**: a table whose first-column body cells all match `^X\d+$` (after link replacement), at least three rows. Each row is an `AFFIRM` for `detector:X<n>`. A catalog whose first column is a link to a per-code page does not match: in `docs/contradictions/README.md` on main the cells are `[X1_NULLABILITY](X1.md)`, which read as `X1_NULLABILITY`. That catalog, with its "Status today" column, is **not read**. This is a stated limit (ADR-0014, Negative); reading it would be a new anchor and an amendment to ADR-0014.
  - **List-item marker**: a list item whose lead label contains one or more `X<n>` codes **outside parentheses** and one dormancy cue from the closed list `does not fire`, `do not fire`, `cannot fire`, `can not fire`, `none of them can fire`, `never fires`, `dormant`, `not yet`, `yet`. A `DEFERRED` marker for each code. **The lead label is read with its code spans kept as text** (a code span is replaced by its content, not deleted as `P` deletes it from a sentence), then parenthetical groups are deleted and the text is lower-cased. Both a code span and plain text give the marker. `README.md:184` on main is the list item whose label is the bold span "`X10` (untested PII write path) does not fire on real repositories yet.", and its code is plain text there, not a code span; a later edit that wraps it changes nothing. A sentence marker, below, has no code spans left, so the same words in a paragraph need the code in plain text.
  - **Sentence marker**: a sentence (prepared by `P`, section 3.2) with one or more `X<n>` codes (`x<n>` after lower-casing) and a cue from the same list. A `DEFERRED` marker for each code.
  - **A range phrase is not an enumeration of codes.** In a label or a sentence, before the codes are collected, every range phrase `X<a> to X<b>`, `X<a> through X<b>` or `X<a>-X<b>` (ASCII hyphen; matched after lower-casing) is deleted and contributes no code. A range names its two ends and not what lies between, and an end of a range is not the subject of the cue. On main, `docs/design/real-world-inputs.md:356` reads "every X1 to X10 either fires on an unmodified corpus repository or is disclosed dormant with its reason": without this rule it marks `X1`, which is live, as `DEFERRED` (found by replay). A code written outside the phrase still counts: `X1 to X2 are live, but X3 is dormant` marks `X3` only, and `X2, X3 do not fire yet` marks both. (These examples sit in code spans on purpose: this document is itself in the input set, and a plain sentence of that shape would be a marker.)
  - A code that is not in the detector registry yields no claim.
  - **Why the bare cue `yet` stays.** The disclosures this repository writes use it ("does not fire on real repositories yet"). A sentence that names a detector and says `yet` for another reason yields a `DEFERRED` marker; the worst a spurious marker can do is turn an Unexplained gap into a Planned gap (still reported) or into `Unknown(cannot-confirm-presence)`. It can never produce drift.
  - **The one non-template rule.** The two marker forms (label and sentence) are the one place where the scanner is not template-shaped (3.2): they test a unit for a detector code and a cue from a closed list, wherever they sit in it, instead of matching a whole sentence from its first token to its last. They are kept because the disclosures this repository writes are free-form; the range rule above and the bound in the previous bullet are what contain them, and the fixtures of 12.2 pin both.
- **Subject.** `detector:X<n>`.
- **Probe `detector-liveness` v1** (reads the evaluated tree and the scope table of section 5.1).
  1. The registry is the array exported as `ALL_DETECTORS` (`packages/contradictions/src/detectors/index.ts:29`, main). Its elements resolve, by import, to detector files; each detector's code is the `X<n>` prefix of the string literal in its `code:` property.
  2. **Required scopes.** The detector's own declaration of the scopes its answer depends on: the array in its `requiredScopes:` property (`x10-untested-pii-write.ts:68`, main). Each element is a string literal, or an identifier imported from a relative module that exports it as a `const` initialised to a string literal (`SCOPE_CODE` and its siblings, `packages/contradictions/src/scopes.ts:25-29`, main). A detector without the property, or an element that does not resolve that way, is `UNKNOWN(reads-unresolvable)`. This is the list `seamline check` itself gates the detector on (`blockedScopes`, `packages/contradictions/src/detector.ts:121-123`, main), so the probe is never more permissive than the detector it describes.
  3. **Read model.** In the detector's own file, every call expression named `factNodes` (kind in the second argument) or `nodesByKind` (kind in the first) with a string-literal kind is a **read**. A **read group** is formed by every maximal `||` chain (a `||` binary expression that is not itself an operand of another `||`) all of whose operands contain at least one read: the reads inside its operands, at any depth, are one group, and any member suffices. This is the shape of `x10-untested-pii-write.ts:51`, `factNodes(g, 'TestCase').length > 0 || factNodes(g, 'CoverageRecord').length > 0`, where the reads sit inside comparisons. A read in a `||` chain that has an operand containing no read is **optional** and belongs to no group. Every other read is a group of one. The probe treats **every group as required**; that is an assumption about the detector, stated in `fact.detail`. A call whose kind is not a literal makes the reads incomplete: `UNKNOWN(reads-unresolvable)`. A file with no group is `UNKNOWN(reads-unresolvable)`.
  4. **Scope check, before any kind is looked at.** No extractor result at all: `UNKNOWN(facts-missing)`. Otherwise every required scope must be `PASS` in the scope table (section 5.1). **A scope that no result declares is not declared, and a scope that is not declared is not `PASS`**: "we have no record of that extractor running" and "that extractor ran and found nothing" are different answers, and only the second may be used to deny that something exists (the comment on `scopeStatus`, `packages/core/src/store/sqlite-store.ts:645-657`, main; AGENTS.md invariant 3). If any required scope is not `PASS`, the result is `UNKNOWN(scope-not-pass)`, `unknown.scopes` names those scopes, and `detail` says for each one `FAIL`, `UNAVAILABLE` or `not declared`. The probe never looks at a kind in that case. A crashed extractor **may be recorded with no scopes**: `unavailable()` (`packages/cli/src/commands/extract.ts:405-416`) and `failed()` (`:450-461`), both main, write `authoritative: []`, so in a SIF from such a run its scope is simply not declared, which this step turns into `Unknown`. A crash that declares its scopes with a non-`PASS` status instead (as `refused()` does, `:428`, and as a first-party crash does once its scopes are declared) is caught by the same step, because the scope is declared and not `PASS`. The rule is written to be correct for either shape; the store case is in 5.1. Note (2026-11-10): as implemented, `unavailable()` and `failed()` in `packages/cli/src/commands/extract.ts` now declare the extractor's scopes with their non-`PASS` status, as `refused()` does, so `seamline extract` no longer records the no-scope shape. The rule for it stays, because a run recorded by an older build or by another producer can still have it.
  5. **Result, with every required scope `PASS`.** `PASS-produced` is the union of the declared `kinds` over **every** `PASS` scope of the table, not only the required ones (`ExtractorResult.authoritative`, `packages/ontology/src/contract.ts:253`, main). A group is **produced** if one of its kinds is in `PASS-produced`.
     - Every group produced: `HOLDS` ("not shown dormant at the level of node kinds"; `detail` names the produced kinds).
     - Some group not produced, and one of its kinds is declared by a scope of the table that is not `PASS` (a result that failed but kept its scopes, as `refused()` does, `:428`): `UNKNOWN(scope-not-pass)` naming that scope. A declared scope that did not pass might have produced the kind.

       tree: `UNKNOWN(scope-not-pass)` with `unknown.scopes` empty and `detail` naming the first
       file (by path) and the kind. A discovered package (5.3) is an **extractor package** if it is

       identifier `ExtractorManifest` at all**: as a variable annotation, a return type, a
       parameter type, `satisfies ExtractorManifest`, `as ExtractorManifest` or an `import`, found
       by the parser as an identifier node (a comment or a string literal is not an identifier).
       The mention test is deliberately wider than "declares a manifest", because every widening
       can only turn a gap into `Unknown`: a package that merely takes a manifest as a parameter
       counts (`packages/core/src/security/sandbox.ts` does), and so does a package that declares
       its own `interface`, `type` alias or `class` of that name. Exactly one package is not

       This is the _name scan_. An extractor whose source names the kind but whose scope is not in
       the run, because it was left out (a partial run) or crashed without declaring it, might have
       produced the kind, and the detector's own `requiredScopes` cannot show it. The scan reads

### 4.4 `CONTROL_ENFORCEMENT`

- **Anchor.** A table whose first-column cells match `^C\d+$`, under a heading whose text (leading number and punctuation removed) begins with `Controls`. A row yields an `AFFIRM` for `control:C<n>` only if the row's second cell contains an enforcement cue from the closed list `enforces`, `enforced`, `enforce`, `wired`, matched as a whole word, case-insensitively (control C3 reads "Wired at ..."). A row with no cue yields nothing.
- **Subject.** `control:C<n>`.
- **Binding (which code the claim is about): B1 only.** The document must name the code. B1: code spans anywhere in the row that name a path existing in the tracked tree at the evaluated commit (a code span containing `/`, or ending in a TypeScript or JavaScript extension; a trailing `/` is removed). A code span that names no tracked file or directory is ignored. A row naming no existing path is `UNKNOWN(claim-unanchored)`. **There is no second binding.** A candidate found by shared wording between a row and a source comment is a **proposal** (section 8.6), never a binding. ADR-0014 section 2 records why: wording shared between two human-written texts is a name match, and a name match is `INFERRED`, which AGENTS.md invariant 5 forbids as the ground of a finding.
- **Module set `M`: the files the run read.** `M` is the set of `File` nodes **of the run** whose `path` is, or lies under, a bound path, excluding tests. This is the set the `code.ts` scope selector covers, and nothing else: a file the extraction did not read is not in `M`, whatever its extension, and "source file" in this probe means a file in the run. In the pre-fix tree the selector lists only `*.cts`, `*.mts`, `*.ts` and `*.tsx` under package and example `src/` directories, and the SIF has no `File` node for any `.js` or `.mjs` file; the same holds on main (2026-10-19), where `docs/dogfood/baseline/code-ts-coverage.json` records `scripts/license-gate.mjs` as unread. So:
  - **`M` empty is `UNKNOWN(non-extracted-anchor)`.** If `M` has no file, the probe does not run. That covers a bound path with no `File` node in the run (a `.mjs` script, a workflow directory, a TypeScript file that no loaded tsconfig project reads) and a bound path whose only files are tests, such as a package that holds nothing but tests (`@seamline/integration`) or a row that names a `*.test.ts` file: a control enforced by a test is a normal pattern, and the module-wiring probe does not look at tests.
  - If some bound paths have `File` nodes and others do not, the probe runs on `M`; `HOLDS` stands, and a result that would otherwise be `no-static-consumer` is `UNKNOWN(non-extracted-anchor)`, because a named path was not read at all.
  - **An entry point is wired by its manifest.** An **entry point** is a file that the output-to-source mapping of 5.3 gives for a `bin` target of a package, or for its `main` or `exports` targets (declaration files excluded): `packages/cli/src/bin.ts` and `packages/cli/src/index.ts` are two. Nothing in the workspace imports the first (the package manager or the shell runs it), and the second is the package's public surface, consumed from outside the workspace where the graph cannot see. The manifest, a `DECLARED` fact the probe already reads, is their consumer. So if a bound path **is** an entry point (it names that file, and the file is in `M`), the result is `HOLDS`. A bound path that is a package or a directory which merely contains an entry point does not count: C3 names `packages/cli`, which holds a `bin` target, and a row about a package is not made true by the package having a command. Like every `HOLDS` here this is a presence witness: the file is declared as run or exported, not shown to enforce anything.
- **Probe `module-wiring` v1** (reads the run's graph facts). Requires the scope table (section 5.1) to hold `code.ts` as `PASS`, else `UNKNOWN(scope-not-pass)`; a `code.ts` that no result declares is not `PASS`.
  - **The probe never answers `ABSENT`: it confirms or it declines.** The only consumer evidence is a file-level `IMPORTS` edge, and `extract-code-ts` records an edge only from an `import` declaration and an `export ... from` declaration (`packages/extract-code-ts/src/relations.ts:174-185`, main). It records none for a dynamic `import()`, a `require()`, a `new URL('./x.ts', import.meta.url)`, a path named in a `package.json` `scripts` value (the root `eval` script runs `packages/eval/src/bin.ts` that way, `package.json:33`, main, and nothing imports it), a path named in a workflow or a tool configuration, or a file the run did not read (the set `U`, next). Any of them can be the consumer of a module of `M`, and the graph cannot tell, so a missing edge is not a finding. The extraction can witness the presence of wiring and never its absence: a control claim can be confirmed (`HOLDS`) or left `Unknown`, and this probe never reports one as an Unexplained gap or a Planned gap. This is the stance `format-witness` takes toward presence (its `HOLDS` is a weak witness and never produces a drift class, 4.2), applied to the one kind whose evidence is only presence. Narrowing the residue, for example by reading those shapes for a specifier that names the module, is a new design pass (section 10).
  - **Unread source `U`.** The tracked files of the evaluated commit with an extension in `.ts .mts .cts .tsx .js .jsx .mjs .cjs`, that are not declaration files (`*.d.ts`, `*.d.mts`, `*.d.cts`), not tests (below), and have no `File` node in the run. A consumer in one of them is invisible to this graph. `U` changes no class (there is no `ABSENT` for it to withhold); the `detail` of `no-static-consumer` gives its size. In this repository `U` is not empty: `eslint.config.js`, `ontology/*.mjs`, `scripts/*.mjs` and `examples/semantic-world/demo.mjs` are tracked, run through Node or the type stripper rather than loaded by a tsconfig project, and unread (in the pre-fix tree seven files, at main eleven; `docs/dogfood/baseline/code-ts-coverage.json` lists the unread code).
  - **Graph.** File-level `IMPORTS` edges only (`src` and `dst` are `File` nodes). **Symbol-level edges are never used**, because symbol ids are `{module}#{name}` and two exports of the same name in one package are one node: in the pre-fix tree both `packages/core/src/security/sandbox.ts:168` and `packages/core/src/merge/tombstone.ts:39` export `globToRegExp`; the SIF has a single `Symbol` node for it (path `merge/tombstone.ts`), carrying `CONTAINS`, `EXPORTS` and `CALLS` edges from both files; and the `File` node of `sandbox.ts` has an `EXPORTS` edge to it. The only inbound `CALLS` onto it from another file is `merge/tombstone.ts` calling its own function, and a symbol-level reading would call `sandbox.ts` wired on that edge alone. (Package-scoped symbol id collisions are already a known open follow-up.) The edge prop `typeOnly` is **ignored**: a type-only import counts as a consumer, which errs toward `HOLDS`. The flag is not reliable across commits: the edge from `security/index.ts` to `sandbox.ts` carries `typeOnly: true` in the SIF in the pre-fix tree although the barrel re-exports values, and `false` on main since the order-independence fix of the `IMPORTS` facts. The edge prop `reExport` is used for barrels, below.
  - **Test and barrel.** A file is a **test** if its path matches `*.test.*`, `*.spec.*`, or contains `/__fixtures__/` or `/__tests__/`. A file is a **barrel** if it has at least one outgoing `IMPORTS` edge, every outgoing `IMPORTS` edge has `reExport: true`, and no `Symbol` node has it as its `path`. Barrels are transparent: the importers of a barrel are importers of whatever it re-exports, transitively. A name collision can only make a file look like a barrel, which makes its importers count as consumers, the direction that errs toward `HOLDS`.
  - **Consumer.** A file `g` outside `M`, not a test, not a barrel, with an `IMPORTS` edge to `f` or to a barrel that transitively re-exports `f`. Importing a barrel counts as consuming everything it re-exports (an over-approximation, toward `HOLDS`).
  - **Result.** After the `code.ts` gate above, the first rule that applies gives the result, so a result has exactly one reason:
    1. `UNKNOWN(non-extracted-anchor)` if `M` is empty.
    2. `HOLDS` if some `f` in `M` has a consumer, or a bound path is itself an entry point (above). A positive result is found before every `Unknown` below and stands over it.
    3. `UNKNOWN(cross-package-unobservable)` if some `f` in `M` belongs to a package that has **dependents** (section 5.3).
    4. `UNKNOWN(non-extracted-anchor)` if some bound path had no `File` node.
    5. `UNKNOWN(manifest-unparseable)` if package discovery is incomplete (5.3: a `package.json` of a discovered package or the root's does not parse, or the workspace file is unreadable or holds an entry the reader does not support).
    6. Otherwise `UNKNOWN(no-static-consumer)`, with `detail` giving the size of `U`.

    There is no `ABSENT`, so there is no class that reports a control as unwired. Step 5 exists to name the reason: the dependents rule and the entry-point rule read manifests, and a manifest that cannot be read might list the claimed package among its dependencies or name the claimed file as its `bin`. Without the step the reader would be told only that the graph has no edge; with it the reader learns that part of the input was unread too. It changes no class. A row whose paths are whole packages (C3 and C8 below) has every consumer outside `M` in another package, so it is `Unknown(cross-package-unobservable)` for any package that has dependents, whatever entry points that package holds.

  - **Why the cross-package rule exists.** The extraction records **no `IMPORTS` edge that crosses a package**: 0 of 727 in the pre-fix tree (counted over the SIF in the pre-fix tree) and 0 of 978 on the code of main as of 2026-10-19 (counted over `SEAMLINE_DETERMINISTIC=1 seamline extract` with the four non-history extractors, all `PASS`), because a specifier such as `@seamline/core` resolves to `packages/core/dist/index.d.ts`, outside the file set the extractor reads (`packages/extract-code-ts/src/relations.ts:168`, `:174-179`, main). A module whose only consumers live in another package therefore has no inbound edge in this graph, and reading that as absence would call every library module "unwired". The rule gives that case its own reason, `cross-package-unobservable`, which tells the reader which part of the blindness applies and what would remove it (section 10). The other blind spots (the residue above) are named `no-static-consumer`. Both are `Unknown`, and the class does not depend on which one applies.
- **Completeness.** `presence-only`: the probe has no `ABSENT` result, by design (the residue above). `HOLDS` means only that the module is imported statically by non-test code outside itself, or is named as an entry point by the manifest: **referenced**, not proven to enforce anything. `Unknown(no-static-consumer)` means the graph records no static importer, and says nothing about whether another kind of consumer exists. The other reasons are as in 5.2.

## 5. Facts, probes and what "unknown" means

### 5.1 The run, and what pins a fact to a commit

Documents, manifests and sources are read at the evaluated commit. Graph-derived facts come from a **facts source**, one of two, and every probe that reads one asks the **scope table** defined below, never the bare list of extractors.

- **Store (default).** The store's runs (`RunRecord`, `packages/ontology/src/contract.ts:264`, main, has `commit: string | null`). **The commit rule** is applied to each run that supplies an entry of the scope table (the _supplying runs_, below). A supplying run whose `commit` is non-null and differs from the evaluated commit (full SHA) gives `UNKNOWN(run-commit-mismatch)` for every probe that reads the run (`RUNTIME_FLOOR` reads none). If every supplying run's `commit` is non-null and equal, `run.pairing` is `verified`. **A `null` commit is not a mismatch**: it means the pairing is unknown, exactly as for a SIF, so `run.pairing` is `asserted` (the caller asserts that the store was filled at the evaluated commit, and the command prints that the pairing is asserted, not verified). With `--worktree` the commit cannot be verified and `pairing` is `asserted`.
  **Today a store source cannot be verified.** `seamline extract` always records `commit: null`: `packages/cli/src/commands/extract.ts:230` (main) is `const run = { runId, repo: config.repo, commit: null, startedAt, ontologyVersion: '1.0.0' }`, and nothing else sets it. So a store written by `seamline extract` is always `asserted`; the `verified` and mismatch branches are reachable only for a store written by another producer. Recording the evaluated commit in `RunRecord.commit` is a later change (section 13) and needs no change to this rule. The self-proof uses `--facts` for that reason (12.1).
- **`--facts <file.sif>`.** A snapshot made at the evaluated commit, such as the committed `docs/dogfood/baseline/extract.sif` in the pre-fix tree (run id `run-deterministic-0000`; results `extract-code-ts`, `extract-data`, `extract-contracts`, `infer-join`, all `PASS`). **A SIF carries no commit**: `serializeSif` writes the header `{runId, t, version}` and one status line per extractor (`packages/cli/src/sif.ts:42-45` in the pre-fix tree, `:43-46` on main), and `RunRecord.commit` is not in it. So for a SIF source `run.commit` is `null`, **the commit rule is not applied**, **the caller asserts the pairing** between the file and `--at`, the packet records `facts.source: 'sif'` and `run.pairing: 'asserted'`, and `run.ontologyVersion` is `null`. The command prints that the pairing is asserted, not verified. Note (2026-11-10): as implemented, a SIF is format version 2 and its first record is the run record, which has `commit` and `ontologyVersion` fields (`serializeSif` in `packages/cli/src/sif.ts`). `seamline extract` writes `commit: null`, and for a SIF source the commit rule is still not applied and the pairing is still asserted (`runProvenance` in `packages/align/src/facts.ts`). `ontologyVersion` is read from the run record and is `null` only for a snapshot that has no run record (`packages/cli/src/align-port.ts`). A past commit must be evaluated against a snapshot made by that commit's own extraction: an engine from a later commit extracts capabilities the earlier tree lacked.

**The scope table.** For each scope named by an `authoritative` entry of a result, the table holds the scope's `status`, its declared `kinds` and the run that supplies the entry. The entry is taken from the **newest run that declared the scope**; when one run has several results on a scope, the worst status wins (`FAIL`, then `UNAVAILABLE`, then `PASS`) and the kinds are the union. This restates `scopeStatus` and `worseStatus` of the store (`packages/core/src/store/sqlite-store.ts:645-657` and `:138-142`, main), the rule the detectors' own gate applies. A SIF is one run. Two rules are added for a facts source that is a store:

1. **Not declared is not `PASS`.** A scope that no result of the source declares has no entry, and a scope without an entry is not `PASS`.
2. **A failed extractor does not fall back.** A crashed extractor may declare no scope (on 2026-10-19 `unavailable()` and `failed()` wrote `authoritative: []`, `packages/cli/src/commands/extract.ts:405-416` and `:450-461`, main; in 0.1.0 they declare their scopes, see the note in 4.3 step 4), and then the store's `scopeStatus` lets an older run's `PASS` stand for the scope of an extractor that failed in the newest run. An alignment report asserts a fact about one commit and must not: if the newest run holds a non-`PASS` result for an extractor, every scope that extractor declared in an earlier run is entered with that result's status. An extractor with **no** result in the newest run (a partial run made with `--only`) keeps its older entries, as `seamline check` does. If a crash declares its scopes with its non-`PASS` status (the shape `seamline extract` records in 0.1.0, see the note in 4.3 step 4), the newest-run rule above already enters them and this rule changes nothing.

A scope is **`PASS`** when the table holds it as `PASS`. `format-witness` and `module-wiring` need `code.ts` to be `PASS`; `detector-liveness` needs each of the detector's required scopes (4.3). The packet records the table as `run.scopes` (8.1).

### 5.2 Status mapping and the closed reasons

- A probe is `PASS`, `FAIL` or `UNAVAILABLE`, as extractors are (`packages/ontology/src/contract.ts:243`, main). Anything but `PASS`, and every `UNKNOWN(reason)` a probe returns, classifies as **Unknown**. A crashed or unsupported probe is never a missing fact. This is AGENTS.md invariant 3 and ADR-0003, applied to a second report.
- **A failed extraction, or one that never ran, cannot become absence.** A crashed extractor may be recorded with no scopes (on 2026-10-19 `unavailable()` and `failed()` did, `packages/cli/src/commands/extract.ts:405-416` and `:450-461`, main; in 0.1.0 they declare their scopes, see the note in 4.3 step 4), so the scopes it would have declared may be missing from the run. A probe that reads the run may therefore call something `ABSENT` only after it has asked the scope table (5.1) and found every scope it depends on declared and `PASS`: `detector-liveness` asks for each of the detector's own required scopes (4.3), and `format-witness` and `module-wiring` ask for `code.ts`, a deliberate conservative gate (their scans read source directly, but an alignment report is not made from a run in which the product's own code reading failed, and Resolved is computed across runs, section 7). A scope that no result declares answers the same as one that failed: `Unknown(scope-not-pass)`, with `detail` saying which. What the scope table cannot see is stated in 4.3 (Completeness) and section 14.
- **Closed reason set for Unknown:** `scope-not-pass`, `probe-failed`, `source-unreadable`, `manifest-unparseable`, `unsupported-range`, `non-extracted-anchor`, `claim-unanchored`, `reads-unresolvable`, `run-commit-mismatch`, `facts-missing`, `limit-exceeded`, `cannot-confirm-presence`, `no-source-roots`, `cross-package-unobservable`, `no-static-consumer`. `non-extracted-anchor` means that the fact may lie where the probe does not read: a bound path with no `File` node in the run (4.4), or a floor declared at a site other than the `engines` field that the probe reads, or at a site nearer than the `engines` it reads (4.1).
- **No network, no execution.** Probes parse; they never run repository code, never spawn a process other than reading git objects, and never open a socket. They read only the declared document globs, package manifests, `tsconfig*.json` files (for the output-to-source mapping below and the path-alias test of 4.2, which follows a relative `extends`), the list of tracked file names (for the name witnesses of 4.2 and the pin files of 4.1; the contents of those files are not read) and the source files of section 5.3.
- **Completeness is a property of the probe.** `exact` (only `RUNTIME_FLOOR`) means `HOLDS` and `DIFFERENT` are both conclusive. `absence-sound` (`format-witness` and `detector-liveness`, with the stated conditions) means only `ABSENT` is conclusive. `presence-only` (`module-wiring`) means the probe has no `ABSENT` result and its `HOLDS` is a weak witness. This matters in rules D7 and D8 below. Every `ABSENT` that any probe returns, `RUNTIME_FLOOR`'s included, is conclusive only over the closed set of sources that 5.4 lists for that probe.

### 5.3 Packages and the source universe

Used by `format-witness` and `module-wiring`, and by the extractor-package scan of `detector-liveness` (4.3).

- **Packages.** The directories matched by the root `pnpm-workspace.yaml` `packages:` entries, or else the root `package.json` `workspaces` array, that contain a `package.json` with a `name`; plus the root itself if its `package.json` has a `bin`. Zero packages: `UNKNOWN(no-source-roots)`, or `UNKNOWN(manifest-unparseable)` when discovery is incomplete (below).
- **The workspace reader.** It reads the file line by line and uses no YAML library. Blank lines and lines whose first non-space character is `#` are skipped. A line that starts in column 0 must be a top-level key (`name:`) or a `- ` item of the key above it, and a line indented with a tab is never valid: any other line (a merge-conflict marker, a document marker) makes the file unreadable. The entries are the `- ` items under the top-level key `packages:`, whose own line has no value (a flow sequence `packages: [...]` is unsupported). Each entry is a plain or a quoted (single or double) scalar with nothing after it, and its text is `/`-separated segments, each a literal made of `A-Z a-z 0-9 . _ @ -` or exactly `*`. An entry of any other form is **unsupported**: `**`, a `!` negation, a brace set, a segment that mixes `*` with other characters, a trailing comment, an anchor, an alias or a tag. Lines under other keys are ignored. When there is no `packages:` key, the root `package.json` `workspaces` value is read the same way and must be an array of such strings.
- **Incomplete discovery.** Package discovery is incomplete when a `package.json` of a discovered package, or the root's, does not parse, or when the workspace file is unreadable or holds an unsupported entry, or the root `workspaces` value is not an array of supported strings. An entry the reader does not read can hide whole packages (a `bin` package, a dependent, an extractor), so the reason is `UNKNOWN(manifest-unparseable)` for every one of these cases: the workspace file is a manifest for this purpose. A result that needs discovery to be complete is then `UNKNOWN(manifest-unparseable)`; a positive result already found stands. Those results are every `ABSENT` of `format-witness` (4.2, step 5), every `ABSENT` of `detector-liveness` (4.3, the extractor-package scan) and the `no-static-consumer` result of `module-wiring`, which becomes `manifest-unparseable` (4.4, Result, step 5). A package whose manifest does not parse, or that sits behind an entry that was not read, is not a discovered package, so its dependents, its `bin` and its source are unknown to the probe, not absent.
- **Dependents of a package.** The other discovered packages that list its name in `dependencies`, `optionalDependencies` or `peerDependencies` (not `devDependencies`: a `devDependencies` dependent only turns `no-static-consumer` into `cross-package-unobservable`, both `Unknown`, and the omission is deliberate; `format-witness` does put `devDependencies` in its closure, 4.2 step 3).
- **Source files of a package.** Every tracked file under the package directory with an extension in `.ts .mts .cts .tsx .js .jsx .mjs .cjs` (the extensions `packages/integration/src/semantic-boundary.test.ts` scans), wherever it sits (`src/`, `lib/`, `scripts/`), excluding declaration files, tests (the test rule of 4.4), `__fixtures__/`, `node_modules/` and the package's `compilerOptions.outDir`, plus the code file(s) named by `bin`, `main` and `exports`. Existing tracked `.json` resource targets are names, not TypeScript source (the resource rule below). A package whose code lives outside `src/`, or in `.cjs` or `.jsx`, is therefore inside a scan, not silently outside it. In the pre-fix tree and on main every such file of every package is under `src/` and none is `.cjs` or `.jsx`, so this changes no result of the self-proof. A source file **cannot be parsed** when the TypeScript parser reports at least one syntactic diagnostic for it (`ts.createSourceFile` never throws, so parse failure is not an error to catch). In the pre-fix tree and on main none of the source files of the discovered packages has one (176 and 207 files).
- **Other-language packages.** A scan-set package (4.2, step 3) or an extractor package (4.3, step 5) is **not wholly TypeScript or JavaScript** if a `bin` target of its manifest does not end in one of `.ts .mts .cts .tsx .js .jsx .mjs .cjs` (an npm shim around a native executable, a shell script, a target with no extension), or if the tree tracks under its directory a file with an extension of the closed list `.go .rs .py .rb .java .kt .c .cc .cpp .cs .swift .zig`. For such a package an unwitnessed format is `UNKNOWN(source-unreadable)`, never `ABSENT`: the code that renders output may be in the part the scan does not read. A witness found in the TypeScript or JavaScript part stands. An extractor package of that kind gives `UNKNOWN(source-unreadable)` for a kind it does not name, never dormancy, for the same reason. The list is closed on purpose and can only add `Unknown`. In the pre-fix tree and on main no scan-set package has either property (the extractor packages are among them), so this changes no result of the self-proof.
- **Output to source.** A `bin`, `main` or `exports` target string that lies under the package's `compilerOptions.outDir` (default `dist`, read from its `tsconfig.json` with the `typescript` package's JSON reader) is mapped to the same relative path under `rootDir` (default `src`) with `.js` read as `.ts`; declaration-file targets are dropped. If the mapped file does not exist, the file as named is used if it exists, else `UNKNOWN(source-unreadable)`. The mapped files are the package's **entry points** (4.4).

**JSON resource entry points.** An existing tracked `.json` target of `main` or `exports` is a resource, not executable TypeScript or JavaScript. It is omitted from syntax-token scans and the extractor-manifest mention scan, just as an ordinary JSON data file is. Its tracked basename and directory names retain the format-name scan of 4.2, including that scan's existing test, declaration-file, node_modules and output-directory exclusions; its manifest entry-point status for module wiring is unchanged. Classification is by extension and declaration, never by a package-specific allow-list. A JSON `bin` remains a non-JavaScript executable target and yields the existing other-language Unknown. Missing targets and unreadable JavaScript sources retain their existing Unknown behavior. An unknown non-code target must yield Unknown even if its contents happen to parse as TypeScript; it must neither be silently omitted as a resource nor parsed as implementation evidence. No unreadable source becomes a passing extraction scope.

This boundary admits the named consumer of section 12.1: self-alignment of a workspace that publicly exports JSON corpora as resources. JSON resource content can name formats or hold strings used by runtime code; this remains the explicitly unobserved data-content case of 4.2/5.4, not a claim that every possible renderer is statically visible. Code selected through resource content has the same limitation as code selected through any other data file. A kept source token or resource filename admitted by the 4.2 name scan and naming a format still prevents an ABSENT result.

The implementation of this amendment uses probe version 2, with the same version on both sides of a baseline comparison. Note (2026-11-10): as implemented there is one version number for all four probes (`PROBE_VERSION = 2` in `packages/align/src/types.ts`), so the "v1" beside each probe name in section 4 is the version that probe was first specified at, not the version a packet records. Regenerate the before packet from the original committed SIF; do not relabel an old Unknown as Resolved. Required controls assert the authoritative probe fact, not a rendered message or successful command exit:

- An ordinary JSON resource export whose content names a format only as data yields `ABSENT`, without opening its content as TypeScript. The extractor-manifest scan also ignores its content.
- A resource basename naming the format yields `HOLDS` when admitted by the unchanged 4.2 name scan. A resource under `outDir` remains excluded from that name scan, so an otherwise unwitnessed format yields `ABSENT`.
- A JavaScript witness reachable only through a manifest entry yields `HOLDS`. Use an existing output-directory fallback file that ordinary source discovery excludes, so dropping all manifest entries is killed.
- A non-JavaScript bin and a missing JavaScript export each yield `UNKNOWN(source-unreadable)` in the absence of a positive witness.
- An unknown non-code export with TypeScript-parseable content still yields `UNKNOWN(source-unreadable)`, killing indiscriminate parsing and broad resource omission.
- A module-wiring control proves the JSON resource remains a declared entry point independently of its omission from syntax scans.

Apply the applicable controls to both format and extractor-manifest scans. The standing records and fail-safe bounds in sections 12.1 and 12.2 remain acceptance requirements.

### 5.4 Absence is closed-world per probe

Three probes can answer `ABSENT`: `manifest-field`, `format-witness` and `detector-liveness`. (`module-wiring` cannot, 4.4, and has no entry here.) Each reads a **closed set of witness sources**, listed below, and one rule binds all three:

> **A probe answers `ABSENT` only over the sources it reads. If the evaluated tree contains a declaration or a source of a kind that the probe knows can carry the fact, and the probe does not read it, the answer is `UNKNOWN` with the reason named for that kind below, never `ABSENT`.** A witness that the probe did find stands over every `Unknown`.

An `Unexplained gap` says that the implementation lacks something; a probe that merely did not look has not shown that (AGENTS.md invariant 3). Each layout that moves the fact into a source the probe does not read would be a new false gap: a floor kept in a pin file, a library that a bundled CLI lists under `devDependencies`, a format selected by file name, an extractor kept in a package that declares its own manifest type. Handling such layouts one by one does not terminate, so the sources are written down here, per probe, and each known kind has a fires/does-not-fire fixture pair in 12.2. The same holds for a farther answer that a nearer source would overrule: a floor inherited from the root across a package that pins its own runtime in a file the probe does not read would be a false drift, and the floor is therefore inherited only across directories that hold no other floor site (4.1).

**`manifest-field` (`RUNTIME_FLOOR`, 4.1).**

- _Reads:_ the `engines.<runtime>` field of the tracked `package.json` files from the document's directory up to the root, taking the nearest that declares it, across directories that hold no other floor site.
- _Known sources it does not read_, each `UNKNOWN(non-extracted-anchor)`. When the walk found no `engines.<runtime>`: `engines.<runtime>` in a manifest off the walk; a `devEngines` or `volta` key in any manifest; `packageManager` beginning `pnpm@` (for pnpm) and `pnpm.executionEnv` (for node) in any manifest; tracked `.tool-versions`, `mise.toml`, `.mise.toml`, `.config/mise/config.toml` and `.mise/config.toml`, and for node `.nvmrc` and `.node-version`; a tracked `package.yaml` or `package.json5`; a tree with no `package.json`. When the walk found one in a farther manifest: any of the same sites in a directory nearer than the declaring manifest, and a nearer `package.json` that is not a discovered package. A manifest that does not parse is `UNKNOWN(manifest-unparseable)`.
- _Residue_ (the tree gives no evidence the probe can test): a floor pinned at a site that is a file whose presence says nothing about the floor, such as a CI workflow's `node-version`, a container image tag or the `use-node-version` setting of an `.npmrc`.

**`format-witness` (`OUTPUT_FORMAT_SET`, 4.2).**

- _Reads:_ the tokens (4.2 step 4) of the non-test source files of the scan set, which is the `bin` packages and the closure of the workspace packages they list in `dependencies`, `optionalDependencies`, `peerDependencies` and `devDependencies` (followed by key, by a `workspace:<name>@<range>` alias and by a path specifier that is a discovered package's directory), less the instrument; and the names of that set's tracked files, its directories and its declared dependencies.
- _Known sources it does not read:_ code in another language (a `bin` target that is not TypeScript or JavaScript, a tracked file of the closed list of 5.3) and a source file that cannot be read or parsed: `UNKNOWN(source-unreadable)`; a scanned file whose imports lead out of the scan set (a relative specifier that leaves the package directory, an import of a workspace package outside the set, a `tsconfig` that declares `paths` directly or through a relative `extends`); a dependency whose specifier names a path that is not a discovered package (`file:`, `link:`, `portal:`) or a `workspace:` target that is not one; a tracked `package.json` with `bin` that no discovery reached: `UNKNOWN(source-unreadable)`; a bound exceeded: `UNKNOWN(limit-exceeded)`; incomplete package discovery, or a tracked `package.json` that no discovery reached and that does not parse: `UNKNOWN(manifest-unparseable)`; no `bin` package: `UNKNOWN(no-source-roots)`.
- _Residue:_ a format selected only through a list (A1); a name that does not spell the format as separate words (an alias, a name run together, an acronym with a plural `s`); a renderer chosen through a computed specifier or a plugin path; a format named only by the content of a data or template file; a renderer in an executable that the CLI spawns by name, a tracked shell script among them (FW6); a `paths` entry in a base configuration that a `tsconfig` reaches through a bare `extends` (an installed package).

**`detector-liveness` (`DETECTOR_LIVENESS`, 4.3).**

- _Reads:_ the registry `ALL_DETECTORS`, each detector's `code`, `requiredScopes` and kind reads in its own file, the scope table of 5.1, and the names (string literals and identifiers) in the non-test source of every extractor package.
- _Known sources it does not read:_ a required scope that is not declared or not `PASS`, a non-`PASS` scope that declares the unproduced kind, an extractor package that names the kind but is not in the run, and a result of the run that did not pass, declares no scope and names an extractor that no package of the tree carries (the lost extractor, DL5): `UNKNOWN(scope-not-pass)`; a package that mentions `ExtractorManifest` counts as an extractor package even when it declares its own type, the vocabulary package `@seamline/ontology` alone excepted; an extractor package in another language, and a source file of any discovered package that cannot be read or parsed: `UNKNOWN(source-unreadable)`; a read whose kind is not a literal, a `requiredScopes` element that does not resolve, a detector with no read group: `UNKNOWN(reads-unresolvable)`; no extractor result: `UNKNOWN(facts-missing)`; a bound exceeded and incomplete package discovery as above.
- _Residue:_ an extractor outside the discovered packages whose failure the run does not record (a contrib or third-party extractor, `THREATMODEL.md` C13, DL1); a kind reached only through a constant imported from another package, read from a JSON file that the extractor imports (DL3), or built at run time; a package that is not named `extract-*`, is not `infer-join`, never mentions `ExtractorManifest` and builds its manifest by another route (E14); a detector that reads a kind optionally other than by the `||` rule; dormancy below the level of node kinds (`X3`, `X5`, `X7`, `X8`).

_What residue is._ The line this section draws is **a file the probe can recognise by name without parsing** it, or a key of a manifest the probe already parses, whose presence is itself evidence that the fact may be declared there: a `.nvmrc` exists to pin a version, and a `volta` key exists to pin a tool. Such a source is a known kind, and the probe must withhold on it. Residue is a source for which the tree holds no evidence that the probe can test: a file whose name does not say that it holds the fact (a CI workflow, an `.npmrc`, a `Dockerfile`, which hold a runtime version only sometimes, and which most repositories track, so that withholding on their presence would withhold on nearly every repository, while finding the version in them would need parsing that this section does not do), a computed specifier, a word inside a data file, an extractor elsewhere. It is a stated limit (section 14), pinned by a fixture where a fixture can show it (A1, E14), and it is the only place where an `ABSENT` can still be wrong toward reporting. Adding a source, a known kind or an `ABSENT` result to another probe is an amendment to this section, made together with the probe's own section and a fires/does-not-fire fixture pair per known kind in 12.2. A probe that cannot list its known kinds does not get an `ABSENT`.

## 6. Classification: the decision table

The subject universe is the union of the subjects of the claims at the evaluated commit and the subjects of the baseline's findings. For each subject, the engine has `claims(S)`: which polarities are present at the evaluated commit, across all documents. It also has `fact(S)` from the probe. `HOLDS` and `DIFFERENT` are decided **per claim** (two documents may say 22.11 and 22.13): `fact(S)` is `DIFFERENT` if at least one `AFFIRM` claim's value differs from the observed value (every differing claim is listed), and `HOLDS` only if all `AFFIRM` claims agree. The first matching row among D1 to D11 gives the **standing result**. A subject with several members (formats) is evaluated per member. A subject that has **no claim at the evaluated commit** (it comes from the baseline alone) has `claims(S)` empty. For `RUNTIME_FLOOR` and `CONTROL_ENFORCEMENT` no probe runs for it, because those probes take the claim's own document or row as input (the manifest is found by walking up from the document; the binding is read from the row), and its standing result is nothing, so a baseline drift on it resolves as `claim-removed` (section 7). For `OUTPUT_FORMAT_SET` and `DETECTOR_LIVENESS` the probe runs on the subject alone, and D1 and D10 apply. If the baseline's claims for the subject lay in a document whose input status at the evaluated commit is not `PASS` (a bound exceeded, or a blob that cannot be read), its standing result is `Unknown` with that document's reason (`limit-exceeded` or `source-unreadable`), never nothing: a claim that vanished with its unread document was not removed. Row R then says when a Resolved record is added; it needs the baseline, which D1 to D11 never consult.

| Row | `claims(S)`                                  | `fact(S)`               | Standing result                                                                                             |
| --- | -------------------------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------- |
| D1  | any                                          | `UNKNOWN(r)`            | **Unknown(r)**                                                                                              |
| D2  | AFFIRM (with or without markers)             | `DIFFERENT`             | **Observed drift** (`value-mismatch`)                                                                       |
| D3  | AFFIRM, no DEFERRED                          | `ABSENT`                | **Unexplained gap** (`absent-in-implementation`)                                                            |
| D4  | AFFIRM and DEFERRED                          | `ABSENT`                | **Planned gap** (`deferred-and-absent`), every claim, affirmative and deferred, listed in `claims`          |
| D5  | DEFERRED, no AFFIRM                          | `ABSENT`                | **Planned gap** (`deferred-and-absent`)                                                                     |
| D6  | AFFIRM only, or none                         | `HOLDS`                 | aligned: no finding; counted in `summary.aligned` if a claim exists                                         |
| D7  | DEFERRED (with or without AFFIRM)            | `HOLDS`                 | probe `exact`: **Observed drift** (`stale-deferral`). Any other probe: **Unknown(cannot-confirm-presence)** |
| D8  | ABSENT (with or without AFFIRM), no DEFERRED | `HOLDS`                 | probe `exact`: **Observed drift** (`stale-absence`). Any other probe: **Unknown(cannot-confirm-presence)**  |
| D9  | ABSENT only                                  | `ABSENT`                | aligned                                                                                                     |
| D10 | none                                         | `ABSENT` or `DIFFERENT` | nothing. Undocumented implementation is never reported.                                                     |
| D11 | any combination not matched above            | any                     | **Unknown(probe-failed)**, with `detail` naming the combination. Never aligned, never a gap.                |

D11 is a total-function guard. Today it is unreachable: only `RUNTIME_FLOOR` produces `DIFFERENT`, it has no markers and its claims are all `AFFIRM`, so `DIFFERENT` never meets a marker-only set. It makes a future probe that can produce one fail closed. Three rows are unreachable for a whole kind: `CONTROL_ENFORCEMENT` has no marker grammar and its probe has no `ABSENT` result, so it reaches only D1 (`Unknown`) and D6 (aligned), never D3, D4 or D5. A control is aligned or `Unknown`, never a gap.

`stale-deferral` and `stale-absence` Observed drift are **unreachable in v1**: they need an `exact` probe that also carries markers, and the only `exact` probe, `RUNTIME_FLOOR`, has none. They stay in the table so that a later `exact` probe needs no change to it. In v1 a marker beside a present feature is always `Unknown(cannot-confirm-presence)`, and the documents are not told that a marker is stale.

**Row R.** When a baseline is given and it reported drift (Observed drift or Unexplained gap) for S, a **Resolved** record is added if and only if the standing result is aligned, Planned gap, or nothing. It is never added when the standing result is Unknown, Observed drift or Unexplained gap (section 7).

Properties the table guarantees, each asserted by a test in the implementation:

1. **D1 beats everything.** A baseline drift whose subject is now Unknown stays Unknown. Resolution cannot be manufactured by a failing extraction.
2. **Nothing is derived from absence of a claim in the code direction.** D10 has no output. There is no class for an implementation no document mentions.
3. **Planned gap is not a suppression.** It is reported and counted. A DEFERRED marker on something the implementation has is `Unknown(cannot-confirm-presence)` in v1 and would be drift under an `exact` probe.
4. **Only Observed drift needs an exact probe for the stale rows**, so the project cannot report a stale document on the strength of a weak witness.
5. **A gap needs a probe that can see absence.** D3, D4 and D5 take an `ABSENT` fact, and `module-wiring` has none, so the blind spots of the extraction (4.4) cannot become a gap.
6. **An `ABSENT` fact is closed-world.** D3, D4, D5 and D9 take their `ABSENT` from a probe that read every source it knows can carry the fact (5.4). A source of a known kind that it did not read arrives as `UNKNOWN(r)`, D1 beats everything, and so a layout that moves the fact into such a source cannot produce a gap.

Class order for display and for the packet: Observed drift, Unexplained gap, Planned gap, Unknown, Resolved.

## 7. Baseline and Resolved

`Resolved` exists only when a baseline packet is supplied (`--baseline <packet>`). The baseline is read as data: its `schemaVersion` must be 1 and its digest must verify, else the command fails with a usage error. A baseline's `subject.commit` need not be an ancestor of the evaluated commit.

For each baseline finding with class Observed drift or Unexplained gap, matched by `id`, the head evaluation produces a **Resolved** record when the head standing result is aligned, Planned gap, or no claim (row R). The record carries `resolved.from` (the baseline class), `resolved.by`, and the baseline's `digests`:

| `resolved.by`            | Condition                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------- |
| `claim-corrected`        | the claim digest changed and the fact digest did not                                        |
| `claim-removed`          | no claim exists at head for the subject                                                     |
| `fact-changed`           | the fact digest changed and the claim digest did not                                        |
| `claim-and-fact-changed` | both changed                                                                                |
| `explained`              | head's standing result is a Planned gap (the discrepancy remains, the document now says so) |

The conditions are checked in this order: `explained`, then `claim-removed` (only when the documents that held the baseline claims were read, section 6), then the three digest rows. For a Resolved record, `reason` equals `resolved.by`. `claim-removed` is reported distinctly so that a "fix" that merely deletes a sentence is visible as such. Baseline findings of class Unknown, Planned gap or Resolved never produce a Resolved record. A Resolved record has the same `id` as the baseline finding it resolves; uniqueness in a packet is `(id, class)`, so one subject can appear as a standing Planned gap and as a Resolved record at once (for a baseline drift that becomes a Planned gap). `fact-changed` also covers a presence witness that appears: a `HOLDS` is an aligned result, so a baseline Unexplained gap whose claim is unchanged resolves when a token or a name that carries the format shows up in the scan set (4.2, Completeness; H1 to H1c in 12.2), and `fact.detail` says whether it was a token or a name.

**Digests of a finding** (defined here because the rows above compare them). `digests.claim` is the SHA-256 of the sorted claim digests (section 3.3) of the finding's claims joined by LF, or `null` when it has none. `digests.fact` is the SHA-256 of canonical JSON of `{ probe, probeVersion, observed, binding }`, plus `result` **only when the result is `ABSENT` or `UNKNOWN`**, and nothing else: not `detail`, not `source`, not any commit, line number or scan count. `HOLDS` and `DIFFERENT` are left out on purpose: they are the outcome of comparing the claim with the fact, so they change when only the document changes, while `ABSENT` and `UNKNOWN` are properties of the implementation side alone. With this definition a document-only correction of the Node floor (the claim moves from 22.11.0 to 22.13.0; `observed` stays `22.13.0`; the comparison moves from `DIFFERENT` to `HOLDS`) changes the claim digest and not the fact digest, which is `claim-corrected`; a change to `engines` alone changes `observed`, which is `fact-changed`. `observed` is path-free by construction (8.1). Because the digests carry no path, no line, no commit and no excerpt, `git mv` of a document, or a reworded sentence of the same meaning, changes neither, and a change in the redactor's rules cannot change them.

## 8. The finding packet, schema v1

### 8.1 Shape

```
Packet {
  schema         : 'seamline.alignment-packet'
  schemaVersion  : 1
  repo           : string                           // the repository slug used in node ids
  producer       : { tool: 'seamline', toolVersion, alignVersion: 1, sifVersion }
  subject        : { commit: string | null, worktree: boolean }   // commit: full SHA; null with --worktree
  run            : { runId, commit: string | null, ontologyVersion: string | null,
                     pairing: 'verified' | 'asserted',
                     extractors: [ { name, version, status: 'PASS'|'FAIL'|'UNAVAILABLE', scopes: [string] } ],
                     scopes: [ { scope, status: 'PASS'|'FAIL'|'UNAVAILABLE', kinds: [string], runId } ],   // the scope table, 5.1
                     facts: { source: 'store' | 'sif', digest: 'sha256:<hex>' } }
  inputs         : { docs:   [ { path, sha256, status, claims: number, diagnostics: [string] } ],
                     probes: [ { probe, version, status, diagnostics: [string] } ],
                     excluded: [string] }
  baseline       : null | { digest, commit: string | null, runId: string | null }
  summary        : { classes: { 'Observed drift': n, 'Unexplained gap': n, 'Planned gap': n, 'Unknown': n, 'Resolved': n },
                     claims: n, aligned: n }                 // aligned: subjects that are aligned (D6, D9), not claims
  sensitivity    : 'internal'
  untrustedFields: [ 'findings[].claims[].excerpt', 'findings[].fact.detail', 'findings[].unknown.detail', 'inputs.*.diagnostics[]' ]
  findings       : [ Finding ]
  proposals      : [ Proposal ]
  digest         : 'sha256:<hex>'
}

Finding {
  id         : string                     // 8.2
  class      : 'Observed drift' | 'Unexplained gap' | 'Planned gap' | 'Unknown' | 'Resolved'
  claimKind  : 'RUNTIME_FLOOR' | 'OUTPUT_FORMAT_SET' | 'DETECTOR_LIVENESS' | 'CONTROL_ENFORCEMENT'
  subject    : string
  member     : string | null
  reason     : string                     // closed set, sections 5 and 6
  claims     : [ Claim ]                  // section 3.3; the claims behind this result, may be empty for Resolved
  fact       : null | { probe, probeVersion, status, provenance: 'EXTRACTED' | 'DECLARED',
                        result: 'HOLDS' | 'DIFFERENT' | 'ABSENT' | 'UNKNOWN',
                        observed: string | boolean | null,    // table below
                        binding: 'B1' | null, detail: string,
                        source: null | { path, lineStart, lineEnd, commit } }
  unknown    : null | { reason, scopes: [string], detail: string }
  resolved   : null | { from: 'Observed drift' | 'Unexplained gap', by: string,
                        baseline: { claimDigest, factDigest } }
  digests    : { claim: 'sha256:<hex>' | null, fact: 'sha256:<hex>' | null }
}

Proposal {
  id          : string                    // '<repo>:align-proposal:<claimKind>:<subject>:<n>'
  claimKind, subject
  provenance  : 'INFERRED'
  basis       : 'name-match'
  candidate   : { kind: 'File', canonicalName: string }   // the repo-relative POSIX path: a locator field, not part of any id
  note        : string                                    // untrusted; names the shared wording
}
```

`fact.observed` by claim kind: `RUNTIME_FLOOR` the normalised string `X.Y.Z` of the manifest (`null` when `ABSENT` or `UNKNOWN`); `OUTPUT_FORMAT_SET` a boolean, whether the format is witnessed; `DETECTOR_LIVENESS` a boolean, whether every read group has a produced member; `CONTROL_ENFORCEMENT` `true` when a static consumer or an entry point is found (`HOLDS`) and `null` otherwise (the probe never reports `false`, because it cannot see the absence of a consumer). A version is a string, never a number, so `22.10` and `22.1` stay distinct. There are no timestamps, no durations, no absolute paths, no machine names and no confidence field. A confidence score would invite a threshold, and classification here is exact.

**Counts.** `summary.claims` is the number of claims in all the documents read. A statement of the form "N claims in M documents", in a packet field, a message or a test, takes M as the number of documents **read** (the entries of `inputs.docs`, whatever their `status` or `claims` value), never the number of documents that carry a claim: a document with `claims: 0` was read and is counted.

### 8.2 Ids: stable and path-free

`id = <repo>:align:<claimKind>:<subject>` with no member suffix: for a set-valued kind the subject already names the member (`cli:output-format:csv`), and the `member` field repeats it for grouping. For example `seamline:align:RUNTIME_FLOOR:runtime:node`, `seamline:align:OUTPUT_FORMAT_SET:cli:output-format:csv`, `seamline:align:DETECTOR_LIVENESS:detector:X10`, `seamline:align:CONTROL_ENFORCEMENT:control:C4`. The subject is built only from the semantic keys in section 4 (a runtime name, a format name, a detector code, a control id, an npm package name), never from a file path, a line number, a commit, or a document's wording. Moving a document with `git mv` changes `claims[].source.path`, `inputs.docs[].path` and the packet-level `digest`, and nothing else: not an `id`, not a per-finding digest. This is AGENTS.md invariant 1, and the same argument as ADR-0002: a natural key is reproducible, diffable and debuggable, and a hash would add nothing but opacity.

The class is not part of the id, because the same discrepancy moves between classes as the repository changes, and the id must follow it.

### 8.3 Byte-reproducibility

The packet is serialised as UTF-8, LF, object keys sorted by UTF-16 code unit, two-space indent, one trailing newline, integers only. Arrays are ordered: `findings` by (class order, `id`); `claims` by (`source.path`, `source.lineStart`, `digest`); `inputs.docs` by `path`; `inputs.probes` by `probe`; `run.extractors` by `name`; `proposals` by `id`. `digest` is the SHA-256 (`node:crypto`) of the serialised bytes with the `digest` field omitted.

**Reproducibility is relative to the run.** Two runs of `align` on the same commit, the same facts source and the same baseline, from different working directories and time zones, produce the same bytes (AGENTS.md invariant 4; ADR-0009), and no wall-clock time is read by `align`. But `run.runId`, and the `firstSeenRun` and `lastSeenRun` values inside the SIF, come from `deps.clock.runId()` (`packages/cli/src/commands/extract.ts:197`, main), which is not fixed outside `SEAMLINE_DETERMINISTIC=1`. Re-extracting an identical tree can therefore change `run.runId` and `facts.digest` (the SHA-256 of the SIF bytes, which embed those ids), and so the packet's bytes. The guarantee is: same inputs including the same run record, same bytes. The self-proof (section 12) pins the run by using the committed SIF and a deterministic extraction.

### 8.4 Run provenance

`subject.commit` is the evaluated commit; `run` is the `RunRecord` of the extraction the graph facts came from (`packages/ontology/src/contract.ts:264`, main; for a store, the newest run), or the equivalent read from a SIF (section 5.1), reduced to its identity, its extractor results and the scope table the probes used (`run.scopes`, which names the run that supplies each scope). `run.facts.digest` is the SHA-256 of the SIF bytes, or, for a store source, of the canonical JSON of the newest run record and `run.scopes`. A consumer can therefore tell exactly which tree, which extractors at which versions, which statuses, and whether the pairing of tree and run was verified or asserted. Claim provenance is on each claim; fact provenance is on each fact.

### 8.5 Redaction: the existing redactor is the sole writer

- Every string that is **free text** (`claims[].excerpt`, `fact.detail`, `unknown.detail`, every `diagnostics[]` entry, `proposals[].note`) passes through the existing redactor's `redactString(text, target, field)` (declared on the `Redactor` interface at `packages/core/src/security/redactor.ts:268`, implemented at `:299`, main). A matched secret becomes a reference. Note (2026-11-10): the redactor is now in the separate package `@seamline/security` (`packages/security/src/redactor.ts`), and `@seamline/core` re-exports it; `packages/core/src/security/redactor.ts` no longer exists.
- Every **identity and locator** field (`id`, `subject`, `member`, `repo`, every `source.path`, `source.commit`, `inputs.docs[].path`, `candidate.canonicalName`) follows [ADR-0013](../adr/ADR-0013-redactor-never-rewrites-identity.md): never rewritten; a closed-format credential in one refuses the whole packet. No partial packet is written; the command exits 3 and its message names the rule and field and never the credential. The redactor guards these fields with an internal function (`keepStructural`, `redactor.ts:333`, main) that is not on the `Redactor` interface. If the interface offers no entry point for applying that rule to a plain string, the implementation adds one, additively, to the same module (`redactor.ts`), and does not add a second scanner.
- **One writer, enforced structurally** as in ADR-0011: the serialiser accepts only an opaque `RedactedPacket`, which only the redaction function can construct, and the `@seamline/align` package contains exactly one site that writes a file or stdout. A test fails if a second appears. **Every output of `seamline align` goes through that site**, the summaries of section 8.8 included: they are projections of the `RedactedPacket`, not a second path.
- Tests assert outcomes: a canary secret planted in a document sentence, in a manifest value and in a code identifier appears nowhere in the bytes written or in stdout; a canary in a document's path refuses the packet.

### 8.6 Proposals

A proposal records a candidate link that is not anchored. In v1 the only producer is for a `CONTROL_ENFORCEMENT` row that came out `Unknown(claim-unanchored)`, and no model is called. A **candidate** is a non-test TypeScript or JavaScript file whose **header comment** (the first block comment, before any statement; lines joined with the leading `*` removed) shares at least **two** word 2-grams with the row's second cell.

- **2-grams.** Computed on lower-cased text in which each code span, and each of the characters `. ! ? ; : ( ) , |`, ends a run of words. A word is a maximal run of `[a-z0-9]`, so `allow-list` is the words `allow` and `list`. A 2-gram is two adjacent words of one run, and it is ignored if either word is in the closed stop list `a an and are as at be by for from in is it of on or the to with`.
- **Order and cap.** At most five per claim, ordered by (number of shared 2-grams descending, path ascending). `note` lists the shared 2-grams. `provenance` is `INFERRED` and `basis` is `name-match`.
- **In the pre-fix tree** the C4 row yields exactly two proposals (replayed over the tree at that commit): `packages/core/src/security/sandbox.ts`, ranked first with three shared 2-grams ("allow list", "capability manifest", "provenance ceiling"; its header reads "The capability manifest in `ExtractorManifest` is enforced here"), and `packages/infer-join/src/manifest.ts` with two ("capability manifest", "provenance ceiling"). Thirteen other files share one 2-gram and are below the minimum.

The classifier never reads `proposals`; a test removes them and asserts the findings are byte-identical. A proposal becomes a claim only when a human edits the document to add the anchor (a path in the row), after which the next run reads it as a `DECLARED` claim with binding B1.

### 8.7 Versioning

`schemaVersion` is the integer 1. Within version 1 a producer never removes, renames or retypes a field. It may add fields, and a consumer must ignore fields it does not know. A breaking change is version 2 with the deprecation window of aspirational-state 4.2.

### 8.8 Export stays default-deny

Producing packet bytes (to a file or to stdout) requires `--profile <name>`, and the named profile must opt in with the optional key `packets: ['alignment']` on `ExportProfile` (`packages/core/src/security/export-profile.ts`; the key is absent from the canonical form when it is not named). Absent means none, so every profile that exists today keeps denying. The export profile format has no single sensitivity ceiling (its `allow` lists `(kind, sensitivity)` pairs), so the packet's sensitivity is a per-kind statement: the packet names files by repository-relative path, which is a `File` at `internal`, and it can name symbols, which is a `Symbol` at `internal`; everything else in it is text from documents and manifests rather than a graph node. The profile is accepted only if its `allow` lists `(File, internal)` and `(Symbol, internal)`; where it is unclear whether a kind is carried, the stricter reading is taken. If it does not, the command refuses with a usage error and writes nothing, as `export` refuses without a profile. There is no flag to emit a packet without a profile, and the existing `seamline export` is unchanged and never emits one.

Without a profile, `seamline align` prints a human summary and, with `--json`, a **summary object**: class counts, a `documentsNotReadInFull` count with closed reasons (documents skipped for a bound, unreadable, or read only up to a line bound, so that a document that could not be read never reads as clean; no path), and per finding only `id`, `class`, `claimKind`, `member`, `reason`. It carries no excerpt, no observed value and no source path. It is built from the `RedactedPacket` and written through the single write site (8.5), so it is redacted like the packet. `id` includes the subject, which can include an npm package name; that is the same disclosure `seamline check` already makes without a profile (node names and ids on stdout), and it is not an export of the store.

## 9. The command, gating and the packaging

```
seamline align [--at <rev> | --worktree] [--facts <file.sif>] [--baseline <packet>]
               [--profile <name> [--packet <file>]] [--store <dir>] [--json]
```

`--repo <path>` is a global `seamline` option and applies to `align` as to every command.

- **Exit codes.** 0 whenever a report was produced, whatever it contains. 2 for usage errors (unknown revision, `--packet` without a profile, a profile without `packets: ['alignment']`, a baseline that does not verify). 3 for runtime errors (a redaction refusal, an unreadable facts file). The existing constants are `packages/cli/src/io.ts:15-18` (main). These are the only non-zero paths and none depends on what drift was found. There is **no flag, environment variable or configuration key that makes drift fail**, and none is to be added without amending ADR-0014.
- **`seamline check` is unchanged.** Its report, its JSON and its exit code stay as at `packages/cli/src/commands/check.ts:95,108` and `packages/cli/src/render.ts:17-19` (main); X1 to X10 keep their gating. A regression test runs `check` on a repository with every kind of drift and on the same repository without, and asserts byte-identical output and equal exit codes.
- **Wiring.** A new workspace package `@seamline/align` (private until the release step assigns it a tier) holds the scanner, the claim kinds, the probes, the classifier, the baseline logic and the packet. It depends on `@seamline/ontology`, `@seamline/core` (the redactor) and the `typescript` package already used by `extract-code-ts`; it adds no third-party dependency. Note (2026-11-10): as implemented, `@seamline/align` is published in 0.1.0, and `typescript` is an optional peer dependency of it, not a dependency; without it the probes that parse TypeScript source answer `Unknown(probe-failed)`, see `packages/align/src/ts.ts`. `packages/cli/src/commands/align.ts` follows the existing ports pattern (`packages/cli/src/ports.ts`, `packages/cli/src/run.ts`).
- **Outside the contradiction pipeline.** ADR-0014 decides that alignment is a second report family **beside** the contradiction pipeline (extract, merge, infer-join, X1 to X10, check, export, MCP), not a stage of it. No pipeline stage imports `@seamline/align`: the CLI package is in `PIPELINE_PACKAGES` (`packages/integration/src/semantic-boundary.test.ts:52-66`, main), and within it only the `align` command (a report command beside the stages, not one of them) does. The implementing change must classify `@seamline/align` in the package lists of the semantic-boundary test that ADR-0015 adds (`PIPELINE_PACKAGES` and `NON_PIPELINE_PACKAGES` in `packages/integration/src/semantic-boundary.test.ts`, which fails on an unclassified package): it goes in **`PIPELINE_PACKAGES`**, the strict list, because the alignment code must not import the optional semantic layer of ADR-0012 either (section 11, Fusion). Note (2026-11-10): done; `'align'` is in `PIPELINE_PACKAGES`.
- **Not an extractor.** The scanner and probes write no nodes and no edges, have no scope, run only under `align`, and are not registered with `extract`. They are not a fourth source extractor in the sense of aspirational 6B.5 (ADR-0014, section 6, gives the argument). They still follow the extractor controls that make sense for a reader: declared inputs only, no network, bounded work, fixed output.
- **Not persisted.** Nothing is added to the store and no schema migration is needed. The baseline is a file the caller keeps.
- **Threat model.** The implementation amends `THREATMODEL.md` to record the new input class (document text from a contributor is untrusted, excerpts carry `untrusted`, and every renderer delimits them as C6 requires), the bounds in 3.1, and that grammars are linear-time.

## 10. Ontology and contract impact

**None.** `packages/ontology/src/contract.ts` and `ontology/seamline.yaml` are not changed. Claims are not graph nodes, so no node kind, edge kind, signature or sensitivity is added; the packet is a separate artifact with its own versioned schema.

Considered and not taken: add `Document` and `Claim` node kinds and a `CLAIMS_ABOUT` edge from `Claim` to `Symbol`, `Column`, `Operation` or `File`. That would be an ontology change under v3 section 7's evolution test and would bring claims under run and tombstone semantics. It is the right shape only if a later consumer needs claims queryable through the store or the MCP server, and that is a separate design pass. If it is ever taken, the exact change is: `NODE_KINDS` gains `Document` and `Claim`; `EDGE_KINDS` gains `CLAIMS_ABOUT`; `EDGE_SIGNATURES` gains `CLAIMS_ABOUT: [['Claim','Symbol'], ['Claim','Column'], ['Claim','Operation'], ['Claim','File']]`; `DEFAULT_SENSITIVITY` is unchanged (both default `internal`); and the YAML source and the generated vocabulary are regenerated.

Also considered and not taken: emit cross-package `IMPORTS` edges from `extract-code-ts` (resolving a workspace specifier to its source file), which would let `module-wiring` see consumers in other packages. It would not by itself make absence reportable: a dynamic `import()`, a `require()`, a `new URL(..., import.meta.url)` and a path named in a script would still be unrecorded (4.4), so a probe that reports a control as unwired needs an extraction that records all of them, and its own design pass. The change alters extraction output and the dogfood baseline. Until then the probe answers `Unknown` (`cross-package-unobservable` or `no-static-consumer`) rather than guess.

## 11. Out of scope

Not admitted by this design, each needing its own admission under aspirational 5.3 or a new adversarial review under 6A:

- **Runtime or infrastructure observation** of any kind: no database, cluster, cloud, process or network introspection, and no reading of state or plan files (aspirational 6A.2).
- **New capability families.** No new extractor, no new node or edge kind, no fifth claim kind, no claims about prose beyond the templates above, no checks of severities, descriptions, counts or links.
- **Fusion.** No merge of alignment output with the semantic engine of ADR-0012, no import of it, no use of it as input to a contradiction detector, and no use of drift as a fact for any gate.
- **Anything that makes drift gate**, scores it, adds a waiver, or reports code that no document mentions.
- **Models in the path.** No language model reads a document or classifies a finding (aspirational 6A.4); a model may only be the source of a proposal, and v1 has none.
- **A web viewer, a hosted service, telemetry, a network call.**
- **Re-expansion toward v2.** This adds one command and four claim kinds; it does not add lenses, scorecards, a readiness score or a needs matrix.
- **MCP tools** for alignment (agent-facing work, not shipped today), and any lifting of the packet into the store.
- **Other declared entities and non-Markdown documentation** (YAML annotation strings such as `ontology/seamline.yaml`, source comments, HTML) and non-TypeScript sources for the code probes.

### 12.4 Implementation resolutions

The design left eight points open that the implementation had to decide. Each choice below fails toward `Unknown`, never toward absence, and each has a test.

1. **A list item can yield two claims.** When a list item's lead label and one of its sentences both
   carry a dormancy marker for the same code (`README.md:173` in the pre-fix tree, the `X5` item), both claims
   are kept. They share a subject, are identical in meaning and classify identically, and findings
   merge claims by subject. Both claims must remain in the actual per-packet counts reported under
   12.1; dropping the second changes those counts. The original baseline has 34 claims; head totals
   must be measured for its pinned SHA.
2. **The code-span wording of 4.3** is corrected above: on main the `X10` label is plain text, and both forms fire.
3. **Reason order for `OUTPUT_FORMAT_SET`.** The gate of 4.2 (`scope-not-pass`) is tried first and wins over everything below. With no root package (no workspace package declares a `bin`), `format-witness` answers, in order: incomplete discovery (`manifest-unparseable`), a stray `bin` it cannot scan (`source-unreadable`), a stray unparseable manifest (`manifest-unparseable`), and otherwise `no-source-roots`. With a root, it answers in order: an unreadable file in the scan set (`source-unreadable`), a stray `bin` (`source-unreadable`), an exceeded bound (`limit-exceeded`), incomplete discovery (`manifest-unparseable`), a stray unparseable manifest (`manifest-unparseable`), and only then `ABSENT`. A witness found at any point earlier returns `HOLDS` first.
4. **An over-long line.** Only the first 4096 characters of a line are matched. Claims found in that prefix are kept, and the document is recorded `FAIL` with `limit-exceeded` and a diagnostic naming the first such line. A positive found on a prefix stands (a positive result is found before every `Unknown`, as in 4.4); truncation can drop a claim, never create absence, and the summary names the document as not read in full (8.8).
5. **The `@<package>` suffix of a floor subject** is added only for a document that lives under a discovered non-root package (5.3). A manifest outside the workspace entries gives its documents no suffix, so such a claim never merges with the root subject `runtime:node`.
6. **`inputs.docs[].sha256`** is the bare lower-case hex SHA-256 of the document's bytes, without the `sha256:` tag the other packet digests carry, and `null` when the bytes were never read (a document skipped by the document-count bound, a document after the claim cap, or an unreadable blob). A document over the size bound but within the preload still carries its hash, and so does the document that tips the claim cap.
7. **An unparseable `tsconfig*.json` in the paths check of 4.2** is treated as one that may declare `compilerOptions.paths`, because it cannot be read as a tsconfig. That is `Unknown(source-unreadable)` for an unwitnessed format, never a gap.
8. **The run id of a failed extractor's scope-table entry (5.1).** When an extractor's newest result is not `PASS` and its scopes come from an earlier declaration, the entry takes the **newest** run's id, because that run's result supplies the status; the kinds come from the earlier declaration.

Facts reach the probes through `isFact()` only: `File` and `Symbol` nodes and `IMPORTS` edges that are `INFERRED` or `LLM_SUGGESTED` are dropped by the store and SIF adapter (AGENTS.md invariant 5).

## 14. Risks, stated

- **Template brittleness.** A reworded sentence drops a claim silently. Mitigations are partial: the `claim-removed` reason, the per-document claim counts, and the fires/does-not-fire pairs. This is the cost of refusing free-prose reading, and it is a smaller cost than a guess presented as a finding. A marker inside a parenthetical (`v3.md:260` in the pre-fix tree) is not seen. The `DEFERRED` detector markers are the one non-template rule (3.2, 4.3): a code and a cue anywhere in a label or a sentence, with range phrases excluded. They can produce a wrong `Planned gap` or a wrong `Unknown(cannot-confirm-presence)`, never drift.
- **A control row that names no code is `Unknown`.** That is the intended failure direction: not aligned, not resolved, not a guess. It also means the tool did not find the C4 defect in the pre-fix tree; it found that the document could not be checked, and said why. A row that names code the extraction does not read, whole packages that have dependents, or a path that holds only tests, is `Unknown` too (`non-extracted-anchor`, `cross-package-unobservable`), and so is a module with no recorded static importer (`no-static-consumer`). A control row is confirmed only when it names a module that a non-test file imports statically, or an entry point of a package.
- **Weak `HOLDS`.** `format-witness` and `detector-liveness` can only prove absence, and `module-wiring` can only prove presence; none of them proves that a feature works. `format-witness` `HOLDS` is a word in an identifier or property name, in a string that a comparison or a `case` tests, or in the name of a file, a directory or a dependency; `module-wiring` `HOLDS` is a non-test static import, or a bound path that is an entry point of its package. The cost is missed drift (a stale marker beside a present feature reads as `Unknown(cannot-confirm-presence)`), never invented drift. A `HOLDS` can still produce a `Resolved` record: a name witness (a stub file named for the format, an unused dependency) resolves a baseline gap while the feature is not there. `Resolved` is a class, so this is a false `Resolved`, not a false drift; it is visible as `fact-changed` with a `fact.detail` that begins `name`.
- **Format `ABSENT` can still be wrong toward reporting, in the ways listed.** The witness rule of 4.2 does not count a name that only sits in an array, a `Set` or a call argument, because lists of names collide with unrelated code (the MySQL engine names of `packages/extract-data/src/clickhouse.ts:104` hold `'csv'`). A CLI that selects a format only through `['json', 'csv'].includes(format)`, with no comparison, no `case` and no identifier, property, file, directory or dependency name carrying the word, would get an `Unexplained gap` for a statement that is true, and the fixture A1 of 12.2 pins it. The other ways are the `format-witness` residue of 5.4: a name that does not spell the format as separate words (including an acronym with a plural `s`), a renderer chosen through a computed specifier or a plugin path, a format named only by the content of a data or template file, a renderer in an executable that the CLI spawns by name (a tracked shell script, FW6), and a path alias set in a base configuration that is installed from a package. The tree gives the probe no evidence of any of them, so it cannot withhold on them; every case it can see (another language, an unparseable file, an import that leaves the scan set, a path alias, also through a relative `extends`, a dependency that names a path or an alias it cannot resolve, a `bin` package that no discovery reached, incomplete discovery) it does withhold on.
- **Absence is closed-world per probe (5.4).** Every probe that can answer `ABSENT` lists the sources it reads and the sources of known kinds it does not, and answers `Unknown` when the tree holds one of the latter. What remains is residue the tree gives no evidence of. For the floor, it is a pin at a site the probe has no entry for (a CI workflow's `node-version`, a container image tag, an `.npmrc` `use-node-version`): a document that states a floor pinned only there is an `Unexplained gap` for `runtime:node`. For detector liveness, it is an extractor outside the discovered packages and a kind reached only through an imported constant. The cost of the rule runs the other way: an `Unknown` where a person would call the claim a gap or a drift (a package document whose sibling package declares the floor, a package that pins its runtime beside a farther `engines`, a documentation-site manifest outside the workspace, a `paths` entry that only maps a package to itself), which is the intended direction.
- **Non-TypeScript sources.** A scan-set package that is not wholly TypeScript or JavaScript (a `bin` target that is not a TypeScript or JavaScript file, or a tracked file of the closed list of other languages in 5.3) gives `Unknown(source-unreadable)` for an unwitnessed format, never a gap, and an extractor package of that kind does the same for a detector's unproduced kind, never dormancy. Two of the four kinds are repository-shaped already (below); a repository whose CLI is a native executable behind a thin npm shim reads as `Unknown`, which is the honest output.
- **Incomplete package discovery withholds absence.** An unparseable `package.json` of a discovered package or of the root, a workspace file the reader cannot read, and a workspace entry it does not support (`**`, a `!` negation, a brace set, flow-style YAML, a trailing comment) leave package discovery incomplete, and every `ABSENT` of the two probes that report it becomes `Unknown(manifest-unparseable)` (5.3), because the dependents, the `bin` and the source of the packages that were not read are unknown. `module-wiring` has no `ABSENT`; its `no-static-consumer` becomes the same reason, so the reader sees the unread input.
- **Kind-level dormancy and the read model.** `X3`, `X5`, `X7` and `X8` are dormant for reasons below the level of node kinds. This design reports `X10` only. They are not claimed live: the packet names the probe's level. A detector that reads a kind optionally would be over-reported dormant (4.3).
- **Catalogs and pages the anchors do not read.** The per-code catalog in `docs/contradictions/README.md` (its first column holds links, and it carries a "Status today" column) is the clearest statement of which detectors fire, and it is not read, because its cells do not match the catalog anchor (4.3). Output-format sentences in parentheticals, and declared entities other than `package.json`, are not read either. All of these are silent: absent claims, not wrong ones.
- **Cross-package blindness of the graph.** The extraction records no import that crosses a package, so `module-wiring` answers `Unknown(cross-package-unobservable)` for a module in a package with dependents. Section 10 records the extraction change that would remove the limit.
- **Self-reference.** Two of four kinds apply only to repositories shaped like this one. The packet and classes are general; the checks are not, and the ADR says so. The tool's own lexicons would witness every format in a self-run, which is why `@seamline/align` is excluded from `format-witness`.
- **What the scope table cannot see.** `detector-liveness` is as strong as the detector's own
  `requiredScopes`. An extractor that is absent from the run, or that crashed and so may have declared
  no scope, and whose scope the detector does not list, is invisible to `seamline check`, and to this
  probe unless its source is in the tree: the extractor-package scan (4.3, step 5) turns a kind named
  as a string literal or an identifier in an extractor package into `Unknown(scope-not-pass)`, so
  `extract-tests` declaring `TestCase`, missing from a run, cannot make `X10` read as dormant. What
  remains invisible is an extractor outside the discovered packages whose failure the run does not
  record (a contrib or third-party extractor, `THREATMODEL.md` C13; one that the run records as failed
  with no scope is the lost extractor of 4.3 and gives `Unknown`), a kind named by no literal or
  identifier (including one read from a JSON file), and a package that is not named `extract-*`, is
  not `infer-join` and never mentions the identifier `ExtractorManifest` (a factory with an inferred
  type). A package that mentions the identifier in any position is an extractor package, so the scan
  errs toward `Unknown`; only `@seamline/ontology`, the vocabulary package, is exempt, and by name. A
  required scope that is missing, failed or never declared is `Unknown(scope-not-pass)`, never
  dormancy. The X10 self-proof withholds baseline absence when source input is unreadable and requires
  the complete scan at head, never a separate inspection or scope flags alone (12.1).
- **`module-wiring` never answers `ABSENT`.** The graph holds static `import` and `export ... from` edges and nothing else. A dynamic `import()`, a `require()`, a `new URL(..., import.meta.url)` reference, a `package.json` script, a workflow, a tool configuration and every source file the run did not read are consumers it cannot see (4.4). So a control claim is confirmed or `Unknown`, and the packet can never say that a control is unwired. The cost is a missed finding: the C4 defect of the pre-fix tree would have been `Unknown` even had the row named the module. It is accepted because the alternative is a report of absence that is wrong for a lazily loaded command module or a script-run file, and a wrong absence is the failure the project's rules against manufactured findings exist to prevent. Recording those consumers in the extraction (section 10) is what would reopen the question.
