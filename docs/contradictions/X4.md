## What it compares

For one `Contract`, its response properties that resolve to a producer against those that do not. A response property is a `SchemaProperty` child of the contract whose direction is `response` (`detectors/x4-unbacked-property.ts:54-56`). A producer is a `Column` or `CodeField` reached by `SchemaProperty -BACKED_BY-> ...` or `... -EXPOSED_AS-> SchemaProperty` (`detectors/x4-unbacked-property.ts:32-41`). Direction is read from an explicit `direction` prop or derived from the `jsonPointer`: a pointer of the form `/paths/{path}/{method}/responses/...` is a response (`props.ts:131-139`, the anchored patterns at `props.ts:147-148`). A pointer that merely contains the word, such as a Zod property named `responses`, gets no direction.

On its face this is an absence, which this project refuses to report. It becomes a contradiction through the sibling control below.

## When it fires

When a contract has at least two response properties, at least one resolves to a producer and at least one does not (`detectors/x4-unbacked-property.ts:57`, `:66`). One finding per unbacked property, naming a backed sibling as the witness (`detectors/x4-unbacked-property.ts:68-88`).

## When it must not fire

- **No sibling resolves.** Then the honest reading is that the join failed on this contract, not that the API invents fields (`detectors/x4-unbacked-property.ts:66`). Tested at `detectors/controls.test.ts:50-52`.
- **Too few siblings resolve.** Confidence is `backedShare * bestSiblingJoin`, so one of three resolving gives 0.33 times the join confidence, under the 0.35 floor, and nothing is reported (`detectors/x4-unbacked-property.ts:73-74`). Tested at `detectors/controls.test.ts:54-56`.
- **Fewer than two response properties** (`detectors/x4-unbacked-property.ts:57`).
- **Properties with no direction.** A property with neither `direction` nor an OpenAPI `/paths/{path}/{method}/responses/` or `/paths/{path}/{method}/requestBody` pointer is neither request nor response and is not counted (`props.ts:136-137`, `props.ts:147-148`).

## Severity and confidence

Declared `medium` (`detectors/x4-unbacked-property.ts:45`). Confidence is `backedShare * witnessJoinConfidence`, rounded to six places (`detectors/x4-unbacked-property.ts:73-74`). Nine of ten resolving at 0.95 gives about 0.855 (`medium`); anything under 0.5 degrades to `low`; under 0.35 it is dropped.

## Controls

- **Sibling control.** The detector speaks only where the join demonstrably works for this contract, because other properties on it do resolve (`detectors/x4-unbacked-property.ts:1-21`).
- **The control is also the confidence.** A contract where few properties resolve is suppressed by the floor rather than by a special case.
- Only extracted facts and non-LLM edges (`graph.ts:59-66`).

## Example

`fixtures.ts` (`x4`): three columns on `orders` and three response properties on `orderApi`. `id` and `total` are backed by inferred `BACKED_BY` edges (confidence 0.95); `discountLabel` is backed only in the clean graph:

```ts
{ kind: 'SchemaProperty', name: 'discountLabel', canonical: 'openapi.orderApi#/Order/discountLabel',
  props: { type: 'string', required: true, direction: 'response' } },
// BACKED_BY edges for id and total always; for discountLabel only when backDiscountLabel
```

Fires with `backDiscountLabel = false` (`FIXTURES.X4_UNBACKED_PROPERTY.firing`, "the order response returns discountLabel, which nothing produces, while its siblings resolve"): two of three resolve, so confidence is 0.6667 x 0.95 = 0.633333 and severity `medium`. With `true` (`FIXTURES.X4_UNBACKED_PROPERTY.clean`, "discountLabel is backed by orders.discount_label") all three resolve and it is silent.

Tests: `meta.test.ts:42` (`X4_UNBACKED_PROPERTY > fires: the order response returns discountLabel, which nothing produces, while its siblings resolve`), `meta.test.ts:72` (`... > does not fire once discountLabel is backed by orders.discount_label`), and the control at `detectors/controls.test.ts:24-61`.

## How UNKNOWN arises

If `contracts`, `data`, `code.ts` or `infer-join` is not `PASS`, the detector is not run and reports UNKNOWN (`runner.ts:93-113`). It is also declared `absenceOfCode` (`detectors/x4-unbacked-property.ts:47`): "no producer" is only as good as the code that was read, so while the `Repo` node names a workspace package or project `extract-code-ts` did not read, the detector reports UNKNOWN with every scope `PASS` and no blocking scope (`runner.ts:115-134`; the reason is `code.ts did not read N workspace package(s)`). Tests: `incomplete-code.test.ts`. A contract whose properties could not be joined is silent, not UNKNOWN.

## Current status

**Fires, narrowly.** Everything the detector reads is emitted, but two properties of real extraction restrict where it can speak.

1. **Direction exists only for inline response schemas.** `extract-contracts` emits `jsonPointer` and no `direction` (`packages/extract-contracts/src/emit.ts:133`). A response schema reached through `$ref` is recorded at its component pointer (`#/components/schemas/...`), which contains no `/responses/`, so `propertyDirection` returns `undefined` and the property is not counted (`props.ts:131-139`). This matches the README ("X4 ... sees only some response shapes").
2. **The join needs a container name that corresponds to an entity.** `infer-join` takes a schema property's container from the pointer segment before `properties` or `items` (`packages/infer-join/src/facets.ts:82-98`). For a schema placed directly under a response media type that segment is `schema`, which matches no table or class, so nothing is joined and the sibling control keeps the detector silent. A response whose properties sit in a nested object named like the entity (a `person` property holding the fields, for a `people` table) gets container `person` and joins.

A local end-to-end run over a small constructed repository confirmed both: an inline response schema directly under the media type produced no `X4_UNBACKED_PROPERTY`; wrapping the same fields in a `person` object produced findings at confidence 0.653. In that run the object-typed wrapper property `person` was itself reported as "nothing produces it", because the detector counts every response-direction `SchemaProperty` child of the contract and does not exclude object-typed ones (`detectors/x4-unbacked-property.ts:54-56`). No checked-in test drives X4 through real extraction.

Doc difference: the README row and design v3 section 5 describe a property "backed by no column and no computing symbol". The code looks for a `Column` or a `CodeField` only (`detectors/x4-unbacked-property.ts:37`); a `Symbol` that computes the value does not count as a producer.
