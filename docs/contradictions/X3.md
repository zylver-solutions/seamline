## What it compares

A column's own constraints against the constraints of the validator symbol joined to it, on the dimensions **both sides state** (`detectors/x3-constraint.ts:1-12`). The dimensions are `required`, `maxLength`, `minLength`, `minimum`, `maximum`, `enum` (`props.ts:342-344`). The column side is read by `columnConstraints`, which maps `nullable` to `required` (`props.ts:359-369`); the validator side by `validatorConstraints` (`props.ts:372-379`). The join is `COLUMN_TO_VALIDATOR`: a direct `VALIDATED_BY`, or one through a mapped code field, an exposed contract property, or a backing property (`joins.ts:28-33`), always ending on a `Symbol` (`detectors/x3-constraint.ts:39`).

## When it fires

For each column with at least one constraint and each joined validator `Symbol` with at least one, for every dimension where both state a value and the values differ (`detectors/x3-constraint.ts:37-47`). Example: `varchar(50)` (`maxLength=50`) behind a validator accepting 255.

## When it must not fire

- The column states no constraints, or the validator states none (`detectors/x3-constraint.ts:37`, `:41`).
- A dimension is stated on only one side. That is [X7](X7.md)'s subject; the two detectors partition the space so the same pair is not reported twice. Tested at `detectors/controls.test.ts:133-137`: with `maxLength` different on both sides X3 owns it and X7 is silent.
- Values are equal (`detectors/x3-constraint.ts:46`).
- Endpoints that are not extracted facts, tombstoned nodes, `LLM_SUGGESTED` edges (`graph.ts:59-66`).

## Severity and confidence

Declared `medium` (`detectors/x3-constraint.ts:28`). Confidence is the join confidence of the path to the validator (`detectors/x3-constraint.ts:55`). At 0.5 or above the finding is `medium`; below, it degrades to `low` and is dropped under 0.35.

## Controls

- Only dimensions both layers can express are compared. Regex, format and cross-field rules are not in `CONSTRAINT_DIMENSIONS` (`props.ts:335-344`).
- Both sides must state a value for the dimension.
- Accessors return `undefined`, never a default, for an unextracted constraint (`props.ts:1-14`).

## Example

`fixtures.ts` (`x3`): a `varchar(50)` column joined by an inferred `VALIDATED_BY` edge (confidence 0.85) to a validator symbol:

```ts
{ kind: 'Column', name: 'display_name', canonical: 'db.public.users.display_name',
  props: { type: 'varchar(50)', nullable: false, maxLength: 50 } },
{ kind: 'Symbol', name: 'displayNameSchema', canonical: 'src/validation/user.ts#displayNameSchema',
  props: { maxLength: validatorMaxLength, required: true } },
{ kind: 'VALIDATED_BY', src: 'db.public.users.display_name',
  dst: 'src/validation/user.ts#displayNameSchema', provenance: 'INFERRED', confidence: 0.85 }
```

With `validatorMaxLength = 255` it fires (`FIXTURES.X3_CONSTRAINT.firing`): "display_name is varchar(50) while its validator accepts 255 characters", severity `medium`. With `50` (`FIXTURES.X3_CONSTRAINT.clean`, "the validator accepts 50") it does not; `required` is `true` on both sides in both graphs.

Tests: `meta.test.ts:42` (`X3_CONSTRAINT > fires: display_name is varchar(50) while its validator accepts 255 characters`) and `meta.test.ts:72` (`X3_CONSTRAINT > does not fire once the validator accepts 50`).

## How UNKNOWN arises

If `data`, `code.ts` or `infer-join` is not `PASS`, the detector is not run and reports UNKNOWN (`runner.ts:93-113`). `contracts` is not required. A pair with no constraint on either side is silently skipped.

## Current status

**Dormant.** It reports `clean` on a repository extracted today, for two independent reasons, either of which is enough.

1. **No validator `Symbol` carries a constraint property.** The detector reads constraints off the `Symbol` that `VALIDATED_BY` points to (`detectors/x3-constraint.ts:39-40`). The only validator-related prop `extract-code-ts` puts on a variable `Symbol` is `library` (`packages/extract-code-ts/src/symbols.ts:195-203`, alongside `exported`, `declaredType`, `type`). A decorator target is the decorator function's own symbol. `infer-join` emits the `VALIDATED_BY` edge (`packages/infer-join/src/validators.ts`, rules R1 and R2) but adds no property to the symbol (`packages/infer-join/src/manifest.ts:49-58` declares it emits no nodes).
2. **The constraints that are extracted live on a node the detector does not read.** `extract-contracts` records `minLength`, `maxLength`, `minimum`, `maximum` and `enumValues` on `SchemaProperty` nodes (`packages/extract-contracts/src/emit.ts:144-154`), and the detector's traversal filters to `Symbol` (`detectors/x3-constraint.ts:39`). The key also differs: the contract emits `enumValues`, the detector reads `enum` (`props.ts:350-353`).

The column side is also narrower than the dimension list. `extract-data` emits `nullable` and `maxLength` as constraint-like column props (`packages/extract-data/src/emit.ts:173`, `:167`) plus the raw `checkConstraint` text (not parsed into `enum` or a range); `minLength`, `minimum`, `maximum` and `enum` are never present on a column. So even with validator constraints extracted, only `required` and `maxLength` could be compared today.

The README (`README.md`, "X3 (constraint disagreement) does not fire on real repositories yet") and design v3 section 9 state the validator-side reason. They do not mention the `enum` / `enumValues` key mismatch or the narrow column side.

To make it live, an extractor must emit constraint props on the validator symbol (or the detector must read `SchemaProperty`), under a design-spec pass with a named consumer ([design v3 section 9](../design/v3.md)).
