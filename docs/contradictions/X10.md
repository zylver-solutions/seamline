## What it compares

A fact Symbol that explicitly writes a PII Column, with no accepted fact TESTS or COVERS relationship reaching that Symbol or its containing File. A COVERS record that states `covered: false` does not verify the target. At least one TestCase or CoverageRecord fact must exist before this absence comparison is attempted. Required scopes must PASS, and unread code prevents the absence conclusion. See the detector's `verificationFactsExist`, `isVerified`, `symbolIsVerified`, and `absenceOfCode` declaration (lines 54, 58, 97 and 107).

The PII label is priced through `piiWeight`, and the write edge's confidence is included. An inferred label cannot obtain more confidence than its stated weight. Non-fact nodes or edges and tombstones do not justify findings. The standard detector scope, provenance and confidence gates remain in force.

## Explicit write columns

The real code extractor emits `insertColumns` with `insertComplete`, and `updateColumns` with `updateComplete`. It folds all statements for a Symbol and Table into one QUERIES edge. An upsert has both halves; a folded SELECT does not supply write columns. See `packages/extract-code-ts/src/queries.ts:119` and the accessors in `packages/contradictions/src/props.ts:212`.

X10's `writtenColumns` (detector lines 70 to 95) requires every relevant write half to have a complete, present column list and unions those lists. Only explicitly named PII columns can produce findings. A write to `display_name` does not imply a write to sibling `email`. Identifier spelling is preserved, so distinct quoted `Email` and `email` columns are not collapsed.

The older explicit `{ writes: true, columns: 'email' }` fact shape remains supported when it contains no operation or per-class metadata. Generic `columns` cannot override typed facts or complete a folded read/write edge. Contradictory extra-class metadata and unsupported write classes are withheld.

When verification facts exist and an unverified writer reaches a table with PII but its write-column set is missing, incomplete or unsupported, X10 returns UNKNOWN with `WRITE_COLUMNS_UNOBSERVED`. It does not treat a withheld list as empty or assume every PII column was written (detector lines 110 to 125). A verified writer requires no absence conclusion and remains silent.

## No verification facts

Without any TestCase or CoverageRecord facts, X10 reports no findings. If potential PII write paths exist, the runner retains an explanatory note; the outcome is clean. This is not evidence that verification extraction is complete. The control in `packages/contradictions/src/detectors/controls.test.ts` ("reports a note, not findings, when the repository has no tests at all") asserts that distinction.

## Severity, confidence and the fixture pair

Declared `medium`. The finding's confidence combines the PII label's weight with the write edge's confidence, as described above, and the shared wrapper lowers the severity when that confidence is under the floor for `medium` (0.5, from the table in the [index](README.md)).

The fixture graph has a `customers.email` column labelled `pii: 'high'`, a symbol `updateCustomerEmail` whose `QUERIES` edge states `{ writes: true, columns: 'email' }`, and one `TestCase` that tests a different symbol, `getCustomer`. That one test is what lets the absence comparison run. The firing claim is "updateCustomerEmail writes customers.email (pii=high) and no test reaches it". The clean graph adds a `TestCase` with a `TESTS` edge to `updateCustomerEmail` and nothing else.

## Regression evidence

`packages/contradictions/src/detectors/x10.test.ts` covers complete insert/update/upsert sets, each upsert half, mixed SELECT/write edges, legacy compatibility, missing and incomplete lists, contradictory metadata, quoted identifiers, verified writers and the unchanged no-verification behavior.

`packages/integration/src/x10-write-columns.test.ts` runs the real data, code and contract extractors, persists their output, runs real join inference, and checks its PASS status. It asserts the actual QUERIES property names, positive email writes, negative display-name writes, quoted identifiers and incomplete-column UNKNOWN outcomes.

The integration verification control is explicitly authored DECLARED input. No shipped extractor emits it, and no manufactured PASS status is introduced. These hybrid regressions establish consumer behavior only; they do not prove verification extraction, unmodified external repository firing, independent labels, recall, or the sealed evaluation that `docs/PUBLIC-RELEASE-CHECKLIST.md` (item G8b) calls passing M2.

## Current coverage limit

The detector is implemented, registered in `ALL_DETECTORS` (`packages/contradictions/src/detectors/index.ts`) and exercised by its fixture pair and the tests above. What is missing is its input. No shipped extractor emits TestCase/TESTS or CoverageRecord/COVERS facts. X10 therefore remains dormant on current real extraction. The verification extractor is deferred behind a named consumer and its own design pass in `docs/design/v3.md` section 9 ("Deferred, each behind a named consumer"); the paragraph there headed "On detectors whose input facts no shipped extractor emits" records the missing producer facts. Fixing write-column consumption does not supply that missing producer or change the measured development-corpus recall denominator.

`seamline align` reports the same thing from the other side. It classifies X10 as a planned gap with the reason `deferred-and-absent`: the documents mark the detector dormant, and no extractor scope of the run produces a `TestCase` or `CoverageRecord` node. That classification is about whether X10 can fire on real extraction. It does not mean the detector code is absent.
