Citations are relative to `packages/contradictions/src/` unless the path starts with `packages/`. Shared mechanics are on the [index](README.md). The design is [real-world-inputs](../design/real-world-inputs.md) 5.1, 5.2 and 8.1.

## What it compares

A column that is `NOT NULL` and has no default that the writers supply (`Column.nullable === false`, and `Column.defaultSite` of `none`, or of `client` when no insert went through the ORM client) against the set of columns that the traced **inserts** into its table name. The schema says a value is mandatory on every insert; the code says no insert supplies one. The inserts are the `QUERIES` edges into the `Table` whose statements include an insert class (`insert`, an upsert's insert half), from a fact node, read through `insertColumns` and `insertComplete` (`props.ts`). An `UPDATE` that does not set a column is correct, so update and delete edges are not read. This detector uses no inferred join: both insert `QUERIES` assertions and column `CONTAINS` membership must have fact provenance (`EXTRACTED` or `DECLARED`).

Where a default lives decides who receives it (design 4.4). A database default (`defaultSite = db`, for example `@default(now())`) reaches every writer, raw SQL included. A client-side default (`defaultSite = client`, for example Prisma `@updatedAt` alone) is supplied only by an insert that went through the ORM client (`insertOrm`); a raw `INSERT` does not receive that client-side default. Runtime schema mutation, which can provide a separate database default, is guarded as described below. An absent `defaultSite` is unknown and the column is not reported.

## When it fires

For a table that survives the guards below, for every `NOT NULL` column that no insert's `insertColumns` names (lowercased) and whose default is not supplied to the writers. One finding per such column, citing a deterministic witness insert (the first by source symbol id).

## When it must not fire

- **The statement is not an insert.** An update or a delete edge is not read; a table with no insert edge is not mentioned at all.
- **An insert assertion or its writer is not a fact.** The table is withheld with a note: discarding a guessed insert would let the remaining writers establish a false absence claim. Inferred or suggested column membership cannot establish that a table requires the column.
- **One insert is not fully known.** An insert edge without `insertComplete` counts as incomplete, as does `insertComplete` false, and one incomplete insert silences the table, because the insert it cannot read may supply the column. An edge that says nothing about its statements may hold an insert and is treated the same way.
- **Per-table facts withhold the table**, each with a note naming it: `declarations` above one (the table's columns are a union of several source files, so an insert written for one declaration can look short of a column only the other has), an `insertTrigger` of true (a `BEFORE INSERT` trigger may supply the column), the table named in `Repo.unknownWriterTables` (read through the typed accessor `unknownWriterTables(props)`, case-insensitively), and an absent `declarations` or `insertTrigger` (unknown, never "one" or "no trigger").
- **Any traced insert names the column.** X5 is a "no writer supplies it" detector: when one writer names the column it is silent even if siblings omit it (design 9.4).
- The column is nullable, or `nullable` / `defaultSite` was not extracted.

## Severity and confidence

Declared `medium`. Confidence is the minimum of the contributing insert edges' own `confidence`, because the claim is that every insert omits the column and is only as strong as the least certain one. A name-only table binding is 0.7, so a finding that rests on one carries 0.7, not 1. The earlier rule (a fact edge counts as 1) is gone for this detector.

## Controls

- **Repository-wide facts, UNKNOWN (`unknownWhen`).** `Repo.untracedWriteCalls`, `Repo.writeHooks`, `Repo.runtimeDdl` or `DataSource.dynamicDdl` above zero make X5 UNKNOWN, and so does any of them absent: a missing prop is not zero. An absent `Repo.unknownWriterTables` (the list was not measured) is UNKNOWN as well.
- **Withheld tables are reported, not hidden.** The detector's `notes` name each withheld table and why. `check` prints them under "NOT EVALUATED", adds `detectorNotes` to `--json`, and says on the `CLEAN` line that a detector did not evaluate part of its input, so a withheld table never looks clean. Notes never change the exit code.
- **The `insertOrm` branch is fixture-only.** The detector reads `insertOrm` (a client-side default is supplied to an insert that went through the ORM client), but no extractor emits it yet; it has been exercised only by fixtures and has not been observed on a real repository. On real extraction a table with an ORM writer reaches X5 through `unknownWriterTables` and is withheld, so the result is sound; the emitter arrives with the ORM-edge row.
- **MCP does not surface notes.** The MCP contradictions tool returns `unknownDetectors` only, so an MCP client sees X5 with no findings and no hint that tables were withheld. Use `check` (CLI) to see the NOT EVALUATED notes.
- The guards are lexical and bound recall. They weaken the claim from "no write path supplies the column" to "no traced write path supplies it" (design 5.2, "What the guards do not see").

## Example

`fixtures.ts` (`x5Spec`): table `accounts` with `id` (database default), `tenant_id` (`NOT NULL`, `defaultSite = none`) and a nullable `label`, one insert, and the repository-wide counts at zero:

```ts
{ kind: 'QUERIES', src: 'src/repo/accounts.ts#createAccount', dst: 'db.public.accounts',
  props: { operation: 'insert', insertColumns: 'id,label', insertComplete: true },
  sourceRef: 'src/repo/accounts.ts:19' }
```

With `insertColumns = 'id,label'` it fires: "accounts.tenant_id is NOT NULL and has no default, and none of the 1 traced insert path(s) into accounts writes it". With `'id,label,tenant_id'` it does not. `detectors/x5.test.ts` holds the other pairs, one per rule above.

Tests: `meta.test.ts` (the X5 pair), `detectors/x5.test.ts`, `detectors/controls.test.ts`, `packages/cli/src/commands/check.notes.test.ts`, and the real-extraction acceptance `packages/integration/src/x5-column-writes.test.ts`.

## How UNKNOWN arises

If `data` or `code.ts` is not `PASS`, the detector is not run and reports UNKNOWN (`runner.ts`). With both `PASS`, `unknownWhen` can still stand it down for the repository-wide facts above, and the reason names the prop and its value. `infer-join` is not required.

## Current status

**Implemented and guarded; authored-fixture proof only.** Current firing on an unmodified non-self corpus repository is unverified, so X5 is disclosed dormant pending evaluation under design section 6.5. The pieces it needed shipped as rows A to D of [real-world-inputs](../design/real-world-inputs.md) 2.1: `defaultSite`, `insertTrigger`, `declarations` and `dynamicDdl` from `extract-data`; per-statement `insertColumns` and `insertComplete` on raw-SQL `QUERIES` edges, including interpolated templates; the unknown-writer facts on the `Repo` node; and the `unknownWhen` hook.

The historical development candidate is pinned as `saintandstory-parent` and `saintandstory-fix` in `eval/corpus.json`. Its two parent findings and one fix finding were adjudicated as three false positives by a fresh second source-review agent using the same account in `eval/labels.json`. Runtime schema setup can supply database defaults absent from the Prisma declaration; conditional creation does not establish a pre-existing production database's state. This same-account review receives no formal release independence credit under design section 6.3. The FP verdicts and `blind: false` labels remain unchanged. The earlier two-then-one output is not a verified true positive or a successful precision prediction.

The runtime-DDL guard now makes X5 UNKNOWN when `Repo.runtimeDdl` is positive, missing or invalid. The deterministic measurement counts SQL expression sites with top-level schema-mutating statements, including statements after a read or session prefix. Outermost string compositions are reconstructed from literals, concatenations and constant nested templates through transparent TypeScript assertion wrappers, including const initializers and module expressions, and count once. Unknown operands remain sentinels; contiguous known segments beside them are inspected independently. No identifier or call is executed or resolved. Words inside SQL strings and comments are ignored. The guard can conservatively count code that never executes, and does not extract runtime defaults. A profile hiding the measurement leaves the detector UNKNOWN. Authored real-extraction fixtures cover the runtime-default gap and a control that still reports a genuine synthetic omission.

The earlier other-development runs were UNKNOWN for their recorded write, hook, DDL or scope guards. They predate this change. A fresh corpus run is required before stating current per-repository outcomes or precision; no verified real-world true positive is established by this candidate.
