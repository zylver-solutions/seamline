## What it compares

Both endpoints are live fact `Migration` nodes. The first carries a reference to a qualified table or column and its state at that statement. The second carries a matching local creation declaration. A finding says the object is **absent at this point in the declared migration replay**. It does not describe the current database or promise that the history executes successfully in every environment.

The replay starts with an empty catalog for each migration group. Current ORM and SQL snapshots do not populate historical state, and groups cannot lend one another declarations. The supported order is Supabase filename order, established by a positively parsed project configuration. Unknown configuration, ambiguous membership and unsupported framework ordering cannot certify absence. See `packages/extract-data/src/migration-order.ts` and `packages/extract-data/src/migration-replay.ts`.

This is static analysis. SQL, stored functions, modules and database connections are never executed. Closed procedural forms have checked effect footprints. An unsupported membership effect makes the data scope UNAVAILABLE, preserving prior authoritative facts instead of certifying an empty history. Runtime effects of invoking stored functions remain outside the declared-DDL claim. Within supported executable blocks, a recognized function name alone does not establish its native effect: replay inventories source-declared routine creation, alteration and removal across the group, and withholds dependent native-call assumptions on a matching name. Qualified project functions are not admitted as catalog helpers. Project-relation guard reads and exception statements remain unsupported: reads can invoke hidden view or policy functions, while exceptions terminate execution. Accepted catalog reads also depend on their source relations remaining unchanged. Procedural CHECK additions with unproved expression calls are refused because constraint validation can execute them for existing rows. Procedural validation of stored constraints, type coercion and call-bearing default changes are also withheld when their effects are unproved. System-catalog row writes, including writable CTEs and implicit catalog target names, are unsupported membership effects. A row-only exemption also requires a positively established physical table at the write site. Writes through declared, renamed or possibly external views are withheld because their target can rewrite to catalog metadata or invoke rules. This conservative refusal accounts for PostgreSQL's [overload resolution](https://www.postgresql.org/docs/17/typeconv-func.html).

## When it fires

A complete current replay certificate records known absence for a required local reference, with a creation witness in the same repository, data source, group and snapshot. The witness can be later creation, or an earlier declaration followed by retirement of that object's lifetime. The detector validates the qualified target and the witness's statement and source line before reporting the disagreement.

A never-created object is external. It supplies no local creation witness and produces a withholding note, not an orphan finding. A later DROP cannot retroactively invalidate an earlier valid reference. An IF EXISTS guard can skip a reference, and a skipped IF NOT EXISTS declaration cannot donate columns. A table name never declared by the group cannot prove that an external relation-existence guard is false. Conditional index bodies are skipped only with positive relation-existence evidence; otherwise their references remain unknown. Table mutations conservatively invalidate recorded index-existence evidence. Sequence declarations and implicit primary-key, unique and serial relation names also prevent a table guard from inferring absence solely from the table catalog. Implicit names supply uncertainty, never a table or column creation witness.

## Stored evidence and controls

`DataSource` carries `replayVersion`, `replayEpoch`, `replaySnapshotHash`, inventory and membership completeness, and canonical JSON group rows with a checked policy, configuration hash, member names and input hash.

Each examined `Migration` carries that snapshot and group input binding, a group-local `replayOrdinal`, logical statement and unknown-step counts, declarations, and five explicit reference categories:

- `unresolvedRefs`: known absence with a local creation witness.
- `validRefs`: positively established point-state.
- `skippedRefs`: references on a branch proved not to execute.
- `externalRefs`: known absence without local creation.
- `unknownRefs`: a point-state that cannot be established.

Each category has an exact count. Empty arrays are explicit. Qualified identifiers use tuple fields, not dotted-name suffix matching. Logical positions distinguish nested procedural statements even on the same physical line. CHECK and generated expressions contribute their local column dependencies. Source lines and statement positions are evidence, never identity inputs. No raw SQL is stored in these replay props. The producer emits these scalar props in `replayMigrations` (`packages/extract-data/src/migration-replay.ts`).

Supported views retain their named relation and checked projected column inventory. A wildcard or another unknown projection leaves column membership unknown; replacement cannot donate a complete new inventory to an uncertain relation. Replay refuses identity-bearing identifiers above 63 UTF-8 bytes rather than treating an overlong spelling and PostgreSQL's truncated spelling as different objects. Unquoted identifiers are restricted to ASCII so the tolerant lexer cannot substitute JavaScript Unicode case folding for PostgreSQL UTF-8 identifier rules; quoted UTF-8 names retain exact case within the byte bound. Ignored policy labels never enter object identity or member resolution. PostgreSQL documents the default limit in its [lexical rules](https://www.postgresql.org/docs/17/sql-syntax-lexical.html).

Extension installation and relocation remain unsupported membership effects. PostgreSQL loads extension scripts, and `IF NOT EXISTS` supplies no proof of which implementation is installed ([CREATE EXTENSION](https://www.postgresql.org/docs/17/sql-createextension.html)). A major server version and an extension name do not establish a pinned script footprint. This boundary still withholds the named consumer's complete parent/fix result.

The decoder bounds JSON size and row work, requires canonical sorted rows, checks counts and category disjointness, and verifies every supporting node's live fact provenance, natural identity, current epoch, data source and snapshot. It validates a whole group before releasing any of that group's findings (`packages/contradictions/src/detectors/x8-replay-proof.ts:28`, `:83`, `:104`). The snapshot digest binds the certificate bodies as well as their source inputs, while excluding the epoch from content hashing. Same-run retries and interrupted writes cannot combine an older interpretation of the same inputs with current reference props.

Replay-bearing Migration nodes are classified confidential because their tuples carry data-model identifiers. A profile that admits only internal history metadata cannot release those tuples through a Migration prop wildcard. An explicit profile must admit the confidential nodes and required props; a projected view without complete evidence withholds X8.

The former current-schema and tombstoned MIGRATED_BY routes are removed. Legacy target props, inferred nodes, retired endpoints and final-schema suffix matches cannot bypass replay evidence. Store visibility and tombstone rules are unchanged.

## Example and verification

An independently authored fixture uses two direct migration files beneath a supported project configuration:

```sql
-- 001_ref.sql
ALTER TABLE public.accounts ADD COLUMN tag integer;
-- 002_create.sql
CREATE TABLE public.accounts (id integer);
```

The ALTER requires the table while its group-local catalog is empty. The later CREATE is the local witness. Moving CREATE before ALTER makes the table reference examined and valid. This pair does not depend on current-schema absence.

Producer controls are in `packages/extract-data/src/migration-replay.test.ts`. Decoder controls are in `packages/contradictions/src/detectors/x8-replay.test.ts`. Real SQLite tests in `packages/integration/src/x8-replay-lifecycle.test.ts` cover positive/fix transitions, unsupported input, deletion, restoration, same-run retry, group recognition changes, cross-group isolation and an interrupted write while the previous data scope still reads PASS. The production sandbox and CLI storage lifecycle control is `packages/cli/src/sandbox/x8-replay-lifecycle.test.ts`; it asserts current positive endpoints, an examined fix, unavailable/resource-limited scopes and protected prior facts. The graph fixture pair is `packages/contradictions/src/__fixtures__/replay.ts`.

These authored controls do not establish external precision, calibration, the sealed partition bar or formal mutant recall. The design requires complete real-source parent/fix CLI acceptance before implementation merge.

## UNKNOWN, notes and confidence

A non-PASS data scope blocks detection. Missing, stale, malformed, incomplete or unsupported replay evidence withholds the affected group. With no known finding and a withheld group, X8 reports UNKNOWN. A known finding can retain notes about other withheld groups or references; those notes do not turn an unexamined reference into a passing negative.

An explicitly examined empty inventory can be clean. A PASS scope with no replay inventory cannot. External and unknown references are counted and disclosed separately.

Each supported disagreement uses two fact endpoints and confidence 1, with declared severity low (`packages/contradictions/src/detectors/x8-orphaned-migration.ts:8`). This confidence describes the fact comparison within its declared replay scope. It is not an empirical precision or calibration claim.
