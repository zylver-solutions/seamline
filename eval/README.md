# Evaluation corpus and `pnpm eval`

`pnpm eval` measures Seamline on public repositories it did not write. It reports, per detector, how often a finding is right (precision), how often an injected contradiction is found (recall), and whether the detector fires on real code at all.

The harness is `packages/eval` (`@seamline/eval`), a private workspace package: it is not published to npm, and `pnpm eval` runs only in a clone of this repository.

It is not part of `pnpm verify`. Nothing in `verify` fetches, and the engine never makes a network call: the only network access is a plain `git` subprocess in `packages/eval`, run on request.

The design is section 6 of `docs/design/real-world-inputs.md`. Where this harness does not yet do what that section says, the list at the end of this page says so.

## What is in this directory

| File           | Contents                                                                                                                                                                                                                                                                                             |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `corpus.json`  | Ten entries: pins of seven public repositories (saintandstory is pinned at a parent and its fix; umami at a base commit plus an X7 parent and its fix), each pinned by clone URL and full commit SHA, with its declared license status, the stacks it exercises, why it is there, and its partition. |
| `labels.json`  | Review verdicts on findings, keyed by finding id; recorded reviewer identity determines formal independence credit.                                                                                                                                                                                  |
| `mutants.json` | Injected contradictions: minimal edits to a scratch copy of a dev repository, with the finding each should produce.                                                                                                                                                                                  |
| `FREEZE`       | Absent in 0.1.0; recorded when M2 is run for 0.2.0. One commit id: the point at which the detector and extractor change set was frozen. Until it exists, labels for sealed findings are refused (see "The freeze").                                                                                  |

Entries declaring license `none` are read only at run time, never copied or quoted. Nothing from the corpus repositories is vendored here. `mutants.json` edits JSON documents by JSON Pointer and so holds no text from them; its few text edits are a handful of tokens in MIT-licensed files. The repositories themselves are only ever read from a gitignored clone.

### Partitions

Repositories are either `dev` or `sealed`.

- **dev** repositories are the ones detector work is tuned against. Their findings are read, discussed, and fixed.
- **sealed** repositories are held out. People who change detectors look at counts for them, not at individual findings. Concretely, for a sealed repository:
  - `report.md` gives counts only and lists no finding;
  - `report.json` keeps, for each finding, only `id`, `repo`, `partition`, `code`, `severity`, `confidence`, `calibratedConfidence`, `occurrences`, and `verdict`. It omits the subjects, the claim, the facts, and the reviewer's cluster name (free text written by someone who read the finding), which is already folded into the clustered counts;
  - an extractor diagnostic is shown as its code only: the part before the first colon, and only when it is an upper-case identifier (`^[A-Z][A-Z0-9_]+$`, for example `CONTRACT_NAME_COLLISION`), otherwise `(unclassified)`, because the rest names the repository's own files and symbols. A detector's UNKNOWN reason is reduced the same way (the contradictions runner starts it with `SCOPE_NOT_PASS`, so that is what a sealed repository shows), and the cause of a crash or timeout is reduced to the outcome;
  - the run's failure output names no subject, cluster, or finding id, and the error for a cluster that mixes verdicts says only how many clusters in which repository.

  The one door to sealed findings is `pnpm eval label-sheet <repo>`, for reviewers, and it opens only once the partition is frozen (see "The freeze"): before `eval/FREEZE` exists, and once the partition is burned, it refuses. It then builds this repository and shows only a baseline that the current sources and build made, so a baseline left from before the freeze, or from tuned code, is not shown as the sealed findings. The raw per-repository output under `eval-out/` (`check.stdout.json`, `baseline.json`) holds sealed findings in full; it is local, gitignored, and not part of the report, and keeping it unread is procedure, not something the harness can enforce.

### The freeze

The sealed partition stays useful only while nobody tunes against it, so it is not opened until the detector and extractor change set is frozen.

- The freeze is a commit id in `eval/FREEZE` (one 40-character hex line; blank lines and `#` comments are ignored).
- **0.1.0 ships without a freeze.** `eval/FREEZE` is absent, so `pnpm eval` reports "no freeze recorded; re-freeze on the public history before the next release evaluation". A freeze must name a commit in the public history, so it is recorded when the evaluation is run for 0.2.0.
- Without `eval/FREEZE`, a label for a sealed finding is refused: the run stops with a configuration error. Sealed labels are committed only after the freeze.
- `pnpm eval label-sheet <sealed repo>` is refused before `eval/FREEZE` exists and when the partition is burned. `label-sheet` for a dev repository does not read `eval/FREEZE` at all, so it works with the file absent, malformed, or naming a commit a shallow clone lacks.
- With the file present, the sources listed below are compared with that commit. Any difference burns the sealed partition: a changed tracked file, committed or not, a new untracked file that is not git-ignored, and a deleted or renamed one (a rename counts as a deletion of the old name). The headline is withheld, the report says so, and the run fails. A burned partition is replaced by new repositories and a new freeze is recorded.
- **Record what was frozen.** When `eval/FREEZE` is added, run `pnpm eval` once at the freeze commit and put the report's `provenance.codeId`, `provenance.sealedCorpusDigest` and `provenance.scorerDigest` (printed under "Provenance" in `report.md`) in the commit message. The scorer is not watched (see below), so the release checklist (item G8) compares its digest with the one recorded here. The sealed corpus digest is compared automatically; recording it lets a reader verify, from the commit message alone, which sealed pins were frozen.
- **Hold dependency updates between the freeze and the release.** The lockfile and the manifests are watched, because the extractors run on the parser, YAML reader and glob matcher those files select. The repository's weekly npm update PRs touch them, so one merged after the freeze burns the partition. Pause them until the release, or accept the burn. A Dependabot security fix (the repository has those on too, see item F6 of the release checklist) that changes `pnpm-lock.yaml` after the freeze burns the partition the same way; so does a security fix to a manifest.
- A freeze naming a commit that is not in this repository's history (a shallow clone) is an error, not a guess.
- **The sealed pins are compared by digest.** `readFreeze` also compares the sealed entries of `eval/corpus.json` (name, url, commit and partition of each) with the freeze commit's. Any difference burns the partition and names `eval/corpus.json`: another commit for a sealed repository, a repository moved between `dev` and `sealed`, a sealed repository added or removed. A `dev` entry, and a sealed entry's `license`, `stacks` and `why`, are not part of it, and neither are the order and the formatting of the file, so adding a development repository does not burn. Replacing a burned partition edits this file together with `eval/FREEZE`, so the remedy is not in its way. The digest (`provenance.sealedCorpusDigest`) is printed in every report.

**What is watched, and why.** The list is `FREEZE_WATCHED_PATHS` in `packages/eval/src/freeze.ts`. It covers the sources the CLI loads when it runs `extract` and `check`, what it is built and run from, and the harness's run definition; the sealed pins are compared separately (above). It is a list of what is loaded, not of what is called: a module's top level runs when it is imported, whether or not anything it exports is used. What no list can cover is under "What a freeze cannot see", below. Three kinds:

1. the product the CLI loads on every run (`extract` and `check` are the commands the harness runs, but the dispatcher imports every command and the root barrel re-exports `traversal`);
2. what the product is built and run from (dependencies, compiler configuration);
3. the harness's own run definition: the files that decide which extractors run, with which configuration, environment and arguments, and how the output becomes findings.

A test finds the first and the last kind from the imports instead of from a list someone remembers to update. It starts at the detectors, `infer-join`, the extractors, the CLI's entry (`index.ts`, the file the harness runs) with the `extract` and `check` commands and their wiring, and the harness files that build, fetch, copy, run and read. From each it follows every module that is loaded: every `import` that is not `import type` (a side-effect import and `import { type T }` included, because the repository compiles with `verbatimModuleSyntax` and the test asserts that), every `export * from` and `export { } from` that is not `export type`, and an `import()` or `require()` with a literal target. Only types are not followed. The test fails when it reaches a file the list neither covers nor excuses, and it fails, rather than guesses, on:

- an `import()` or `require()` whose target is not a literal;
- a relative or `@seamline/*` specifier that does not resolve to a source file. `@seamline/<pkg>/<subpath>` is resolved through each `package.json` `exports` to the `src` file the entry is compiled from, never through `dist/`, so the answer does not depend on a build;
- a use of `createRequire`, under any name, in a file that the test does not list with a reason (`extract-contracts/src/zod.ts` is the only one: it loads the optional `typescript` peer dependency by that literal name, which the lockfile and the manifests select);
- a tracked file under `packages/*` outside `src` that is not a manifest, a `tsconfig`, a README, NOTICE, LICENSE or CHANGELOG, and a data file under `src` (outside fixtures) that is not watched. This is how a file read at run time, which no import shows, cannot sit where nothing watches it.

**Not watched, and why.** `packages/core/src/semantic` (an optional layer the root barrel does not re-export), `packages/integration` (tests), and the CLI's `bin.ts` (the packaged launcher, which the harness does not run) and `ports.ts` (types only, erased by the compiler) are never loaded by `dist/index.js`. `colour.ts` is loaded: it is excused because the harness runs the CLI with `--json` and `NO_COLOR`, so it cannot change a finding. **What a freeze cannot see.** No list of source files covers these, and none of them is covered another way unless it says so.

- The Node version and the contents of `node_modules` as opposed to `pnpm-lock.yaml`. The lockfile selects the dependencies and is watched; an installed tree edited by hand is not seen. The Node version is in the report's `run` metadata, not in `codeId`.
- A file a module reads at run time with the file system (`readFileSync(new URL('./rules.json', import.meta.url))`). No import shows it. Nothing reads one today. The last test above keeps such a file from sitting outside `src`, or unwatched inside it, so an edit to it burns the partition; but the trace itself would not notice that a new read had been added.
- The values of the environment the CLI starts with. `pipeline.ts` (watched) fixes which variables pass (`PATH`, `HOME`, `USER`, `TMPDIR`, `TMP`, `TEMP`, `SystemRoot`) and sets the determinism switches, so `NODE_OPTIONS` and the like do not reach the CLI; the values of the passed-through ones on the machine are not recorded.
- Code loaded by a path computed or spelled at run time rather than by an import the trace reads: a `Worker` or a child process started on a source file (`new Worker(new URL(...))`, `fork`, `spawn` of `process.execPath`), `import.meta.resolve`, an `import()` whose literal specifier has a URL scheme (`file:///...`), and a direct `createRequire(import.meta.url)(...)` call in a file already listed for `createRequire`. Nothing does any of these today; the trace does not report them.
- A file read at run time from outside `packages/*` (for example at the repository root); the test on tracked files covers `packages/*` only.
- `.npmrc` and `.nvmrc`. `.npmrc` decides the installed `node_modules` layout from the same lockfile, and `.nvmrc` names the Node version; neither is watched. No route from either to a different finding is known.
- The scorer, on purpose (see below): `scorerDigest` records it and the release checklist compares it.

The scorer is not watched, on purpose: `metrics.ts` (which holds `RELEASE_BAR`), `labels.ts`, `review.ts`, `report.ts`, `evaluate.ts`, `label-sheet.ts`, `mutants.ts`, `roles.ts`, `freeze.ts` itself, and the harness's `bin.ts` and `index.ts` decide how the same findings are counted and shown. Changing them re-scores findings that already exist and exposes nothing new, and burning three repositories for it would cost more than it protects. It does change the figure, though, and a change to `RELEASE_BAR` after the freeze would otherwise be invisible. The same holds for the call sites of the watched checks: `evaluate.ts` calls `analyse.ts` (the pin check, the sealed-baseline rule) and `sealedProblem`, and a change that stopped calling them would not burn the partition; it would change the scorer digest. So every report records a digest of those files (`provenance.scorerDigest`), beside the freeze commit, the digest of the watched sources (`provenance.codeId`) and the build that ran, and the release checklist (item G8) asks for the scorer digest to equal the one recorded at the freeze, or for the scorer diff since the freeze to be reviewed. `freeze.ts` cannot protect itself: that comparison is what stands in for it.

Inside a watched path a change is still ignored when it is inert: a `*.test.ts` or `*.test.mjs`, anything under `__fixtures__`, an editor or merge leftover (`*.orig`, `*.swp`, `*~`), a test helper (`testing.ts`, `test-*.ts`) that only tests import, or a package manifest whose only change is its `version`. A file that production code imports is never inert, whatever it is called.

## The headline, and the release bar

The headline is the sealed partition's precision, by cluster, on the **strict** reading (`unclear` is not a true positive). The lenient reading (`unclear` excluded) is printed beside it. The headline is claimed only when the sealed partition is complete and large enough:

| Status         | Meaning                                                                                                                                                                                                                                                                                                                                                                      |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `powered`      | At least 30 labelled clusters, no unlabelled sealed finding, and complete declared independent review evidence with the required double-review sample. A figure and "met" or "not met" are printed, followed by how many of the 10 detectors are unmeasured.                                                                                                                 |
| `underpowered` | Fewer than 30 labelled clusters. No figure is claimed and the bar cannot be assessed.                                                                                                                                                                                                                                                                                        |
| `incomplete`   | A sealed finding has no label (labelling the easy cases first would bias the figure), a sealed repository was not analysed (crash or timeout: its findings are unknown, not absent), the run was partial (`--repo`, `--mutant`, `--no-mutants`), or declared independent review evidence is incomplete once sealed labels exist. None is claimed, and no "met" or "not met". |
| `burned`       | A watched path or a sealed pin changed after the freeze. No figure is claimed.                                                                                                                                                                                                                                                                                               |

The **bar** is met when the strict pooled precision is at least 0.90 **and** its 95% Wilson lower bound is at least 0.75, over at least 30 labelled clusters, **and** no detector with at least 5 labelled sealed clusters has a strict point estimate below 0.80. 27 of 30 is 0.90 with a lower bound of about 0.74 and does not pass; 28 of 30 has a lower bound of about 0.79 and does. A detector with fewer than 5 labelled sealed clusters is reported as **unmeasured** and cannot be called validated. One prolific detector cannot carry a failing one.

## Running it

```sh
pnpm install
pnpm eval fetch       # clone each repository at its pinned commit into .eval-cache/
pnpm eval             # build this repository, fetch what is missing, analyse, run mutants, write the report
```

`pnpm eval` runs `tsc --build --force` first: the repository's own build, with every package recompiled. `--force` is deliberate. Without it `tsc --build` decides from file modification times whether a package is up to date, so a tree restored with its times preserved (`tar`, `rsync -a`, `cp -p`) after an edit that had been built would keep the edited output while its sources, and so `codeId`, said it was the frozen product. The cost is a full compile on every run, about 20 to 40 seconds on a developer machine, once per `pnpm eval` and once per sealed `label-sheet`. The evaluation drives the built CLI, `packages/cli/dist/index.js`, which is compiled output and not in git, so a run never trusts a `dist/` it did not just make: a stale one would be measured under the identity of the current sources. A source that does not compile is not measured; the run stops with the compiler output. `pnpm eval label-sheet <sealed repo>` builds the same way. The report records the CLI that ran and a digest of the compiled output of every package it was built from.

The report records the path and says it is not this repository's build; its digest then covers that file alone, since what else it loads is not known.                                                                                                                                                                                                                                                                                                                                                                                                                |

Other commands:

- `pnpm eval check-mutants` applies every mutant's edits in memory to the pinned checkouts and prints `ok` or `FAIL` and the reason for each mutant (exit 1 if any fail). It extracts nothing.
- `pnpm eval label-sheet <repo>` prints the blind label sheet (see below).

Outputs go to `eval-out/` (gitignored): `report.md`, `report.json`, and per repository a `store/` (the graph store and run snapshot), the raw CLI output, and the stored baseline.

Exit codes: 0 when nothing needs attention; 1 when a finding has no label, a mutant is invalid or errored, a repository was not analysed, the sealed partition is burned, or declared review evidence is incomplete; 2 for a usage or configuration problem, a checkout that is not the pinned commit, or a sealed label before the freeze; 3 for an unexpected failure.

## How a repository is fetched, and what is never done

- Each repository is cloned into `.eval-cache/<name>` and checked out detached at its pinned SHA.
- Every `git` call runs with `core.hooksPath=/dev/null`, no submodule recursion, no `ext::` transport, `GIT_LFS_SKIP_SMUDGE=1`, and no terminal prompts. Tests check the last two by behaviour: an `ext::` remote is refused even when the machine configuration allows it, and a submodule is not checked out even when the machine configuration would recurse into it.
- No attribute is applied to the checkout. The harness writes `* -text -eol -ident -filter -working-tree-encoding` to the clone's `.git/info/attributes`, which outranks every `.gitattributes` in the tree, so line-ending conversion, `$Id$` expansion, re-encoding, and clean or smudge filters (Git LFS included) cannot change the bytes.
- `git rev-parse HEAD` must equal the pin, the tree must be clean, and the attribute guard must be present. Otherwise the run refuses and measures nothing. `pnpm eval fetch` repairs a drifted cache.
- Nothing from a clone is ever executed: no install, no scripts, no build, no tests. Analysis runs on a scratch copy of the tree without `.git` and **without symbolic links** (a link in an untrusted tree can point outside it, and `extract-code-ts` reads through links), so the cache stays byte-identical to the pin.
- `.eval-cache/` and `eval-out/` are gitignored and are skipped when Seamline extracts this repository itself (the contracts extractor skips them by name, and the repository's `seamline.config.json` passes them to the data extractor), so a populated cache does not change what `pnpm verify` sees.

## What a run does

Before anything runs, the harness builds this repository and names what it built: the digest of the watched sources (`codeId`), of the sealed entries of the corpus (`sealedCorpusDigest`), of the harness code the freeze does not watch (`scorerDigest`), and of the CLI's compiled output. Outside a git checkout (a source archive) the sources cannot be named: a dev run proceeds and records `no git`, and never reuses a baseline; a sealed run is refused.

For each repository, `seamline extract` (with `SEAMLINE_DETERMINISTIC=1`, all extractors except `extract-change`, which needs history a scratch copy does not carry) writes a store to `eval-out/<name>/store`, then `seamline check --json` reports the contradictions. Each CLI call has a timeout. The report records extractor statuses, wall time, node and edge counts by kind, and the findings.

A finding id is the first 16 hex characters of `sha256(repo|code|left|right)`, where `left` and `right` are the node ids the detector compared (never a `File` id, which carries its path). It is stable across a file move that changes no id of the nodes it names (ADR-0016 item 4 says which moves do), and the same in an unmodified run and a mutated copy.

**A repository or scope that is not PASS makes the detectors that need it UNKNOWN in the report. It never shows as zero.** The same holds for a repository the harness could not analyse (a crash or a timeout): every detector is UNKNOWN there.

## Labelling findings

`labels.json` maps a finding id to:

```json
{
  "verdict": "tp",
  "cluster": "board-description",
  "rationale": "One paragraph, citing the source.",
  "evidence": ["prisma/schema.prisma:352", "src/app/api/boards/route.ts:41"],
  "reviewer": "who",
  "blind": true
}
```

- `verdict` is `tp`, `fp`, or `unclear`. `unclear` is for a finding the reviewer cannot decide from the source. It is counted and shown; the lenient reading leaves it out of precision and the strict reading counts it as not a true positive.
- `cluster` is an optional explicit root-cause override. By default, findings of one detector in one repository form transitive components through a shared left id or shared right id. Unlabelled findings participate too; a partially labelled component cannot supply a selected true positive. An explicit override opts that finding out of automatic links and groups it with the same explicit name within that repository and detector. The label rationale must explain the override. Raw and clustered counts remain separate, and labelled members of each component must agree on a verdict. Dev reports display automatic ids as `auto:<minimum-finding-id>`; sealed component identities remain withheld.
- `evidence` cites `path:line` at the pinned commit.
- `blind` records whether the reviewer judged from the label sheet alone.

`pnpm eval label-sheet <repo>` prints, for each finding of that repository, its id, its code, and the two subjects the detector compared with the `path:line` where each was extracted. It prints no claim text, no facts, no severity, and no confidence, so the judgement is made from the source and not from Seamline's own explanation. It reads the baseline a previous run stored, and refuses one made for a different commit than the pin. For a sealed repository it also refuses one that the current sources and build did not make.

A reviewer is a person or agent that did not write the detector change under review.

### Declared identities and second reviews

Schema 8 adds review evidence while preserving findings, primary verdicts, clusters, raw confidence and numeric precision/recall. Legacy labels remain readable. Their display-name `reviewer` string alone receives no formal independence credit. The ledger checks declarations; it does not authenticate accounts or discover omitted authors. Release reviewers must verify account ownership, aliases and the complete detector/extractor change-author roster against the measured change set.

| Location in `labels.json`       | Required evidence                                                                                                                                           |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Top-level `_review.codeId`      | The actual 64-character product `provenance.codeId` measured by the evaluation.                                                                             |
| Top-level `_review.authors`     | A nonempty array containing the complete declared change-author identities.                                                                                 |
| Each label's `identity`         | The primary reviewer's identity; `reviewer` must equal its canonical account identifier.                                                                    |
| Each label's optional `reviews` | Secondary source reviews, each with `identity`, `verdict`, `rationale`, `evidence` and `blind`, using the same verdict/evidence rules as the primary label. |

An agent identity has the form `{ "kind": "agent", "account": "provider:reviewer-a", "model": "model-a" }`; a human uses `{ "kind": "human", "account": "provider:reviewer-b" }`. These are synthetic format examples, not actual reviewers or attestations. Accounts use a provider namespace and identifier, are trimmed and case-folded, and cannot contain whitespace. Two models sharing an account cannot establish independence from each other. A change-author account is ineligible regardless of model.

Every finding needs an eligible primary identity. A cluster is double reviewed only when two distinct eligible accounts reviewed **every member**. Unlabelled members, including endpoint bridges, cannot disappear from the review denominator. The required sample is pooled across the measured development and sealed clusters: `max(10, ceil(clusters / 5))`, not ten separately in each partition. Fewer than ten double-reviewed clusters never meet the requirement, even if every small-sample cluster was reviewed twice.

The report gives numeric coverage and exact verdict agreement over **all eligible complete reviewer pairs with distinct accounts** in double-reviewed clusters. An agent's model is part of its identity: different models on one account cannot combine partial coverage into a complete reviewer, or form an independent pair. A pair agrees only when its verdicts match for every member. Duplicate current verdicts from one reviewer identity are refused, so array order cannot select one. Disagreements remain recorded; the harness neither replaces the primary verdict, chooses an agreeing pair, drops findings nor invents an agreement threshold. Source-verdict adjudication remains a reviewer responsibility.

Missing metadata, a different product codeId, ineligible primary identities or an insufficient sample prevent a sealed headline once sealed labels exist and make the evaluation fail, including with `--allow-unlabelled`. Empty evidence is never ready. Reports expose counts and unmet conditions, not account/model strings, secondary rationales, citations or sealed subjects. This supplies the recording and audit mechanism; actual independent reviews remain required.

An unlabelled finding fails the run unless `--allow-unlabelled` is given. A label whose finding no longer appears is reported as stale (not on a partial run). Labels for sealed findings are committed only after the freeze.

## Mutants

`mutants.json` lists injected contradictions. Each is

```json
{
  "id": "x4-user-one-phantom-property",
  "repo": "dokploy",
  "detector": "X4_UNBACKED_PROPERTY",
  "description": "What the edit does.",
  "edits": [
    {
      "path": "openapi.json",
      "pointer": "/paths/~1user.one/get/responses/200/content/application~1json/schema/properties",
      "set": { "evalPhantomField": { "type": "string" } }
    }
  ],
  "expect": { "code": "X4_UNBACKED_PROPERTY", "leftMatch": "evalPhantomField" }
}
```

An edit is one of:

- `{ path, pointer, set }`, `{ path, pointer, remove: true }`, or `{ path, pointer, renameKey }`: an edit to a JSON document by RFC 6901 JSON Pointer. It holds no text from the document, so a mutant on an OpenAPI file stores no third-party content. The pointer must resolve (and, for `remove` and `renameKey`, the key must exist; for `renameKey`, the new key must be free), or the mutant fails loudly. The document is written back with two-space indentation.
- `{ path, find, replace }`: a literal text edit. `find` must match exactly once. Keep it to a few tokens; the committed ones are 60 characters or fewer, in MIT-licensed files.
- `{ path, append }`: appends text, and may create the file.

An edit that does not apply fails the mutant loudly, because silently picking an occurrence would measure the wrong edit. Edits are applied to a scratch copy, never the cache.

A mutant counts as detected when the mutated run reports a finding with the expected code (and `leftMatch` or `rightMatch` as substrings of the finding's `left` and `right` node ids, when given) whose id the unmodified run did not have. A mutant whose detector is UNKNOWN on the mutated run is a miss, not a detection. A detector with no mutant reports recall as `n/a`, never 1. A mutant never makes a detector count as firing on the corpus.

**Which side a match goes on matters.** Each detector fixes what it puts in `left` and `right` (X4: the unbacked property on the left, a backed sibling's producer on the right; X10: the writing symbol on the left, the PII column on the right). A match on the wrong side can never be credited and looks exactly like a detector that cannot find the defect. `packages/eval/src/roles.ts` records the roles, `parseMutants` refuses a mutant whose match does not fit them, and a test reads the detector sources and fails when a detector's sides stop matching the table.

Every detector X1 to X10 has at least one mutant. Several detectors cannot fire on real input yet; their mutants are there so that recall 0 is reported honestly. The historical ten-mutant evaluation detected none. The historical candidate-draft DEV evaluation detected the new supported X7 Board mutant (1/2 X7 mutants, 1/11 overall); a final-head measurement remains required. Whether the remaining mutants will be detected once their missing input exists is not established: several rely on facts nothing extracts today (each mutant's description says which), and the deferred design changes for X3, X4, X8 and X9 would need fresh measurement. X7 now reads complete validated-write SchemaProperty facts. Its old regex-bearing website mutant remains in the denominator because regex semantics are unsupported; the new Board mutant is additional. In particular the X9 mutant relies on the detector's first direction (an operation nobody serves), which cannot fire while every declared operation has an `IMPLEMENTED_BY` handler; the design leaves `extract-contracts` unchanged and changes the detector instead (unserved means the operation's route handler has no incoming `HANDLES_ROUTE`, behind a `routeMountsUnresolved == 0` precondition). The X4 mutant relies on a join between response properties and columns that is not extracted yet.

## Reading the report

- **Detectors, precision:** findings on the unmodified repositories, true positives, false positives, unclear, unlabelled, lenient precision with its 95% Wilson interval and n, strict precision, the same clustered, and the per-detector status (`unmeasured`, `meets 0.80`, `below 0.80`).
- **Detectors, recall and firing:** mutants evaluated, detected, not detected, of which UNKNOWN (the detector could not run on the mutated repository, which counts as not detected and says nothing about whether it would have fired), recall with n, whether the detector fires on the corpus, and on how many repositories it was UNKNOWN.
- **Partitions:** the same figures for dev and sealed, and the freeze state.
- **Provenance:** the freeze commit, the digest of the watched sources, the CLI that ran with the digest of its compiled output, and the digest of the unwatched harness code (the scorer). These are part of the deterministic body: equal values mean equal inputs.
- **Calibration:** observed precision per confidence band with its interval. A band with few labelled findings has a wide interval; confidence should be recalibrated only when a band falls outside its nominal range by more than that interval.
- **Repositories:** pinned commit, analysis outcome, node and edge counts, extractor statuses, and the scopes that were not PASS.

The report body is deterministic: sorted, with no timestamps. Run time, wall-clock durations, and the Node version are in a separate trailing section and under `run` in `report.json`.

## Not done yet

The design asks for these and this harness does not do them. A "met" cannot be quoted for a release until they are.

- **Independent review evidence.** The ledger audits declared primary coverage, the double-review sample and agreement. Actual independent reviews, verified account ownership and a complete change-author roster must still be supplied; the harness does not authenticate them.
- **Recorded passing release evaluation.** `docs/PUBLIC-RELEASE-CHECKLIST.md` item G8 requires a complete passing run after the release candidate commit, with the candidate SHA, corpus pins, report and provenance, independent review evidence and the actual figures. No qualifying frozen release run is recorded yet. An exit-zero development or underpowered run does not close that checklist item.
- **Calibration evidence.** Development-only band fitting and upstream-group holdouts are implemented. They do not establish calibrated lineage probabilities, independent label review, or a passing external evaluation. The report states the actual labelled sample and unavailable estimates.
- **Dormancy disclosure.** A detector that fires on no corpus repository is flagged in the report; a hand-written disclosure of each reason in the project README is not.
- **Fully generated edit descriptors.** JSON documents are edited by pointer. The few text edits to MIT-licensed source are still literal short `find`/`replace` strings, not anchors such as "Prisma model `Y`, field `X`".

## Confidence calibration

Report schema 8 retains each finding's original `confidence` and adds `calibratedConfidence`. The latter is null where a band is not estimable. It never removes a finding, changes severity, re-runs the detector confidence floor, or changes precision, recall, clustering or firing counts.

The target is raw finding correctness, TP/(TP+FP). Unclear and unlabelled findings remain counted but do not train this lenient calibration ratio. The original calibration table now describes development findings only. `confidenceFit` records the exact fitting-input digest, checkout names, upstream count, band sample counts, intervals, mapping and fold results. A band needs labelled findings from at least two development upstreams. A refit occurs only when its Wilson interval is wholly outside the nominal band; the mapped value is that development band's observed precision. Overlapping intervals retain the raw score, and sparse bands remain not estimable.

Each leave-one-repository-out fold excludes every checkout/pin of one canonical upstream URL, including parent/fix pairs. HTTPS URL identity normalizes trailing slashes and a .git suffix, and GitHub owner/repository case. Different remote URLs that alias the same project are not automatically resolved; corpus review must avoid such aliases. An upstream appearing in both partitions is refused. Fold Brier comparisons use exactly the same labelled findings with estimable mappings and print their denominator; an empty denominator is n/a.

The sealed labels only check the development mapping. They cannot change the mapping, refit decision or fitting-input digest. A poor sealed Brier score remains visible. Development and sealed finding counts still feed their original precision populations, including findings mapped to zero.

This is an experimental finding-level mapping. It does not fit each inferred graph edge, multiply into lineage chains, or validate the original heuristic scores. THREATMODEL R8 therefore remains a limitation. Actual independent labels, their sample size, holdout results and a complete frozen evaluation must accompany any release claim.
