# @seamline/extract-code-ts

> **No measured precision or recall; do not rely on Seamline as a gate.** This is an early release. The one recorded measurement was made on a draft source tree: it produced zero findings and detected 0 of 11 injected mutants. Details are in the [repository README](https://github.com/zylver-solutions/seamline#what-works-today-and-what-does-not).

TypeScript/JavaScript facts at provenance `EXTRACTED`. Reads a TypeScript project through ts-morph's type-checker-backed resolution (through re-exports and barrels to the canonical declaration) and emits `Repo`, `File`, `Module`, `Symbol`, `CodeField`, `Parameter`, and `RouteHandler` nodes with the containment, import/export, call, heritage, type-use, decorator, route, and query edges between them.

## Install

```bash
npm install @seamline/extract-code-ts
```

Requires Node.js 22.13 or later. Most users should not install or import this directly: `seamline extract` in `@seamline/cli` runs it as part of the normal pipeline. Import it directly only if you are building a tool that needs to run this extractor standalone. Installing it brings in `ts-morph`, and `npm install` then reports a moderate advisory in its `minimatch` dependency; see [known dependency advisories](https://github.com/zylver-solutions/seamline/blob/main/SECURITY.md#known-dependency-advisories).

## Usage

```js
import { extractCodeTs } from '@seamline/extract-code-ts';

const { result, nodes, edges } = extractCodeTs({
  repoRoot: process.cwd(), // a directory with a tsconfig.json, or a workspace of packages that have one
  repo: 'my-repo',
  runId: 'run-1',
});
console.log(result.status, nodes.length, edges.length);
```

From `seamline.config.json` you can set `tsConfigFilePath` in this extractor's `options`, and the top-level `include` and `exclude`. The `memoryBudget` and `dataModelIndex` options described below belong to the library function `extractCodeTs` and to the CLI's own wiring; they are not config keys.

## Behaviour

Two properties are load-bearing and both are tested in this package: identity is path-free for every kind except `File`, so a `git mv` within a package changes no symbol, field or parameter id (a moved `File` gets a new id, and `seamline extract` aliases the retired id to it when git reports the committed rename; moving a file to a different package changes the package part of its symbols' ids and is not aliased); and output is byte-identical across runs, so golden files and `seamline diff` mean something.

**Coverage.** The extractor reads the TypeScript project graph reachable from the root `tsconfig.json` (following `references` from a solution-style root), plus every other `tsconfig.json` under the root that the graph does not reference (an example app, a tools package), loaded the same way with its own `include`/`exclude`/`files`. Discovery skips `node_modules`, dot-directories, the loaded projects' `outDir`/`declarationDir`, and the run's `exclude`; a discovered config that cannot be loaded is reported and skipped. Files in no project are still not read. A `PASS` run lists each TypeScript/JavaScript file under the root that no loaded project includes as a diagnostic (`not in any loaded tsconfig project: <path>`, after a `tsconfig coverage: <read>/<candidates>` summary), and narrows its authoritative selector to what the loaded projects include: one `dir/**/*.<ext>` pattern per included directory and extension the project reads, plus `files` entries and any read file outside those directories by name. A file deleted from an included directory stays inside the selector, so its facts are tombstoned; a file outside every project stays outside it, so it is never tombstoned as deleted just because it was not read. A directory pattern that would also match an existing file the run did not read is left out, and that directory's read files are named instead. The run's `include`/`exclude` bound which files count and which configs are discovered; `node_modules` and a loaded project's `outDir`/`declarationDir` never count.

**Workspaces without a root tsconfig.** A monorepo often has a `tsconfig.json` per package and none at the root. When the root has no `tsconfig.json` (and no `tsConfigFilePath` was given), the packages are found from `packages` in `pnpm-workspace.yaml` and `workspaces` in the root `package.json` (an array, or an object with `packages`; both are read, `!` patterns leave directories out). The globs understand `*`, `**`, `?` and `{a,b}`, and match what the package managers match: `**` may match no directory at all, a trailing one included, so `packages/**` also names `packages` itself and `!**/test/**` leaves out `a/test`. A pattern that uses anything else (a character class, an extglob group, a backslash escape, nested braces, a brace group that spans a `/`) or that is unreasonably long is reported (`workspace pattern not supported`), and because the packages it names are never found it counts as unread (`pattern:<glob>`, below); a pattern longer than 80 characters is written in a diagnostic or a name as its first 80 characters and the number left out. A matching directory is a package when it holds a manifest: `package.json`, `package.json5` or `package.yaml`, the three names pnpm accepts (a directory with several is a package of the first in that order). A package with a `package.json` and a `tsconfig.json` is read from that `tsconfig.json`, with `extends` resolved the way the TypeScript API does and offline: a base named by a workspace package (`"extends": "@acme/tsconfig/base.json"`) is found in the repository even though nothing is installed. Nothing outside the repository is read: an `extends` that points out of it is a base that is not there. A package whose manifest is `package.json5` or `package.yaml` is found but not read: this extractor has no parser for either, the package name is what its ids are built from, and a guessed name would give the wrong ids, so a package of that kind that has a `tsconfig.json` is named unread, never silently absent. Its files are not read as a package of their own, but a readable package that imports one of them, or a tsconfig that `references` that package, still reads the file, and its facts are then declared under the enclosing package's name (the nearest ancestor with a `package.json`, often the repository root), so those facts carry ids that will change once the package itself can be read (tracked as a follow-up). The package is still named unread, so the detectors that reason from absence report UNKNOWN. A package whose tsconfig resolves no files and has `references` contributes the referenced configs. Each tsconfig is its own program, so each keeps its own `paths`, `jsx` and `moduleResolution`; every file is declared once, by the tsconfig that includes it whose directory is the nearest ancestor of the file (then config order; a config that reaches into another package with `include: ["../shared/src"]` ranks below the package the file lives in), else by the first program that reaches it by import, so ids do not depend on which program read a file. The run is `PASS` when at least one tsconfig was read, and its authoritative selector is built from the configs that were read, so a package that was not read is outside it and its facts are never tombstoned.

A tsconfig is **not read** when what it means cannot be known: TypeScript reports an error on it. That covers a syntax error in the file itself or in a base it extends (TypeScript recovers from one and goes on to read what it can, which would be wrong rather than absent), an unreadable file, circular `extends`, a relative `extends` that is not there, an unknown option, an option given a value of the wrong type or outside its choices (`"strict": "yes"`), and a `files` entry that is not there or lies outside the repository. It is also not read when it `extends` a package that is not installed and is not in the workspace (`expo/tsconfig.base`, `@tsconfig/node22`) and nothing readable settles null checking over it. The missing base could set `strict` or `strictNullChecks`, they decide what the checker reports as nullable, and facts read under guessed options would be wrong, not absent. Null checking counts as settled when the config itself sets `strictNullChecks` (any value, or a base listed after the missing one does), or sets `strict: true` after the missing base in the `extends` order; `strict: false`, no setting at all, and a setting that a later missing base could override are not. The residual: a missing base that sets `strictNullChecks: false` under a `strict: true` of the config itself is not noticed, because refusing every preset would leave a fresh clone with almost nothing readable. A config read this way says so (`workspace package read: ...`). Every package not read is named in a diagnostic (`workspace package not read: <dir>: <reason>`), as is a package with TypeScript or JavaScript files and no usable `tsconfig.json`. The `Repo` node then carries `unreadCodePackageCount` (exact) and `unreadCodePackages` (a JSON array of the first 25 sorted names, each a directory or `pattern:<glob>`; JSON because a directory name can hold any character), because `GraphView.scopeStatus` is one status per scope: `@seamline/contradictions` reads those props and reports UNKNOWN, not a finding, for the detectors that conclude something from the absence of a code fact (X4, X5, X9, X10), and the CLI (`why`, `blast-radius`, `check`) and the MCP server (`impact`, `lineage`, `context`, `explain`, `contradictions`) list a PASS `code.ts` scope that left packages unread as `PARTIAL`, so a negative answer over it is not read as "nothing reaches it". A workspace with no readable tsconfig at all, and a repository with neither a root tsconfig nor a workspace declaration, stay `UNAVAILABLE` with `no tsconfig.json at tsconfig.json` as the first diagnostic. A root `tsconfig.json`, when present, is used as before and the workspace declarations are not consulted; a project it references, or a discovered `tsconfig.json`, that cannot be loaded is named in the same `Repo` props (by directory) as an unread package. No absolute path reaches a diagnostic. The repository root is replaced by exact string first, in its native, POSIX and symlink-resolved spellings, so a checkout path that holds a space (`/home/John Smith/my repo`) leaves no fragment and a path inside the repository is never reported as outside it; the root counts only as a whole name, so a quoted sibling such as `'/work/repo two/x.json'` is outside, not the root followed by words. Any other absolute path in a message is then found by its shape (a quoted one whole, an unquoted one up to whitespace) and becomes `<outside the repository>`. An unquoted path outside the repository that holds a space therefore leaves the words after the space, which can include a part of a shared home directory such as a user name, and an unquoted sibling whose name is the root followed by a space and more (`/work/repo two/x.json`) shows as the root (`. two/x.json`). TypeScript quotes the paths it reports in nearly every message. A quoted path is taken whole, with one known exception: a quoted path that begins with the root, climbs out of it with `..` and then holds a space keeps the words after the space; TypeScript normalises the paths it prints, so it does not produce that form.

**Memory.** Every program stays alive until the run ends (the passes that follow need them all), so memory grows with the number of programs, and a very large workspace would pass the `memMb` the manifest declares. Which packages are read must be a function of the repository and nothing else (ADR-0009 section 3a), so it is decided from the input before any program is built, never from the process's resident memory. The programs are considered in package order, sorted by directory, and each is estimated from the size of its own file list (`parsed.fileNames`, in-repository files only; see Memory budget below). A program is read when the estimate of those already taken plus its own stays within the manifest's `memMb` (2048 MiB); one that does not fit what is left is not built and the next ones are still tried (first fit), so a large package early in the order does not hide the smaller ones after it. Each one left out is named unread with the reason `memory budget` (`workspace package not read: <dir>: <config>: memory budget`), through the same `Repo` props, so the run stays `PASS` for what it read, the contradiction detectors that reason from absence report UNKNOWN, and the output says the workspace was read partially. Every workspace run writes its estimate (`memory estimate: N MiB ... against a budget of M MiB`). The same tree, config and extractor version therefore name the same packages unread, with the same bytes, on every machine and every run, with one exception, the fail-safe described below: near the ceiling the outcome of a run (`PASS` or `UNAVAILABLE`) can differ from one run to the next, because the process's resident memory varies by tens of MiB between runs, while the bytes of a `PASS` cannot. The CLI runs every extractor in one process, so the extractors configured before this one add to the memory already resident when it starts: reordering `extractors` in the configuration moves the band in which that can happen.

**Memory budget.** The estimate is `baseMib + the sum over programs of (perProgramMib + perSourceMib * MiB of source)`, with three constants in `src/memory.ts` (`MEMORY_MODEL`): `baseMib` = 800 MiB (the process, the type checker's library files, and the passes' fixed costs), `perProgramMib` = 25 MiB (library files and checker state that every program repeats), and `perSourceMib` = 130 MiB (resident memory per MiB of source in a program's own file list, the passes included). They were calibrated against the peak resident memory measured in-process (`process.resourceUsage().maxRSS`, no heap cap) on five repositories, under two rules: the estimate is at or above the measured peak on every one of them, and the repositories that must be read whole (rallly, this repository, dokploy, karakeep) fit the 2048 MiB budget. The measurements are the table below and are pinned in `MEASURED` in `src/workspace-hardening.test.ts`, which fails when an estimate falls under a measured peak. To retune the constants, measure again and change the constants and that table together. This is a calibrated heuristic, not a proof, which is why the fail-safe exists.

What the budget bounds is that estimate of the run's peak resident memory, not what the process can reach. The margin is not large on the repositories that must be read whole:

| repository                 | programs | source (MiB) | measured peak (MiB) | estimate (MiB) | of the 2048 MiB budget |
| -------------------------- | -------: | -----------: | ------------------: | -------------: | ---------------------: |
| rallly                     |        5 |         0.06 |                 295 |            933 |                    46% |
| this repository, installed |       11 |         2.76 |                1347 |           1434 |                    70% |
| dokploy                    |        4 |         6.16 |                1465 |           1701 |                    83% |
| karakeep                   |       21 |         4.22 |                1782 |           1874 |                    92% |
| frapp                      |       14 |        15.78 |                2441 |           3202 |     156%, read in part |

The estimate is 6% above the measurement on this repository, 16% on dokploy, 5% on karakeep and 31% on frapp, and karakeep, the tightest repository that is read whole, uses 92% of the budget, so a repository a few percent larger than karakeep is read in part. Frapp peaked at 2441 MiB, past both the 2048 MiB heap cap and the host's kill line, and is read in part: its tsconfigs are taken in package order while they fit, which is 3 of its 14 (2034 MiB estimated, after which less than the estimate of the smallest of the others is left), with a peak of 1.2 to 1.4 GiB (it varies from run to run; the output does not). The estimate cannot see the declaration files of installed dependencies, which every program loads and which are not in the file lists: the repository measured with its `node_modules` installed has a peak only 6% under its estimate, and one with heavier dependency types could pass it. That is what the fail-safe is for. Resident memory is read only there: if it passes the ceiling (`memMb` by default) while programs are built or the passes run, the run ends `UNAVAILABLE` with nothing extracted, so no store sweeps anything and every scope that needs `code.ts` reports UNKNOWN. It is never a different `PASS`, and the reading itself is never written to the output. The options are `memoryBudget` (`mb` for the budget on the estimate, `ceilingMb` for the fail-safe, and `usedMb` to replace the process reading, which cannot change which packages are read). A budget too small for even one program leaves the run `UNAVAILABLE`, not an empty `PASS`.

**Routes.** A `RouteHandler` is emitted for a NestJS-style method decorator (`@Get(':id')` under `@Controller('users')`), and for a router call (`app.get('/users/:id', handler)`) only when the receiver is a server router or app: built by a factory or constructor imported from `express`, `fastify`, `hono`, `koa-router`/`@koa/router`, or `elysia`, or declared with one of those frameworks' app or router types (or a project-local type of that name). An HTTP client call such as `api.get('/users')` or `cache.get('/key')` has the same shape and is not a route. A receiver whose declaration cannot be traced (an untyped parameter, a value returned by a helper while the framework is not installed) is a missed route, not a guessed one. The rule is in `src/receiver.ts`.

**Table binding.** A table name in a SQL string binds to the `Table` node it means when the run is handed a data-model index (the `dataModelIndex` option: the canonical JSON text `buildDataModelIndex` in `@seamline/extract-data` produces from that extractor's output; this package does not depend on it, and never reads it from disk). Matching follows the dialect the data source recorded: PostgreSQL folds an unquoted name to lower case and keeps a quoted one exact, SQLite compares case-insensitively, and any other dialect compares exactly. A schema-qualified name binds only to that schema; an unqualified one binds to the data source's default schema. A name that two declared tables could both mean (`auth.users` and `app.users`, with no `public.users`) gets no edge, and the tables it may mean are listed in `unknownWriterTables` on the `Repo` node. A name no table matches keeps the name-only answer, an edge to an external `Table` node `{repo}:Table:{schema}.{table}`. So does an unqualified name that only one non-default schema declares (`only_other.widgets` and no `public.widgets`): it is not bound, because which schema a connection searches first is not in the code, but its name is listed in `unknownWriterTables` too, so a detector over the real table withholds instead of trusting "no traced write"; the real table gets no `QUERIES` edge, which costs recall. A repository whose tables all live in one schema other than `public` (Prisma `multiSchema`, Drizzle `pgSchema('app')`) is bound only when the `extract-data` `defaultSchema` option names that schema; see the `extract-data` README. Without an index (`extract-data` did not run, reached FAIL or crashed, knew of a source it did not read, or read sources that declared no tables, or the option was not given) the `Repo` node carries `ormIndexAbsent`, and the run is UNAVAILABLE rather than PASS if the files it read contain a raw-SQL table reference (any string the SQL classifier reads, which is loose: interface prose that starts with a statement verb and holds `from` counts), or an ORM-shaped write (`prisma.user.create({...})`, `db.insert(users).values(...)`) in a repository that mentions `@prisma/client` or `drizzle-orm`. Without the index a statement is not bound to a declared table and its edge points at the name-only table, and the ORM edges a write would have produced are missing; a PASS would tombstone the edges an earlier run, with the index, had bound. The diagnostic names the first such reference or call. The output is still returned, and nothing is swept. With neither, the run stays PASS. An index with no tables is an index, not an absent one: `seamline extract` hands it over when `extract-data` reports that its discovery found no schema source it reads or recognises and knew of none it did not read, every name then keeps the name-only answer, and the run stays PASS. That is a statement about discovery, not about the repository: a schema kept as another ORM's models, or in a database file, is not looked for. A source discovery knows of and did not read (a file over the size limit or one it could not open, a symbolic link, a file under `vendor/` or `build/`, an extension or a Drizzle dialect it does not parse, a Prisma schema a `package.json` names that it did not open) is the opposite case and keeps the index absent; see the `extract-data` README. This means a repository with raw SQL whose `extract-data` did not PASS for another reason (a crash, a source it did not read, or sources it read that declared no tables), and a run narrowed with `seamline extract --only extract-code-ts`, has an UNAVAILABLE code scope.

**Writes the extractor could not turn into an edge.** The `Repo` node records, on every run, what a detector needs to tell "no traced write supplies this column" from "something writes this table that was not seen" (`docs/design/real-world-inputs.md`, 5.2). All of it is lexical: it never resolves a receiver or reads `node_modules`, and a name collision can only over-count. `untracedWriteCalls` is a number: the places that write something no edge can name (`$executeRawUnsafe`, `$queryRawUnsafe`, `.unsafe` and `sql.raw` with an argument it cannot read; a statement whose table is a substitution, `CALL` and `EXEC`; `"INSERT INTO " + table`; a `Prisma.raw` or `Prisma.sql` fragment spliced into the verb or table position; a write on a computed delegate; `.insert`, `.update` and `.delete` in a file that imports `drizzle-orm`, `@supabase/supabase-js`, `knex`, `kysely`, `typeorm`, `sequelize` or `@mikro-orm/core` and does not name a table export of the index). `writeHooks` is a number: Prisma `$use(...)` and a `$extends(...)` that may inject fields into every write. `unknownWriterTables` is a sorted, comma-separated list of table names, `''` when there are none: a statement the index cannot settle, an ORM-shaped write that names a Prisma delegate or a Drizzle table export, and every table that a TypeScript or JavaScript file in no loaded tsconfig project names (as a table, model, delegate or export, as a whole word) when that file holds an insert marker. It is absent when it could not be measured (no index, or the files outside every project could not be read). A `Repo` node that was not emitted carries none of them; a missing prop is not zero. Each run lists its first counted places in `diagnostics`.

Main exports:

- `extractCodeTs`, `defaultTableId`, and the `ExtractCodeTsOptions`, `ExtractCodeTsOutput` types: the extractor entry point.
- `CODE_TS_AUTHORITATIVE`, `CODE_TS_SCOPE`, `EXTRACTOR_NAME`, `EXTRACTOR_VERSION`, `PRODUCED_KINDS`, `manifest` — the extractor manifest.
- `canonicalJson`, `canonicalize`, `toCanonicalSif`, `toSifLines` — deterministic serialization.
- `assertPathFree`, `codeFieldCanonicalName`, `fileId`, `moduleId`, `parameterCanonicalName`, `repoId`, `routeCanonicalName`, `symbolCanonicalName`, `ROOT_MODULE` — identity construction.
- `normalizeTypeText`, `splitTopLevelUnion`, `stripImportQualifiers`, and the `NormalizedType`, `NormalizedTypeInfo` types — type-text normalization.
- `looksLikeSql`, `sqlTableRefs`, `sqlTableOccurrences`, and the `SqlOperation`, `SqlTableOccurrence`, `SqlTableRef` types: SQL-in-code detection feeding the cross-domain join. An occurrence is a reference with the spelling and quoting it had.
- `parseDataModelIndex`, `tableBinder`, `SUPPORTED_INDEX_VERSION`, and the `DataModelIndex`, `IndexedDataSource`, `IndexedTable`, `ParsedDataModelIndex`, `TableBinding` types: reading the data-model index and binding a reference to a declared table.
- `joinRoute`, `normalizeRoutePath` — route path normalization.
- `isRepoRelativePosix`, `toRepoRelative` — path helpers enforcing the repo-relative POSIX path invariant.
